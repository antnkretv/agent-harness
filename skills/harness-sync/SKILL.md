# Обновление harness

Скилл лежит в каталоге `skills/` архива новой версии, и агент выполняет его оттуда, как `harness-init`:
скилл никуда не копируется. Установленная версия - поле `kit` `.harness/state/lock.json` проекта, ответы настройки и их происхождение -
`.harness/project/answers.json`. Порядок установки и разбор ошибок - `AGENT.md`
нового комплекта.


На Windows `configure` с ответом, значение которого начинается с `/` (`--answer docs.generatedSegments=/node_modules/`),
идет из Git Bash с префиксом `MSYS_NO_PATHCONV=1 MSYS2_ARG_CONV_EXCL='*'` в строке этой команды, а не в
окружении сессии (`AGENT.md`, начало).

Выпуск или коммит репозитория комплекта ставит одна команда `python3 .harness/ah.py upgrade [--version <версия> | --commit <ветка или коммит>]`
в клоне проекта: шаги 1-3, `apply` шага 4 и `verify --no-gates` шага 5 она выполняет сама и открывает
черновой PR, а на вопросах новой версии останавливается. Перенос правок проекта, которые `apply`
перезаписал (шаг 4), и полная приемка шага 5 остаются за агентом и человеком в ветке этого PR. Скилл нужен, когда новая версия - архив, а не выпуск или коммит, или когда `upgrade` остановился.

## 1. Комплекты

Путь к архиву новой версии и его sha256 - аргументы вызова; чего нет - спроси владельца. Сверь
sha256 и распакуй вне репозитория:

```bash
sha256sum <архив>                                   # не совпало с данным sha256 - стоп
KIT="$HOME/.cache/harness/$(basename <архив> .tar.gz)"
rm -rf "$KIT" && mkdir -p "$HOME/.cache/harness" && tar -xzf <архив> -C "$HOME/.cache/harness"
```

Архив установленной версии обновлению не нужен. Если он есть у владельца, до обновления
`"$INSTALLED/payload/.harness/hooks/python.cmd" "$INSTALLED/ah.py" status --target <repo>` из его
каталога `INSTALLED` печатает файлы и блоки комплекта, которые проект правил и `apply` перепишет. Архив версии,
которая держит слой в `.platform/`, запускается как `"$INSTALLED/payload/.platform/hooks/python.cmd"`, а
манифест проекта до обновления лежит в `.platform/project.json`: каталог переносит `apply`
нового комплекта.

## 2. Ветка

Из распакованного нового комплекта выдели рабочую копию до обновления:
`"$KIT/payload/.harness/hooks/python.cmd" "$KIT/ah.py" workspace --target <repo> --base origin/<base> --key harness-update`.
`<base>` - `git.baseBranch` манифеста `.harness/project/manifest.json`.
Продолжи в `path` из JSON результата; вторую ветку вручную не создавай.

## 3. Новые вопросы

```bash
"$KIT/payload/.harness/hooks/python.cmd" "$KIT/ah.py" configure --target . --next
```

Записанные ответы установщик берет из `answers.json`, правку манифеста руками - ответом владельца.
Печатается только то, чего прошлая версия не спрашивала: новый модуль, расширение, решение или
факт, а еще решение, записанное без владельца. Какие решения задаются и в каком
виде - раздел "Настройка" `.harness/docs/harness.md` проекта. Сводный вопрос - как при
установке, по п. 6 `$KIT/installer/stages/STAGE-1.md`. Поле `show` каждого вопроса выведи владельцу без правки и без своих слов вокруг, затем задай вопрос через AskUserQuestion, если он есть; ответ передай без правки:
`--answer '<id>=<значение>' --next`. Цикл идет до `{"done": true}`; `show` итога выведи так же без правки, строки `problems` итога
исправляются ответом через `--reopen <модуль>`. Приложение, появившееся после прошлой настройки,
входит в манифест вопросом `--reopen apps`.

## 4. Установка

```bash
"$KIT/payload/.harness/hooks/python.cmd" "$KIT/ah.py" apply --target . --archive <архив>
```

Файлы managed, блоки и ключи комплекта в файлах json `apply` пишет новой версией, даже если проект их
правил; блок project, ключи проекта в json и заготовки не трогаются, текст вне блоков переносится в блок project. Правку проекта, которую `apply` переписал,
в файлах оболочки показывает `git diff`, а поставленный файл `install` переписывает без следа в git, поэтому его правку проект переносит до обновления: нужную перенеси в место проекта, которое называет отказ гейта `harness-files`, а не вноси заново в файл комплекта, ненужную оставь снятой. Строки вывода о подключении к коду
делает агент, как при установке.

Правила, которые новая версия передала проекту, `apply` из блока комплекта снимает, а файл из списка
`released` манифеста комплекта оставляет на месте, без учета в `lock.json`. Снятые строки блока
показывает `git diff`: правила проекта (например, `[*.cs]` в `.editorconfig`) перенеси в блок project
того же файла. Строка вывода о файле, который передан проекту, называет, что ему нужно, чтобы гейт
дальше держал его правила.

## 5. Приемка

Проверь изменения и добавь в индекс только пути этой установки до проверки: гейты реестров читают
отслеживаемые файлы.

```bash
git status --short
git add -- <проверенные пути установки>
"$KIT/payload/.harness/hooks/python.cmd" "$KIT/ah.py" verify --target .
./.harness/hooks/python.cmd .harness/scripts/check/check-all.py --base origin/<база>
```

Заготовки (роль `seed` в `lock.json`) после первой установки принадлежат проекту, и установщик их не
правит. Строку `apply` "в комплекте новая редакция" у заготовки разбери в этом PR: сравни файл проекта с
заготовкой из `$KIT/payload/<путь>` и перенеси нужные правила, сохранив правки проекта. На файл комплекта
заготовка ссылкой не ведет: путь в коде, имя скилла или гейт, иначе `verify` отклонит ссылку на
установленный файл.

Новая версия может принести правило, которого существующий код еще не выполняет: код чинится в
этом PR. Выключить правило можно только записью с причиной и заменой по разделу "Как снять правило"
`.harness/README.md` проекта.

## 6. PR

Коммит явными путями из `git status`, `chore: обновление harness <версия>`, PR черновиком в базовую
ветку. В описании - новые вопросы и ответы на них, правки проекта, перенесенные в места проекта и снятые, правки кода под новые
правила; описание начинается с заготовки `./.harness/hooks/python.cmd .harness/scripts/text/text_templates.py form ChangeBody --out <файл>`, а собирает его `./.harness/hooks/python.cmd .harness/scripts/text/text_templates.py render change/description --set-file ChangeBody=<файл> --out <файл>`.
