# Этап 1: установка harness {{harness.kitVersion}}

Порядок этапов, обозначения, ошибки, критерии готовности и шаблон отчета - [AGENT.md](../../AGENT.md).
Этап кончается PR накатки: дальше этапы 2 и 3 идут отдельными сессиями по [STAGE-2.md](STAGE-2.md) и
[STAGE-3.md](STAGE-3.md).

## Что нужно до начала

- поддерживаемый профиль из [PARAMETERS.md](../../PARAMETERS.md#границы-внедрения);
- архив `{{harness.archive}}` и его sha256 от того, кто дал архив;
- клон репозитория проекта с origin, из которого `git push` проходит без запроса пароля: SSH-ключ в
  `~/.ssh` или `ssh-agent` либо HTTPS-токен, сохраненный git credential helper;
{{#if module:forge/github}}- вход `gh` в GitHub с правами администратора репозитория для меток, секретов и защиты веток - или
  человек, который выставит их по списку из отчета;
{{/if}}{{#if module:forge/gitlab}}- токен GitLab с ролью Maintainer в переменной среды `GITLAB_TOKEN` - в окружении оболочки или IDE,
  где идет установка;
{{/if}}- Python 3.11+: на Windows - Python Launcher или `python` в PATH;
- для исполнителя Cursor в локальном круге и агентах - `cursor-agent` и `CURSOR_API_KEY` в переменных среды;
- место на диске: этап 3 собирает решение .NET и ставит зависимости node - не меньше 3 ГБ свободно,
  `doctor` его не проверяет: агент смотрит `df` до этапа 3;
- владелец проекта в чате: он отвечает на вопросы о модулях и настройках.

Что из этого есть на машине, проверяет `doctor` (раздел "Зависимости"). Отказ по инструменту агент
снимает скриптом установки из этого раздела и повторяет `doctor`. Отказ доступа (`git push`, вход
`gh`, токен GitLab) и Python - действие владельца: агент называет строку `doctor` и не ищет обходной
путь.

## Проверить и распаковать комплект

```bash
sha256sum {{harness.archive}}          # сверить с данным sha256; не совпало - стоп, архив не тот
KIT="$HOME/.cache/harness/$(basename {{harness.archive}} .tar.gz)"
rm -rf "$KIT" && mkdir -p "$HOME/.cache/harness" && tar -xzf {{harness.archive}} -C "$HOME/.cache/harness"
"$KIT/payload/.harness/hooks/python.cmd" "$KIT/ah.py" --help
```

Каталог распаковки лежит вне репозитория проекта: комплект в дерево проекта не коммитится, в проект
попадает только то, что ставит `apply`. Архив хранится у владельца: `harness-configure` и `verify`
идут архивом установленной версии. Если в `KIT` есть `config.json`, архив собран под решения
владельца: модули уже выбраны, и настройка спросит только факты проекта.

Прочитай до любой правки:

## Ветка установки

До правок проекта выдели рабочую копию этапа 1 кодом распакованного комплекта:

```bash

```

Команда работает до появления `.harness` в проекте и создает `chore/harness-install`. Повтор использует ту же копию;
другую ветку вручную не создавай. Конфигурация, установка и PR этапа 1 выполняются в полученном каталоге.

## Зависимости

```bash
"$KIT/payload/.harness/hooks/python.cmd" "$KIT/ah.py" doctor --target .
```

`doctor` сверяет машину со списком `dependencies` в `$KIT/kit.json`: отсутствие проверяемой
обязательной зависимости - `error`, нужной CI - `warning` локально. Python он проверяет через
`python.cmd` - тот интерпретатор, который выберут все команды; push в origin - пробным
`git push --dry-run` без запроса пароля; токены поставщика кода и `CURSOR_API_KEY` - по
переменным среды. До `configure` он не знает выбранных модулей, поэтому после завершения
настройки его повторяют. Запись без `probe`, `status` и `env` выводится
как `info`, отсутствующий optional-инструмент не блокирует проверку; для выбранной автоматизации
его все равно может потребоваться установить. Приемка проекта выполняется отдельно. Недостающее ставят
скрипты `$KIT/payload/.harness/provisioning/scripts/`:
{{#if module:prose/vale}}`ensure-vale.sh`,
{{/if}}{{#if module:shell/shellcheck}}`ensure-shellcheck.sh`,
{{/if}}{{#if stack:dotnet}}`ensure-dotnet-sdk.sh --repo <каталог решения>` по `global.json`,
{{/if}}{{#if stack:node}}`ensure-node.sh` по `.node-version` после установки,
{{/if}}их можно звать до установки.

На Windows путь из JSON результата `workspace` переводит `cygpath -u '<path>'`, а инструменты в
выделенной копии готовят так:

```bash
{{#if stack:dotnet}}SDK_PROJECT_DIR="$PWD/<каталог решения>"
bash "$KIT/payload/.harness/provisioning/scripts/ensure-dotnet-sdk.sh" --repo "$SDK_PROJECT_DIR"
. "$KIT/payload/.harness/provisioning/lib/dotnet.sh"
export DOTNET_ROOT="$(resolve_dotnet_sdk_root "$SDK_PROJECT_DIR" "$HOME/.dotnet")"
export PATH="$DOTNET_ROOT:$PATH"
{{/if}}{{#if module:prose/vale}}bash "$KIT/payload/.harness/provisioning/scripts/ensure-vale.sh"
{{/if}}{{#if module:shell/shellcheck}}bash "$KIT/payload/.harness/provisioning/scripts/ensure-shellcheck.sh"
{{/if}}export PATH="$HOME/.local/bin:$PATH"
```

Если HTTPS обрывается, а без корпоративного прокси работает, сначала исправляют настройки прокси
оболочки. Отключение проверки TLS не требуется. Docker Desktop должен работать с Linux-контейнерами.

## Настройка: вопросы установщика

```bash
"$KIT/payload/.harness/hooks/python.cmd" "$KIT/ah.py" configure --target . --next
```

Подключение без отдельной сверки плана идет одной командой `init` с теми же флагами вопросов:
`"$KIT/payload/.harness/hooks/python.cmd" "$KIT/ah.py" init --target . --archive <архив> --next`. Она задает те же
вопросы, а после `done` сама выполняет `apply` архивом, как раздел "Установка" ниже, без `--dry-run`.
Повторный `init` в подключенном проекте отказывает.

Команда печатает один следующий вопрос JSON. Перед ним установщик сам отвечает на факты проекта,
которые нашел в дереве, - имя, ветки, приложения, пути; поле `answered` перечисляет их. Поле `show` -
текст для владельца: найденные факты, вопрос, пункты и варианты. Поля вопроса -
[настройка](../../payload/docs/platform/agents/harness.md#настройка).

Цикл, пока не напечатано `{"done": true, ...}`:

1. Выведи владельцу `show` без правки: не пересказывай, не сокращай, не сливай строки и ничего не
   дописывай к нему - ни id вопроса, ни слов "вопрос установщика". То, что агент пишет владельцу по
   п. 2, 4, 5 и 6, идет отдельным сообщением.
2. Есть AskUserQuestion - задай через него вопрос `text` с вариантами `options` (`label`,
   `description`): `single` - один выбор, `multi` - несколько, `text` - свободный ответ. Решение о
   модулях, расширениях и настройках принимает владелец: агент на них не отвечает и значение по умолчанию
   за владельца не принимает.
3. Ответ владельца передай без правки, тем же вызовом получи следующий вопрос:

   ```bash
   "$KIT/payload/.harness/hooks/python.cmd" "$KIT/ah.py" configure --target . --answer '<id>=<значение>' --next
   ```

   `multi` и списки - значения через запятую, объекты - JSON.
4. Факт, которого в дереве нет, но у вопроса есть `rule`, агент определяет по `rule` сам:
   `--set '<id>=<значение>'` вместо `--answer`. Значение запишется с происхождением `agent`: выведи
   его в чат строкой `<id> = <значение>` и назови в отчете. На решение `--set` установщик отказывает:
   `rule` решения подсказывает владельцу, как ответить, а не агенту.
5. Отказ `configure` с кодом 2 называет, чем ответ не подошел: переспроси владельца.
6. Сводные вопросы `stack` и `defaults` - решения владельца одним ответом; пункты перечисляет
   `show`. Ответ `keep` оставляет все пункты. Ответ `change` - не ответ: спроси владельца, какие
   пункты исключить, и передай их id через запятую, например
   `--answer 'defaults=modules.githooks,modules.agents.settings.pushback'`. Каждый названный пункт
   установщик затем спрашивает отдельным вопросом.

Порядок вопросов и решения, которые установщик пишет без вопроса, -
[настройка](../../payload/docs/platform/agents/harness.md#настройка).

- Конвенцию имен веток `git.branchConvention` - `conventional` или `gitflow` - решает владелец:
  одна конвенция действует для агента и человека ([`CONTRIBUTING.md` §2](../../payload/CONTRIBUTING.md#2-ветки)).
  Ветки этапов установки - `chore/harness-*` - совпадают в обеих.
- Пути `docs.*` - то, что гейты текста и документов не разбирают или читают иначе:
  `generatedSegments` и `generatedPrefixes` - сгенерированное и вендорное (детектор предлагает
  найденные `.design-sync`, `dist`, `node_modules`), `machineTextPrefixes` - машинный текст,
  `liveDocPrefixes` - живые документы, `historicalPrefixes` - датированные записи, `vendoredSkills` -
  скиллы чужой поставки (детектор предлагает каталоги `.agents/skills/` с `LICENSE`). Найденное
  `configure` записывает сам и выводит в `answered`: сверь его с деревом по обследованию, пропущенный
  каталог дает находки гейтов на чужом тексте и добавляется по `rule` ответом
  `--set 'docs.<ключ>=<список>'`.
  Скиллы пакетов модуля `skills` `configure` вписывает в `vendoredSkills` сам.
- Приложение `node` без слоев - сквозные тесты, плоский пакет - получает причину в
  `apps.<id>.architectureWaiver`: гейт `node-adapter` тогда не ждет `layerBoundaries`.

Итог - `.harness/project/manifest.json` и `.harness/project/answers.json`. Второй файл хранит каждый ответ
и его происхождение ([настройка](../../payload/docs/platform/agents/harness.md#настройка)). Оба коммитятся. `show` итога `done` выведи владельцу
так же без правки: в нем факты последнего вызова и проблемы манифеста. `answered` итога `done` -
факты последнего вызова; в `problems` итога - что манифест не прошел; их исправляют ответом, повторив вопрос:
`configure --target . --reopen <модуль> --next`. После `done` повтори `doctor`.

## Установка

```bash
"$KIT/payload/.harness/hooks/python.cmd" "$KIT/ah.py" apply --target . --dry-run   # план без записи
"$KIT/payload/.harness/hooks/python.cmd" "$KIT/ah.py" apply --target . --archive <архив>
```

| Код | Значит | Что делать |
| --- | --- | --- |
| 0 | установлено | дальше следующий раздел |
| 2 | отказ до записи: манифест, модуль вне архива, JSON проекта не разбирается, серверы или ключи TOML блока project повторяют блок комплекта, навык проекта занял имя навыка комплекта | исправить причину из вывода и повторить |

Существующий файл проекта на пути файла комплекта `apply` заменяет файлом комплекта; в JSON ключи
объединяются без потерь; в общий файл проекта вставляется блок с маркерами, а прежний текст файла уходит в блок project. До `apply` сверь план `--dry-run` с деревом: свое содержимое
замененного файла проект переносит в свои файлы. Повторный `apply` того же архива ничего не меняет.
`lock.json` записывает версию комплекта, объект git манифеста, включенные пути и роли файлов.

Скиллы проекта живут в `.agents/skills/`: Codex и Cursor читают этот каталог сами, Claude Code - через
`.claude/skills`. Правила агентов по путям живут в `.agents/rules/` одним файлом на правило, с
фронтматтером обоих агентов (`paths` для Claude Code; `description`, `globs`, `alwaysApply` для Cursor).
Ссылки `.claude/skills`, `.claude/rules/harness-<имя>.md` и `.cursor/rules/harness-<имя>.mdc` на них
создает старт сессии: [ссылки агентов](../../payload/docs/platform/agents/environment.md#ссылки-агентов).
Свои скиллы из прежнего каталога `.claude/skills/` и свои правила из `.claude/rules/` и
`.cursor/rules/` проекта переносятся в `.agents/skills/` и `.agents/rules/`, а каталог
`.claude/skills/` и прежние файлы правил удаляются: каталог на месте ссылки останавливает старт
сессии, а правило вне `.agents/rules/` отклоняет `check-docs.py --area agents`.

## Поставщик кода

```bash
./.harness/hooks/python.cmd .harness/scripts/release/forge-setup.py
```

Скрипт ставит недостающие метки конвейера, печатает секреты включенных модулей - имя, задание и с какого
момента он нужен - и сверяет их по именам; защиту веток он печатает владельцу. Для `<base>` процесс `change` требует обязательные `check`

успех скрипта не означает, что защита выставлена. Код 1 - метка не встала или настройка не прочитана:
блокер этапа 1; код 4 - блокеров нет, но не хватает секретов CI или их не удалось прочитать: не блокер
этапа 1, перечень идет в отчет действием владельца; код 3 - поставщик кода недоступен: нет `gh`, его
входа или репозитория в манифесте. Перечень секретов скрипт печатает первым, до чтения площадки. Нет доступа к защите
веток, rulesets или секретам (включая ответ 403) - готовность установки не подтверждена;
нужные действия владельца перечисляются в отчете. Секрет CI нужен к первому запуску своего
задания, а не для PR установки: этап 1 их отсутствие блокером не считает. PR установки в CI проходит
только Check, которому секреты не нужны, а ревью первой установки идет локальным кругом.

## Поставщик кода

```bash
./.harness/hooks/python.cmd .harness/scripts/release/forge-setup.py
```

Скрипт ставит недостающие метки конвейера, сверяет по именам переменные CI/CD, которые нужны
включенным расширениям, и при включенных ревью или агенте задач в CI заводит триггер конвейера с
вебхуком событий запросов на слияние и комментариев на ветке `<base>`: на них идут круг ревью и агент задач. Он сверяет минимальную роль
переменных конвейера (`maintainer` или `owner`), защиту веток `<base>` и релиза и "Pipelines must
succeed"; владельцу печатает правило одобрения учетной записи конвейера, защищенные окружения и
защиту переменных секретов. Код 1 - метка или вебхук не встали, настройка доверия
не та: блокер этапа 1; код 4 - блокеров нет, но не хватает переменных секретов CI или их не удалось
прочитать: не блокер этапа 1, перечень идет в отчет; код 3 - поставщик кода
недоступен: нет `GITLAB_TOKEN` или проекта в манифесте. Перечень секретов скрипт печатает первым, до чтения площадки. Нет прав Maintainer - это блокер
готовности: перечень из вывода скрипта идет в отчет действием владельца. Секреты включенных модулей
скрипт печатает с заданием и моментом, с которого каждый нужен, и где его задать: Settings => CI/CD =>
Variables, Protected и Masked с окружением (Environment scope) из шагов владельца, `GITLAB_READ_TOKEN` -
Masked; токен записи - Project access token (Settings => Access tokens, роль Maintainer, scope `api`). Секрет нужен к первому
запуску своего задания, а не для запроса установки: этап 1 их отсутствие блокером не считает. Запрос
установки в CI проходит только `harness-check`, которому секреты не нужны, а ревью первой установки
идет локальным кругом.

Свои задания и `workflow` проекта агент переносит из `.gitlab-ci.yml` в файлы `include` с правилом
`if: $HARNESS_PIPELINE == null`, дописанные к списку после блока комплекта: конвейеры событий и работ
комплекта их не несут. Ключ `.gitlab-ci.yml` вне блока и `include` без правила отклоняет
`check-pipeline.py`.

Свой `workflow:` проекта в файле `include` перекрывает `workflow:` комплекта из `.gitlab/ci/harness.yml`:
GitLab оставляет одно определение `workflow:rules`. Тогда первыми правилами его `rules` идут правила
комплекта в том же порядке - без них конвейеры релиза и мержа в базу теряют запрет автоотмены. `apply`
печатает эти правила строкой подключения к коду с файлом проекта; агент переносит их на этапе 1, а
`check-pipeline.py` - гейт `pipeline` в `verify` и Check - отклоняет `workflow` проекта без них.

## PR накатки

Проверь изменения, добавь в индекс только пути установки и сверь установленный слой:

```bash
git status --short
git add -- <проверенные пути установки>         # явные пути, без -A и .
"$KIT/payload/.harness/hooks/python.cmd" "$KIT/ah.py" verify --target . --no-gates
./.harness/hooks/python.cmd .harness/scripts/text/text_templates.py render commit/message --set-file CommitSubject=<файл заголовка> --set CommitBody= --out <файл сообщения>
git commit -F <файл сообщения>
git push -u origin chore/harness-install
```

Заголовок `chore: установка harness {{harness.kitVersion}}` записывается в файл инструментом записи файла, а не
аргументом командной строки: в PowerShell кавычки и кириллица в `git commit -m` обрезают сообщение. Формат
до коммита проверяет хук `commit-msg` модуля `githooks`, без модуля - команда
`bash .harness/scripts/check/commit-format.sh <файл сообщения>`; `--no-verify` не используется. После
повторного `apply` пути установки добавляются в индекс заново.

`verify --no-gates` - параметры, совпадение манифеста с ответами настройки, модули без причины выключения при
найденной технологии, реестр правил, области и инструменты, без гейтов дерева:
гейты разбирают этапы 2 и 3. Инструменты, нужные CI, ставят скриптами раздела "Зависимости" до коммита:
те, что `doctor` показал предупреждением. На Windows `apply`
сам кладет исполняемые файлы комплекта в индекс с режимом `100755`.
{{#if module:forge/github}}
PR открывается черновиком в `<base>`; номер PR за веткой для трейлеров `commit-msg` записывает
команда открытия ниже. Разделы тела PR - по `.github/pull_request_template.md`, тело
начинается с заготовки `text_templates.py form ChangeBody`, а собирает его установленная команда `text_templates.py render change/description --set-file ChangeBody=<файл>`.
{{/if}}{{#if module:forge/gitlab}}
Запрос на слияние открывается черновиком в `<base>`; номер запроса за веткой для трейлеров `commit-msg`
записывает команда открытия ниже. Разделы тела - по шаблону запроса проекта, тело
начинается с заготовки `text_templates.py form ChangeBody`, а собирает его установленная команда `text_templates.py render change/description --set-file ChangeBody=<файл>`.
{{/if}}{{#if module:forge}}

```bash
./.harness/hooks/python.cmd .harness/lib/forge.py open-change --head chore/harness-install --base <base> \
  --title "chore: установка harness {{harness.kitVersion}}" --body-file <собранное тело> --draft
```

Заголовок - по `CONTRIBUTING.md` §3 проекта, тело - файл из `render`: без описания и с другим
заголовком команда отказывает. PR этапов 2 и 3 открывает та же команда со своей веткой, базой и
заголовком.

Правки этапа над деревом проекта часто превышают `policies.size` методологии: тогда тело PR несет
строку с меткой `policies.size.reason` и причиной, ее читает гейт `pr-size`.
Check PR этапа 1 красен только на гейтах, которые чинят следующие этапы: нарушения в документах
(гейты `check-all.py --docs --list`) - этап 2, нарушения в коде и остальные гейты `check-all.py` - этап 3. Отчет называет каждый
такой гейт с числом нарушений в строке "Работа следующих этапов"; отказ приемки установки (`verify`)
- работа этапа 1. Критерии этапа 2 - [STAGE-2.md](STAGE-2.md), раздел готовности в `AGENT.md`. PR
сливаются от последнего к первому: этап 3 - в `chore/harness-context`, этап 2 с ним - в
`chore/harness-install`, затем PR этапа 1 - в `<base>`: его голова несет все три этапа, Check на ней
зеленый, и PR проходит защиту `<base>` и Ready проекта. Перед Ready локальный круг из раздела ниже
повторяется доверенным архивом на этой голове: политику ревью этапов 2 и 3 задают ветки установки.

### Локальное ревью первой установки

Если в базе PR еще нет harness и движка локального ревью, пакет готовят внешним доверенным
комплектом. Точкой входа служит его `ah.py`, а не скрипт из проверяемой ветки. SHA-256 всего
архива получают от владельца или проверенного источника вне PR; контрольная сумма из самого PR
не подтверждает доверие.

```bash
"$KIT/payload/.harness/hooks/python.cmd" "$KIT/ah.py" review --target <проект> --archive <доверенный-архив.tar.gz> --sha256 <проверенный-SHA256> --pr <номер> --base origin/<база> --work <каталог-вне-проекта> --provider <провайдер сессии> --context <постановка>
```

Команда требует чистую опубликованную голову PR и совпадение головы и базы с данными площадки.
Движок, политика, промпты, стандарты и корневые skills берутся из проверенного архива. Шаблоны
инструкций разворачивает его renderer; исходные AGENTS.md и REVIEW.md из базы сохраняются как
контекст проекта. Их версии из PR политику разбора не меняют. Настройки проекта
используются только как проверенные данные; адрес API и репозиторий должны соответствовать
фактическому origin. Настоящая база и рабочая копия проекта не меняются: политика добавляется
только в отдельное дерево пакета. Подготовка возвращает прежний `round.json`; независимые агенты
сессии работают по нему без запуска оплачиваемого CLI командой подготовки.

После сохранения ответов и журналов повторяют команду с теми же архивом, SHA-256, PR, базой,
каталогом и провайдером, добавив `--collect`. Комплект заново проверяет архив, делегированные
инструменты, снимки деревьев и контекст. Без журнала с подтвержденным чтением вердикт не принимается.
Деревья пакета остаются для проверки. Если движок уже есть в базе, используют существующий вход
ревью проекта; этот bootstrap к установленной базе не применяется.
