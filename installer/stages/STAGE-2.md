# Этап 2: документация проекта

Порядок этапов, обозначения, ошибки, критерии готовности и шаблон отчета - [AGENT.md](../../AGENT.md).

Копию выделяет установленный harness:

```bash
./.harness/hooks/python.cmd .harness/scripts/pipeline/task-worktree.py start --type chore --key harness-context --base origin/chore/harness-install
cd <path из JSON результата>
```

Перечень правок агента `apply` комплекта печатает без записи; его повторяют после правок этапов 2 и 3:

```bash
"$KIT/payload/.harness/hooks/python.cmd" "$KIT/ah.py" apply --target . --dry-run
```

Заготовки проекта - файлы роли `seed` в `$KIT/kit.json`, которые есть в
`.harness/state/lock.json`; свойства csproj раскладки к ним не относятся. Заготовка, которую
создала установка, заполняется фактами проекта: стек, продукт, функции, предметная область. Документ
проекта, поверх которого заготовка не легла, сверяется с разделами `$KIT/payload/<путь>`, дополняется
недостающими фактами и раскладывается по канонам документации комплекта. Глоссарий, промпты и
документы проекта приводятся к стандартам комплекта, пока гейты документации по всему дереву не станут
зелеными, включая ссылки и якоря. Код проекта этап не правит: реестры текста, комментарии и все, что
ловят анализаторы, - этап 3. База проверки - ветка, в которую открыт PR этапа: по ней `commit-format`, `requirements-registry` и
скан секретов истории читают коммиты этапа.

```bash
./.harness/hooks/python.cmd .harness/scripts/check/check-all.py --docs --base origin/chore/harness-install
"$KIT/payload/.harness/hooks/python.cmd" "$KIT/ah.py" verify --target . --no-gates
```

`--docs` запускает только гейты документации и каждый - на полном охвате, а не на диффе: ссылки и
якоря - во всех отслеживаемых Markdown проекта. Нарушения чинятся, а не
выключаются:

| Гейт | Что чинить |
| --- | --- |
| `docs-structure` | битая ссылка, битый якорь в любом отслеживаемом Markdown проекта (файлы комплекта сверяет комплект), документ вне индекса, нет строки типа Diataxis у документа под `docs.typedPrefixes`; [лимит корневых файлов](../../payload/docs/platform/standards/root-entry-docs.md#роли-файлов): текст проекта вместе с блоком комплекта укладывается в него, лишнее уходит в документы по ссылке |
| `doc-symbols` | имя кода в документе, которого нет в коде: имя исправляется по коду или убирается |
| `adr-reference` | голый номер ADR в документе - ссылка на файл решения |
| `pipeline` | промпты и контракт конвейера, на которые ссылаются документы |
| `commit-format` | сообщение коммита ветки установки против Conventional Commits - переписать сообщение |
| `agent-permissions` | конфиги разрешений агентов (`.claude/settings.json`, `.codex/rules/harness.rules`, `.cursor/cli.json`) расходятся с политикой запретов в `.harness/` - собрать их заново по выводу гейта |
| `requirements-registry` | ветка изменила свидетельство записи реестра `docs/platform/requirements/registry.md`, а запись не обновлена - обновить запись |
{{#if module:prose/vale}}| `prose` | текст документа против правил письма - по выводу Vale |
{{/if}}{{#if module:secrets/gitleaks}}| `secret-scan` | секрет в истории ветки: удалить, отозвать, переписать историю ветки установки |
{{/if}}
Правило, которое к проекту действительно не применимо, выключается записью `rules.disabled` с
`reason` и `replacement` в `.harness/project/manifest.json` (`.harness/README.md`, раздел "Как
снять правило"), после нее - `configure --target . --next` и `apply`. Обход гейта (`--no-verify`, выключение без причины, подавление в коде) - не решение.

Первый прогон называет нарушения; пока чинишь их, гоняй скрипт гейта, который чинишь, из
`.harness/scripts/check/`. Повторный прогон обеих команд идет один раз, после апрува всех проходов
ревью, перед Ready.

PR этапа 2 открывается в `chore/harness-install`, ревью - локальным кругом harness проекта:
скилл `.agents/skills/review/SKILL.md`. Этап готов, когда `check-all.py --docs` зеленый локально и, с
поставщиком кода, те же гейты зеленые в Check на голове PR. `adr-reference` и `secret-scan` в Check читают
и код, и дерево целиком: их отказ только на коде - работа этапа 3, на документе - этапа 2. Красные гейты
вне `--docs` - работа этапа 3.
