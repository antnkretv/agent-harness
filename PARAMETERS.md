# Параметры, модули и зависимости

Справочник параметров проекта ставится вместе со слоем:
[`payload/docs/platform/agents/harness-parameters.md`](payload/docs/platform/agents/harness-parameters.md) - в
проекте это `docs/platform/agents/harness-parameters.md`. Там манифест `.harness/project/manifest.json`, модули
каталога с расширениями и настройками, стеки приложений, внешние зависимости и настройки GitHub для
конвейера issue-dev. Архитектурные гейты по стекам и модулям -
[`gates.md`](payload/docs/platform/architecture/gates.md), устройство слоя и
обновление - [`harness.md`](payload/docs/platform/agents/harness.md), формат каталога `modules.json` -
[ниже](#каталог-modulesjson).

Здесь - только то, что принадлежит самому комплекту: границы внедрения, архив, каталог модулей, манифест
и коды установщика.

Места расширений проекта, которые `apply` после создания не пишет, - `.harness/project/` (манифест,
ответы, карта областей, сообщения, гейты `rules.own`, шаги `setup/`), заготовки `project-check.yml` и
`project-deploy.yml` и настройки машины `.harness/settings.env`: перечень и порядок чтения -
[расширения проекта](payload/docs/platform/agents/harness.md#расширения-проекта) и
[настройки окружения](payload/docs/platform/agents/harness-parameters.md#настройки-окружения). Перечень
настроек с значениями по умолчанию комплект держит файлом
[`payload/.harness/settings.defaults.env`](payload/.harness/settings.defaults.env).

Параметры выбирают реализованные модули и адаптеры, описанные в
[границах внедрения](#границы-внедрения). Новое имя стека, CLI или площадки не создает
интеграцию. Для стека без адаптера нужны собственные `check` и точка входа `entries.architecture` либо
`architectureWaiver`; инструменты такого стека проект устанавливает сам. `docs.index` меняет
корень проверки достижимости, но не переносит все пути документации в payload и build-конфигах.

## Границы внедрения

Комплект переносит методологию вместе с ее правилами: централизованными инструкциями и скиллами,
структурой документации, трассировкой требований и проверками существующего дерева. Первая установка
требует миграции проекта под выбранные правила, подключения проверок к коду и настройки CI.
`configure` выбирает состав, `pack` сокращает архив; обязательное ядро остается.

| Область | Встроенная поддержка и границы |
| --- | --- |
| Стеки | Архитектурные адаптеры .NET и TypeScript/npm. Другие стеки подключаются собственной командой `check` и точкой входа `entries.architecture` либо обоснованным `architectureWaiver`; их инструменты проект ставит сам. |
| Node | Корневой npm workspace, один lock-файл, flat ESLint и исходники TypeScript. Чистый JavaScript, pnpm, yarn и Bun требуют отдельного адаптера или миграции; замены имени команды недостаточно. |
| .NET | Импортируется журнал диагностик SARIF: гейт `build-diagnostics` требует ноль диагностик сборки, `dotnet-format` - раскладку CSharpier. Анализаторы, арх-тесты и политику сборки проект подключает сам точками входа `analyze` и `architecture`. |
| Код, задачи и CI | Адаптеры GitHub/GitLab и GitHub Issues/Jira, либо работа без forge. Другой поставщик требует реализации адаптера и CI. |
| Агент | Claude Code, Codex и Cursor CLI; установщик Cursor CLI поддерживает Linux/macOS, на native Windows Cursor CLI ставит его собственный установщик ([окружение агентов](payload/docs/platform/agents/environment.md)). Версии, модели и effort настраиваются. Произвольный CLI или OpenAI-compatible endpoint требует новой интеграции запуска, учетных данных и разбора результата. |
| Машина | Linux/macOS и native Windows x64. На Windows нужны Git for Windows с Bash, Python 3.11+ (Python Launcher или `python` в PATH), Docker Desktop и PowerShell; harness сам выбирает Git Bash и интерпретатор Python. |

`doctor` проверяет зависимости машины в пределах выбранных модулей; до `configure` выбор еще
неизвестен. Записи без проверки (`probe`, `status`, `env`) и отсутствующие optional-инструменты не подтверждают
готовность проекта. После настройки повторяют `doctor`, затем проходят `verify` и проверки кода.
Локальные smoke-сценарии проверяют генерацию и контракты интеграций; готовность живого CI,
секретов и учетных записей подтверждается отдельным запуском в целевом проекте.

Ревью GitLab требует исходный MR pipeline в том же проекте и API с фильтром `pipeline_id`
для статусов коммита: минимальную версию API проверяет адаптер
[`gitlab_adapter.py`](payload/.harness/lib/gitlab_adapter.py). Результаты merged-results и fork
не принимаются как подтверждение исходного SHA. Оснастка и политика круга берутся с защищенной
целевой ветки MR, конвейеры событий, задач и разбора алертов - с `git.baseBranch`, а не с ветки по
умолчанию площадки. Условие слияния у GitLab - одобрение учетной записи круга, которое комплект
ставит вместе с успешным `pipeline/ready`. Права учетных записей, создание MR pipeline и
блокировка слияния проверяются при настройке живого проекта.

На GitHub процесс `change` в базовую ветку требует защиты с обязательными `check` и `pipeline/ready`
от доверенного издателя GitHub Actions и strict up-to-date относительно базы. Для ветки релиза
обязателен `check`; обычный release PR не проходит круг ревью и не требует `pipeline/ready`.
Автоматический Ready доступен при полном включенном процессе; отключенный или неприменимый модуль
не разрешает обход обязательных стадий. Приемка архива не подтверждает готовность установки:
администратор отдельно настраивает защиту веток и доступы. Вывод `forge-setup.py` перечисляет эти
действия; недоступные для проверки настройки, в том числе ответы 403, остаются блокерами установки.

## Архив под решения

```bash
"$KIT/payload/.harness/hooks/python.cmd" "$KIT/ah.py" pack --config <манифест или config.json> --out <каталог>
```

`config.json` - решения без фактов: `{"decisions": {"shape": "backend", "modules.backend":
["dotnet"], ...}}`; из манифеста решения берутся сами. Нерешенный модуль получает значение каталога по умолчанию
или выключение, обязательный без значения по умолчанию - отказ. Архив `agent-harness-<версия>-<первые 8 знаков
sha256 config.json>.tar.gz` несет файлы только включенных путей, установщик, каталог, `kit.json` с
поставленными файлами и путями отсутствующих, `config.json` с каноничными решениями, `AGENT.md`
и инструкции этапов под эти модули, `README.md` и `PARAMETERS.md` полного комплекта: их ссылки на файлы невключенных
модулей в таком архиве не открываются. Одни решения дают одно имя и один архив байт в байт.
`configure` из такого архива начинает с решений `config.json` и спрашивает только факты, а `apply`
отказывает модулю вне них.

## Архив

Архив воспроизводим: одно содержимое дает один и тот же файл байт в байт (без меток времени и
владельцев). Полный комплект несет `AGENT.md` и инструкции этапов под все модули и их
шаблоны в `templates/` для `pack`. Код и скрипты архива идут без комментариев, кроме вендорного кода:
файлы Spec Kit (`payload/.specify/`) и пакетов скиллов - расширений с полем `skills` в каталоге -
идут как у поставщика.

## Конфигурация процессов

Что хранят `pipelines.json`, `methodology.json` и `project/manifest.json` - [что объявляет

## Каталог `modules.json`

`order` - порядок вопросов: каждый модуль ровно один раз. Поля модуля `modules.<модуль>`:

| Поле | Что задает |
| --- | --- |
| `title`, `question` | имя модуля и вопрос его выбора ([стандарт текстов](#стандарт-текстов)) |
| `side`, `stacks` | сторона и стеки, без которых модуль неприменим: `configure` выключает его без вопроса |
| `requires` | пути, которые должны быть включены: модуль или `<модуль>/<расширение>` |
| `wants` | пути, без которых проверка модуля теряет механическую часть: приемка отказывает, пока владелец пути не включен или его `off` не назовет причину проекта и замену |
| `forgeSecrets` | имена секретов модуля по расширению включенного поставщика кода: `{"github": ["AGENT_GITHUB_TOKEN"]}` |
| `secretsUse` | у модуля или расширения с секретами: какое задание берет секреты и с какого момента они нужны; `forge-setup.py` печатает его владельцу у каждого секрета |
| `select` | `min` и `max` числа расширений; `min: 0` дает выбор "включен без расширения", без `select` у модуля расширений нет |
| `slots` | вместо `select`: границы по слотам, у расширения - его `slot`, вопрос - на каждый слот; `question` слота - его текст |
| `default` | расширение или список расширений, когда детекторы ничего не нашли; выбор модуля с `default` - пункт сводного вопроса `defaults` |
| `detect` | следы модуля без расширений: найдены - вопрос предлагает включить модуль; однозначная находка модуля или расширения - пункт сводного вопроса `stack` |
| `required` | модуль не выключается |
| `off` | `reason` и `replacement`: причина выключения и то, что работает вместо модуля; их получают вариант "Выключить" вопроса модуля и записи реестра правил невключенного пути; у выключаемого модуля обязательны. Невключенный путь установщик пишет в запись полем `disabledBy`; пути и команду включения `check-all.py` печатает одной строкой под таблицей гейтов, в тексте замены их нет |
| `settings` | настройки модуля |
| `extensions.<расширение>` | `title` - имя технологии, `about` - необязательное пояснение варианта: `configure` печатает его в описании варианта вместе с находкой и секретами, `slot`, `requires`, `detect` - следы технологии в дереве, `settings`, `secrets` - имена секретов площадки, которые расширению нужны, `adapter` - реализация интерфейса модуля в `.harness/lib`: `<файл>.<класс>`, `server` - сервер MCP, который расширение пишет в конфиги агентов разработки: `url` или `command` с `args`; сервер с командой запускает `mcp-launch.mjs` в окружении сессии, `ensure` - скрипт `.harness/provisioning/scripts/` с аргументами, который идет перед командой, `timeout` - секунды ожидания подключения, `skills` - каталоги `.agents/skills/<имя>` пакета скиллов: `configure` пишет их в `docs.vendoredSkills`, `kit.py check` сверяет их с файлами расширения в `kit.json`, `changeTemplate` и `issueTemplate` - пути установки формы запроса на изменение и формы задачи, на них ссылается `at` файла формы |

Схема настройки:

| Поле | Что задает |
| --- | --- |
| `shape` | форма: `text`, `texts`, `records` с полями `fields.required` и `fields.optional` (`fields.secrets` - поля с именем секрета CI), `choice` и `choices` с объектом `values` `значение => описание`: описание идет в вариант вопроса, `flag`, `object` |
| `kind` | `decision` - решение владельца, `fact` - факт дерева |
| `sources` | откуда значение: `literal`, `env`, `secret`; без поля - только литерал |
| `required`, `default`, `pattern` | обязательность, значение по умолчанию, шаблон строки; решение с пустым `default` (`[]`, `{}`) установка не спрашивает, решение с непустым - пункт сводного вопроса `defaults` |
| `title`, `rule` | имя настройки и как ответить; `configure` печатает `rule` строкой "Как ответить" у вопроса любой настройки, а агент по `rule` факта определяет факт без находки |
| `detect` | детектор кандидатов факта; у решения со значением по умолчанию - один найденный кандидат вместо значения по умолчанию |
| `requires` | пути, без которых настройка не нужна: `configure` ее не спрашивает и значение остается по умолчанию; модуль пути в `order` стоит раньше модуля настройки |
| `in` | `<путь>.<настройка>.<поле>`: значение - одно из полей записей другой настройки-списка; `configure` предлагает их, приемка сверяет; модуль списка в `order` стоит раньше |
| `secrets` | у `choice`: значение - имена секретов площадки, которые нужны при нем: `{"api-key": ["CODEX_API_KEY"]}` |
| `static` | `true` у решения со значением по умолчанию: установка его не спрашивает и пишет значение по умолчанию, вопрос задает `--reopen` модуля |

Ключи `detect` разбирает установщик: `files` и `paths` - маски файлов и путей, `content` - шаблон
содержимого файлов `files`, `migrations` - шаблон имени миграции EF Core или ее класса, `remote` - адрес
`origin`: путь проекта, а с `server` - схема и хост сервера, `packages` - пакеты NuGet, `sdk` - `Sdk=` проектов, `npm` - зависимости `package.json`,
`type` и `typeKind` - типы C# по имени и виду, `projectKinds` и `moduleFeatures` - факты раскладки.
Включенные пути проекта - `core`, `<модуль>`, `<модуль>/<расширение>` и `stack/<расширение>` модулей
сторон `backend` и `frontend`.

### Стандарт текстов

Тексты каталога - вопросы установщика, варианты и записи реестра правил - пишутся русским инженерным
языком по [стандарту текста](payload/docs/platform/standards/text.md): фраза с глаголом, без
канцелярита, дефис `-` вместо тире, прямые кавычки, три точки вместо многоточия, `=>` вместо стрелки,
кеш через "е", имя технологии - как у поставщика.
Механические границы держит `kit.py check`: константы границ - в
[`catalog_checks.py`](tools/kit_support/catalog_checks.py), отказ называет путь записи, границу и текст.

| Поле | Что это | Правило | Механическая граница |
| --- | --- | --- | --- |
| `modules.<м>.title` | имя модуля | именная группа с заглавной: "Поставщик кода", "Раннеры CI"; что модуль делает - в `question` | до 5 слов, без `: ; ( ) ,` и " - ", без точки |
| `modules.<м>.question`, `slots.<слот>.question` | вопрос выбора | один вопрос о проекте в третьем лице, на который отвечает выбор варианта: наличие - "Есть ли в проекте ...?", технология - "Какой ...?", "Где ...?", "Кто ...?", "На чем ...?", практика - "Проверять ли ...?", "Вести ли ...?"; без "harness ставить" и обращения на "вы" | до 12 слов, с заглавной, ровно один `?` в конце |
| `off.reason` | почему модуль выключен | факт о проекте: "в проекте нет бэкенда", "круг ревью в CI не подключен" | фраза со строчной, без точки, до 14 слов |
| `off.replacement` | что закрывает пробел, пока модуль выключен | кто или что делает работу модуля вместо него: "текст проверяет ревью", "гейты запускаются вручную: <команда>"; если предмета модуля в проекте нет - дословно `не требуется, проверять нечего`; без совета включить модуль | фраза со строчной, без точки, до 30 слов; нет слов `включите`, `подключите`, `configure`, `--reopen`, `ah.py`, `<комплект>` |
| `extensions.<р>.title` | имя технологии или варианта | имя, как у поставщика: "Codex", "GitHub Actions", "Spec Kit"; у варианта без технологии - короткое имя: "Модульный монолит" | до 5 слов, без `: ; ( ) ,` и " - ", без точки |
| `extensions.<р>.about` | пояснение варианта, необязательно | что расширение проверяет, ставит или подключает, одной фразой; у пакета скиллов - состав, источник и лицензия; не повторяет имя и не нужно, когда имя все сказало ("PostgreSQL", "gitleaks") | фраза со строчной, без точки, до 18 слов |
| `settings.<н>.title` | имя настройки | отвечает на "что это": "Учетная запись Jira"; формат, пример, ключи и смысл пустого значения - в `rule` | до 8 слов, с заглавной, без `: ; ( )` и " - ", без точки |
| `settings.<н>.rule` | как ответить | обязателен у всех настроек, кроме `choice` и `choices`; порядок: что вписать и откуда взять, пример через "; например", смысл пустого значения через "пусто - ..."; у `records` и `object` называет поля или ключи; у секрета говорит, что вписывается имя секрета CI, а не значение | фраза или две со строчной, без точки в конце, до 45 слов; перед "например" стоит "; " |
| `settings.<н>.values` | значения `choice` и `choices` | объект `значение => описание`; описание - что произойдет при этом значении | описание - фраза со строчной, без точки, до 16 слов |

Фраза начинается с заглавной, только когда первое слово - идентификатор или имя латиницей
(`GITHUB_TOKEN`, `CSharpier`, "Jira"); русское имя собственное в начало фразы не
ставится. Имя со строчной латиницы ("gitleaks") допустимо.

```text
tracker/jira.user
  не так: title: Учетная запись Jira Cloud - почта владельца классического токена API; пусто - персональный токен ...
  так:    title: Учетная запись Jira
          rule:  почта владельца классического токена API Jira Cloud; пусто - вход персональным токеном Jira
                 Data Center в заголовке Bearer

agents.findings
  не так: values: ["same-pr", "separate-pr", "report", "ignore"]
          title:  Попутные находки вне постановки: same-pr - чинить в этом PR, separate-pr - отдельным PR, ...
  так:    title:  Попутные находки вне постановки
          values: {"same-pr": "агент чинит находку в этом же PR", "separate-pr": "агент чинит ее отдельным PR",
                   "report": "агент называет находку в PR и не чинит", "ignore": "агент находку не трогает"}

prose
  не так: off.replacement: текст проверяет ревью; подключите prose с пакетом стиля языка проекта
  так:    off.replacement: текст проверяет ревью
```

Одна сущность в разных модулях называется одним текстом дословно: расширения агентов `claude-code`,
`codex` и `cursor` в `review`, `issue-agent` и `alert-triage`, решение `auth` расширения `codex`,
настройка `onFailure` каналов уведомлений.

## Манифест комплекта `kit.json`

| Ключ | Что задает |
| --- | --- |
| `name`, `version` | имя и версия комплекта; обе пишутся в `lock.json` проекта |
| `repository` | адрес репозитория комплекта: рендер ведет ссылки на справочники места `reference` в `<repository>/blob/v<version>/payload/<путь>`; пишется в `lock.json` проекта: по нему загрузчик и `ah upgrade` скачивают архив выпуска `<repository>/releases/download/v<version>/<name>-<version>.tar.gz` |
| `released` | пути, которые комплект перестал ставить и передал проекту: `apply` снимает их с учета `lock.json`, а файл оставляет на месте |
| `digest` | дайджест сборки: все файлы архива, кроме `kit.json`, и поля манифеста; архив под решения наследует его у полной сборки. Пишется в `lock.json` проекта и отличает сборки одной версии: `verify` и `status` принимают только сборку из `lock.json`, `apply` другой сборки той же версии предупреждает |
| `dependencies` | внешние зависимости: `need` (`required`, `ci`, `optional`), `module` - путь, которому зависимость нужна, минимум, закрепленная или проверенная версия; `pinFile` и `pinPattern` - закрепление в файле, `pinSetting` - ключ проекта, например `agents.cli.codexVersion`; проверка - `probe` (команда версии, `{platform}/` - путь в `.harness` комплекта), `status` (команда, чей код 0 - готовность) или `env` (переменные среды, хватит одной); `local` - только на машине разработчика: `verify` и `doctor --ci` запись пропускают |
| `files` | файл payload: `module` - путь модуля или список путей, из которых хватит одного, `also` - пути, нужные все сразу, `at` - атрибут расширения модуля в каталоге, который задает путь установки файла, роль (`managed`, `json`, `block`, `seed`), `render` для шаблона, `executable` для исполняемого, `extend` - место проекта, куда переносится правка файла: `apply` пишет его в запись файла `lock.json`, а гейт `harness-files` и `ah.py verify` называют его в отказе, `place` - место файла роли `managed` после установки по lock: без поля - `lock`, файл ставит `ah install` из кеша версий; `shell` - файл оболочки в git проекта, его читает инструмент до установки: площадка CI, агент на старте, сборка; `reference` - справочник для людей без подстановок проекта: в проект не ставится, ссылки на него ведут в репозиторий комплекта |

Для `pinSetting` сверка комплекта сравнивает закрепленную версию со значением каталога по умолчанию; `doctor`
установленного проекта читает фактическое значение `agents.cli`, включая переопределение проекта.

Архив под решения добавляет в `kit.json` `absent` - пути файлов
невключенных модулей - и `packed`: дайджест `config.json` и включенные пути. Раздел `modules`
манифеста проекта сверяет с каталогом приемка установки.

## Шаблоны payload

Файл с `render` проходит подстановку при установке:

| Форма | Что делает |
| --- | --- |
| `{{project.name}}`, `{{git.baseBranch}}` и любой ключ манифеста с точкой | значение ключа; отсутствующий ключ - отказ установки с именем файла |
| `{{harness.kitVersion}}`, `{{harness.installDate}}` | версия комплекта, дата установки |
| `{{harness.placed}}` | строки `.gitignore` для файлов места `lock` и каталога модулей `.harness/state/modules.json`, по одной на файл; свертки в каталоги нет, чтобы блок не зависел от индекса проекта |
| `{{harness.extension.<модуль>}}` | выбранное расширение модуля, у которого выбрано одно расширение |
| `{{harness.runner.<вид>}}` | пул раннеров вида задания `check`, `review`, `agent`, `triage` (только GitHub) или `release` списком JSON: метки `runs-on` модуля `runners/github-actions`, с переменной вида в `runners/github-actions.variables` - выражение `fromJSON` переменной репозитория с метками запасным значением, теги `runners/gitlab-runner`; без модуля - `["ubuntu-latest"]` у GitHub и `[]` у GitLab |
| `{{harness.areasTable}}`, `{{harness.profileRows}}`, `{{harness.entryRows}}`, `{{harness.appRows}}` | строки таблиц областей, профилей, профилей с точками входа ролей `apps[].entries` и приложений из `apps[]` |
| `{{#if module:forge/github}}...{{/if}}`, `{{#if stack:node}}`, `{{#if setting:agents.findings=report}}`, `{{#unless ключ}}` | участок по включенному пути модуля, стеку, значению настройки модуля (без записи в манифесте - значение каталога по умолчанию) или ключу манифеста; `{{else}}` внутри участка отделяет текст для невыполненного условия; участки не вкладываются: оставшийся после рендера тег `{{#if}}`, `{{#unless}}`, `{{/if}}`, `{{/unless}}` или `{{else}}` - вложенное условие или опечатка в имени условия - установщик отклоняет с именем файла |

Той же разметкой написаны [AGENT.md](AGENT.md) и инструкции этапов `installer/stages/`: полный комплект
несет их под все модули, архив под решения - под свои ([ниже](#архив-под-решения)); `{{harness.archive}}` в них - имя
архива.

Ссылка документа на файл невключенного пути при установке заменяется ее текстом: битой ссылки в
проекте не остается. Так же снимается ссылка на заготовку `.md`, которую `lock.json` называет, а проект
удалил из дерева (`render.removed_seeds`). Ключ реестра `messages.env`, который упоминают только
файлы невключенных путей, снимается. Так же снимается переменная реестра шаблонов
`.harness/templates/variables.json`, которую используют только шаблоны невключенных путей.
Пути таких файлов `lock.json` перечисляет в `absent`, и гейт конвейера не считает их пропажей.

## Коды установщика

| Код | Значит |
| --- | --- |
| 0 | успех |
| 1 | приемка или `doctor` нашли ошибки; `configure` без `--next` остановился на вопросе или манифест не прошел проверку |
| 2 | отказ до записи: параметры, ответ вне схемы, модуль вне архива, JSON проекта не разбирается, серверы TOML проекта повторяют серверы блока, нет `lock.json`, `verify` не тем архивом |
