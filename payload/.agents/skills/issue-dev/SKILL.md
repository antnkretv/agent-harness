# Конвейер разработки через issue

Issue skill заводит только по просьбе человека. С попутной находкой поступай по политике
`agents.findings` ([`.harness/CONTRIBUTING.md` §10](../../../.harness/CONTRIBUTING.md#10-находки-по-пути)){{#if setting:agents.findings=same-pr}}: она чинится
в текущем PR, каким бы ни был ее объем{{/if}}.
Git-стандарт и имена веток: [`.harness/CONTRIBUTING.md`](../../../.harness/CONTRIBUTING.md).
Композиции: [`.harness/pipelines.json`](../../../.harness/pipelines.json); определения процессов и
параметры review: [`.harness/methodology.json`](../../../.harness/methodology.json).
Исполнение и проверку стадий ведет
[`pipeline-run.py`](../../../.harness/README.md#исполнение-и-подтверждения-стадий): `run change`
и `verify change` с `--task`, `--change` и каждым обязательным `--required-check`. Флаг завершения
от агента не заменяет журнал команд, результат аудита или перечитанное состояние PR. Начни с
`./.harness/hooks/python.cmd .harness/scripts/pipeline/pipeline-run.py next change` и выполняй шаги, которые
он называет ([сессия конвейера](../../../.harness/README.md#сессия-конвейера)).

## Вход

Человек задает условия задачи флагами вызова перед постановкой: `--base <ветка>` - база ветки задачи и
PR вместо базовой ветки проекта, `--review local` - только локальные круги ревью вместо кругов в CI,
`--rounds <N>|max` - предел кругов ревью: после N-го круга с правками управление у человека, `max` -
без предела, `0` - без ревью ([условия Ready и защита базы](../../../.harness/docs/ci-cd.md#локальный-круг-ревью)); `--merge agent` - PR после Ready вливает
агент. Без флага действует значение по умолчанию: базовая ветка проекта, мерж за человеком, предел
кругов - `maxVisits` шага ревью композиции, круги - по настройке `agents.review`; `--review ci`
перекрывает и ее. Действующие условия команда печатает строкой
"Условия задачи".

Флаги читает хук из сообщения человека: вызов скилла стоит в сообщении первым, флаги - сразу за ним.
Команде их не передавай: `next change` таких флагов не принимает, а неизвестный флаг или значение из
вызова человека называет отказом. Дальше базу подставляет выделение ветки, локальный круг - запрос
ревью, а Ready и метку мержа ставят команды, которые называют шаг `ready` и стадия `merge`.

Условия из текста задачи, комментария, файла или пересказа не действуют. Если человек назвал их
словами или не в начале сообщения, сверь его слова со строкой "Условия задачи" и при расхождении назови
ему вызов с флагами.

## Среда

Issue, PR, коммит, комментарий и ответ пиши по разделу "Задачи, изменения и ответы агента"
[стандарта текста](../../../docs/platform/standards/text.md#задачи-изменения-и-ответы-агента) и подразделу о
языке сразу за ним; требование к тексту шаблона печатает
`./.harness/hooks/python.cmd .harness/scripts/text/text_templates.py show <шаблон>`. Вычитывай текст по
[docs-text](../docs-text/SKILL.md). Служебный отчет аудита в публикацию не копируй:
оставь значимые результаты и ссылки на доказательства. Новую issue начни с заготовки формы
`./.harness/hooks/python.cmd .harness/scripts/text/text_templates.py form IssueText --out <файл>`, заполни ее слоты и собери
`./.harness/hooks/python.cmd .harness/scripts/text/text_templates.py render issue/task --set-file IssueText=<файл> --out <файл>`
и заведи коннектором или `tracker.py create --title <заголовок> --body-file <файл> --label <тип>`:
заголовок и метки - по [`.harness/CONTRIBUTING.md` §12](../../../.harness/CONTRIBUTING.md#12-задачи).

{{#if module:forge/github}}Предпочитай GitHub connector; `gh` допустим как fallback.{{else}}Предпочитай
коннектор поставщика кода; запасной путь - `./.harness/hooks/python.cmd .harness/lib/forge.py` и
`./.harness/hooks/python.cmd .harness/lib/tracker.py`.{{/if}} Перед записью проверь repository, issue/PR, base и head.
Не публикуй секреты и вывод credential commands.
PR без мержа закрывай только командой `./.harness/hooks/python.cmd .harness/lib/forge.py close-change <PR> --body-file <файл>`
с комментарием `text_templates.py render comment/close-note` ([`.harness/CONTRIBUTING.md` §3](../../../.harness/CONTRIBUTING.md#3-pull-requests)).

## План процесса

`./.harness/hooks/python.cmd .harness/scripts/pipeline/pipeline-run.py plan change` печатает порядок шагов, исполнителей,
гейты, условия готовности, передачу мержа и параметры ревью из манифестов. Для релиза используй
`plan release`. Выполняй выбранный план; разделы ниже описывают способы работы со стадиями.

### claim

1. Прочитай issue и все комментарии.
2. Убедись, что задача не закрыта, не назначена другому исполнителю и относится к {{#if module:tracker/jira}}проекту Jira из
   `tracker/jira.projects`{{else}}этому repository{{/if}}.
3. Назначь текущего пользователя assignee: `./.harness/hooks/python.cmd .harness/lib/tracker.py assign <ключ>`
   или коннектором трекера. Отдельный комментарий "беру в работу" не нужен.
4. Найди spec/ADR и связанные PR. Не создавай второй PR для уже существующей ветки.
5. Если сессия идет не в выделенной копии, выдели ветку сейчас, когда задача понятна:
   `task-worktree.py start --type <тип> --key <слаг>`: тип - тип Conventional Commits будущего
   заголовка PR, слаг - кебаб-кейс по смыслу задачи. Задача трекера, в том числе названная ссылкой на
   ее карточку, добавляет `--issue <ключ задачи>`; продолжение PR - `--change <номер>` без `--type` и `--key`. Имя ветки
   строит конвенция проекта ([`.harness/CONTRIBUTING.md` §2](../../../.harness/CONTRIBUTING.md#2-ветки)). Дальше работай в
   копии из результата команды; ветку, которую назвала платформа агента, не публикуй.

Без issue пункты 1-3 отпадают: постановку несет само поручение, пункты 4 и 5 остаются.

Постановка координатора следует [шаблону](../../../.harness/docs/delegated-task.md). Первым
действием сверь ее базу с текущей и до начала работы назови пункты, которые сдвиг сделал устаревшими.

### clarify

До правок сверь постановку с кодом, документами, задачей и связанными PR. Вопрос человеку задается,
только когда пункт допускает несколько толкований, выбор меняет результат или объем работы и ответа
нет в коде, документах и задаче; а также когда нужны продуктовое решение или разрешение, которых нет.
Необратимый выбор - по [`.harness/CONTRIBUTING.md` §10](../../../.harness/CONTRIBUTING.md#10-находки-по-пути). Остальное
реши сам и запиши допущением. Вопросы - одним сообщением, после него ход заканчивается. Трек SDD
уточняет сам трек; в сессии без человека вопросов нет. Команды шага -
[сессия конвейера](../../../.harness/README.md#сессия-конвейера).

Во время разработки вопросов не задавай: спорное запиши допущением и назови в итоговом отчете и теле
PR. Находка по ходу работы идет по `CONTRIBUTING` §10{{#if setting:agents.findings=same-pr}} и чинится здесь же{{/if}}.

### sync-base

Ветку и worktree выделяет `task-worktree.py` ([авторская рабочая копия](../../../.harness/README.md#авторская-рабочая-копия));
вторую ветку вручную не создавай.
Обнови сведения о базе и проверь рабочее дерево по
[`.harness/CONTRIBUTING.md` §2](../../../.harness/CONTRIBUTING.md#2-ветки). Хотфикс идет от `{{git.releaseBranch}}` и в `{{git.releaseBranch}}`
(раздел `release`). Не включай чужие изменения. При грязном
дереве используй отдельный worktree или самостоятельный clone. Пока у открытого PR не все проходы
ревью одобрены, базу не подливай: шаг вернется после апрува, подлив вердикты не сбрасывает.

### implement

- {{#if setting:agents.findings=same-pr}}Реализуй scope issue, согласованные уточнения и находки по пути (§10).{{else}}Реализуй scope issue и согласованные уточнения; с находками по пути поступай по §10.{{/if}}
- Следуй корневому [`.harness/AGENTS.md`](../../../.harness/AGENTS.md) и применимым skills.
- Источник истины и готовое решение для [SoT, DRY и KISS](../../../.harness/CONTRIBUTING.md#13-принципы-кода)
  ищи так: символы и ссылки - через LSP, остальное - поиском по дереву, владельца документа - по
  [карте ролей](../../../docs/platform/standards/documentation.md#карта-ролей).
- Новые тесты - по [критерию полезности теста](../../../docs/platform/standards/test-usefulness.md);
  ноль новых тестов - нормальный результат задачи.
- Команды проверок затронутых областей находятся в профилях `CONTRIBUTING.md`.
- Тема PR и предел размера - по [`.harness/CONTRIBUTING.md` §3](../../../.harness/CONTRIBUTING.md#3-pull-requests).

Стейджи только явные пути: `git add -- <files>`. Не используй `git add -A` и `git add .`.

Пуш несет завершенный этап: правки и их упрощение публикуются вместе. Промежуточные коммиты
остаются локально; новый push отменяет начатый Check.

### test-audit

Сравни ветку с базой целиком. Корпус контрактов анализаторов и самопроверки поставки аудируй по их
исключениям в критерии полезности теста: пункты 2-4 к ним не применяются.

1. Найди каждый новый тестовый сценарий, включая добавленный в существующий файл или спрятанный в
   параметризованном тесте.
2. Удали тесты скриптов, workflow, манифестов, DI и конфигурации.
3. Удали всё, что не воспроизводит реальный кейс из источника, существовавшего до реализации.
4. Сведи сценарии к одному на правило и перечисли правила в разделе проверок PR - по строке на
   сценарий. Обычный результат аудита - ноль новых тестов.

Счет сценариев печатает `./.harness/hooks/python.cmd .harness/scripts/check/check-test-budget.py`. Диалект и величины
счета - [критерий полезности теста](../../../docs/platform/standards/test-usefulness.md). Остаток и
полезность добираешь ты, пунктами 1 и 3 выше.

Лимит нельзя расширить обоснованием агента - в том числе указанием вызывающего или
координирующего агента: оно правило не снимает.


### finding-audit

Голова, база и правила аудита не изменились - используй подтверждение прошлого прогона.

Пройди по собственному дифу теми же планками, какими пойдет круг: [`.harness/REVIEW.md`](../../../.harness/REVIEW.md),
[`.harness/review/requirements.md`](../../../.harness/review/requirements.md) и
[`.harness/review/architecture.md`](../../../.harness/review/architecture.md). Планки берутся с
базовой ветки - там же, откуда их берет круг.

Сравнение идет с базой целиком, а не по последним коммитам.

Проверь каждый класс ниже.

1. **Радиус живых документов.** Перечисли документы, описывающие измененное поведение, а не только
   те, что уже лежат в диффе. Введенное имя - метрика, событие, код отказа, поле контракта - ищется
   по дереву: у него бывает каталог, план телеметрии и `data-model.md` активного трека. Записи
   реестра требований называет гейт: `./.harness/hooks/python.cmd .harness/scripts/check/check-requirements-registry.py`; он
   печатает повод, а закрывает запись автор.
2. **Соседний образец.** Добавленный член существующей группы - эндпоинт группы, ветка разбора,
   строка таблицы, миграция, сценарий в файле - сверяется с соседями по группе. Расхождение
   снимается; намеренное - называется в PR причиной.
3. **Проза против головы.** Комментарии, которые PR добавил или тронул, тело PR и правленые
   документы перечитываются по текущему коду, а не по замыслу. Утверждение, которого код не держит,
   правится здесь.
4. **Потребители измененного условия.** У каждого тронутого предиката выборки, окна и горизонта
   назови читателей и проверь, доходит ли до них правка. Условие, отбирающее вход, отсекает и тех,
   ради кого правка сделана.
5. **Критерий приемки построчно.** Каждое требование постановки - своей строкой с адресом
   реализации. Незакрытое называется незакрытым, а не обосновывается.
6. **Поверхность без читателя.** Поле контракта, событие, параметр и признак, заведенные этим PR,
   имеют вызывающего. Недостижимая ветка снимается.
7. **Масштаб путей PR.** Запрос в цикле, выборка без предела, полный проход по растущей таблице и
   обход чаще нужного - по [`architecture.md`](../../../.harness/review/architecture.md).
8. **Структура папок.** Новая папка с одним файлом или папка, где после удаления остался один
   файл, проверяется на лишнее дробление. Объединяй по ответственности; число файлов не заменяет
   смысловую границу и не требует создавать искусственный второй файл.
9. **Удаленное поведение.** По `git diff --merge-base` с базой перечисли каждую снятую строку
   правила, вызов, проверку, условие и файл. Для каждой PR называет замену с адресом или причину
   снятия. Сохранность доказывает проба, а не
   совпадение с собственным снимком.
10. **Охват гейта.** Если дифф трогает вход гейта - правило, конфигурацию, глоссарий, список путей
    или префиксов, - гейт прогоняется по всему корпусу, а не по диффу. PR называет, что проверено и с каким результатом.
11. **Второй источник истины и велосипед.** Каждая сущность диффа сверена поиском по правилу шага
    `implement`.
12. **Паритет адаптеров и потребители.** Правка поведения одного адаптера поставщика кода или
    трекера сверяется с остальными адаптерами того же интерфейса. Правка общего слоя называет путь
    обновления потребителя: установленный проект, внешний сниппет окружения. Переименование и
    удаление идут с переходом для потребителя или с пометкой несовместимости.
13. **Утверждения тела PR.** Каждое утверждение тела о сохранении, замене, ослаблении или полноте
    подтверждено проверкой, которую PR называет: команда, проба или адрес. Утверждение без проверки
    правится или снимается.
14. **Проба гейта.** Для каждой проверки, гейта или стража, которые PR меняет, переносит или
    ослабляет, посей нарушение и запусти фактический вход проверки до правки и после нее. Нарушение,
    которое проверка должна ловить, падает в обоих прогонах: проба одного исправленного случая
    проверку не подтверждает. Разовая проба в репозиторий не коммитится, постоянная идет
    самопроверкой по критерию полезности теста; PR называет проверку, посеянное нарушение и
    результат до правки и после нее.
15. **Заявленная причина.** Причина дефекта из постановки, issue или тела PR воспроизводится до
    исправления: вход, команда, наблюдаемый результат. Невоспроизведенная причина называется в PR
    непроверенной, и исправление на нее не опирается. Воспроизведенная причина объясняет все
    симптомы постановки; необъясненный симптом - признак второй причины, и PR называет его.

Аудит ищет пропуск в уже сделанном, а не улучшение рядом. Результат аудита - дифф: найденный
пропуск закрывается здесь же.

### pre-draft-audit

`./.harness/hooks/python.cmd .harness/scripts/check/check-pipeline.py --emit-prompt pre-draft-audit` выдаёт задание.
Пройди указанные области; с подтверждёнными находками поступи по §10. Шаг не запускает ревью
или preview.

### simplify

Выполни skill [`code-simplifier`](../code-simplifier/SKILL.md) на диффе против базы.

### checkpoint

Зафиксируй правки упрощения вместе с правками этапа. Новые изменения требуют актуального аудита
диффа; полные гейты проекта идут один раз, шагом [`gates`](#gates).

### draft-pr

1. Push branch и открой draft PR в базу задачи: ее называет инструкция шага и поле `base` вывода
   `task-worktree.py start`, без флага входа `--base` это `{{git.baseBranch}}` (хотфикс - в `{{git.releaseBranch}}`). Описание начни с заготовки формы
   `./.harness/hooks/python.cmd .harness/scripts/text/text_templates.py form ChangeBody --out <файл>` и собери командой
   `./.harness/hooks/python.cmd .harness/scripts/text/text_templates.py render change/description --set-file ChangeBody=<файл> --session <id> --out <файл>`:
   разделы заполняешь по [`.harness/CONTRIBUTING.md` §3](../../../.harness/CONTRIBUTING.md#3-pull-requests), разметку формы
   соблюдаешь по [`templates.md`](../../../.harness/docs/templates.md#где-лежат), а затраты разработки команда подставит сама. Без `--session` блока "Статистика сессии" нет,
   и шаг `draft-pr` не засчитывается, пока описание PR не несет запись затрат. С issue добавь
   {{#if module:tracker/jira}}`--issue PROJ-123` (строка `Closes PROJ-123`), а если приемка задачи продолжается после этого PR - `--refs PROJ-123`.
   Задачу закрывает [задание закрытия](../../../.harness/docs/ci-cd.md#закрытие-задач) после мержа в базовую ветку.{{else}}`--issue N` (строка `Closes #N`), а если приемка задачи продолжается после этого PR - `--refs N`.{{/if}}
   Правленое описание собери той же командой с `--change <PR>` из заполненной заготовки: сохрани файл
   заготовки или возьми новую и перенеси в слоты разделы опубликованного описания, а `--issue` и `--refs` оставь, только
   если меняешь связи с задачей: что команда переносит из опубликованного описания, называет
   [`templates.md`](../../../.harness/docs/templates.md#тексты-агента).
   Описание публикуй без правок: новое - при открытии PR, правленое - коннектором поставщика кода или
   командой `./.harness/hooks/python.cmd .harness/lib/forge.py edit-change <PR> --body-file <файл>`.
   Без коннектора PR открывает команда `./.harness/hooks/python.cmd .harness/lib/forge.py open-change --head <ветка> --base <база> --title "<заголовок>" --body-file <файл> --draft`.
   Заголовок - по [`.harness/CONTRIBUTING.md` §3](../../../.harness/CONTRIBUTING.md#3-pull-requests).
2. Номер PR за веткой записывает конвейер: следующий `next change` находит PR ветки, привязывает его к
   рабочей копии и пишет номер в git config ветки, а следующие commits получают PR trailer через
   `commit-msg`. Отдельного шага регистрации нет.

Если PR уже существует, переиспользуй его. Не переписывай первые commits ради
trailer. Заголовок и commits используют Conventional Commits; тело описывает результат и проверки,
не процесс работы агента.

### review

Выполни skill [`review`](../review/SKILL.md).

### gates

Порядок: код, упрощение, ревью, вердикты; после апрува всех проходов - Check в CI. Шаг `gates` стадии
`final-gates` ждет Check в CI на одобренной голове и полный `check-all.py` локально не запускает:
локальный прогон остается по решению разработчика. Аудиты стадии `verification` идут перед черновым PR и
кругами; пока идет работа и круги, хватает хуков и команды проверки той области, которую правишь.
Пока Check идет, шаг ждет его командой `--wait`; Check не идет совсем - шаг `gates-missing` ждет и
после нескольких одинаковых ответов сообщает человеку. Упал Check - шаг называет журнал задания: правка
и коммит. Правка после апрува не снимает апрув прохода и не запускает новый круг, только если ее дифф
от одобренной головы меньше `policies.postApprovalFix` строк и трогает только файлы, которые назвали
упавшие гейты в журнале Check этой головы, или файлы сборки и тестов; слияние базы без ручного
разрешения в дифф не входит, а слияние ветки не из базы требует нового круга. Иначе проход идет в новый круг
([правка после апрува](../../../.harness/docs/ci-cd.md#правка-после-апрува)). Принятые правки
конвейер называет в описании PR (пересобери его с `--change`) и в теле коммита слияния. Зеленый Check -
шаг называет `--run gates`: локально идут только гейты данных PR (`check-all.py --change`): связь с
задачей, размер и сверка коммитов с веткой. Агент в CI до `final-gates` не доходит: у него полный прогон с
номером PR - гейт шага `draft-pr`. Стадию `final-gates` проходят сессия агента и `pipeline-run.py run`
без `--until`.

### ready

Стенд preview, если он есть в проекте, поднимается только по прямому запросу человека: метку или
ручной запуск стенда агент сам не ставит, и готовность PR стенда не ждет.

Условия готовности и передача мержа находятся в `processes.merge.steps` методологии;
получи их выводом `pipeline-run.py plan change`. Перечитай состояние PR, головы, базы и
результатов проверок. Локальный журнал автора не заменяет доверенные результаты конвейера.
Если обязательное подтверждение недоступно, оставь PR в Draft и назови препятствие. При ревью `local` шаг называет команду `--run ready`, когда локальные круги по
поручению человека одобрили все проходы; при `--rounds 0` - в любом режиме ревью, без кругов. Условия команды -
[локальный круг ревью](../../../.harness/docs/ci-cd.md#локальный-круг-ревью). Локальный круг,
которым заменен недоступный круг в CI, оставляет PR в Draft.

### before-merge

Перечитай актуальный план и состояние PR; сверяй разрешение по `processes.merge.steps`.

### merge

Используй объявленную запись `processes.merge.steps` и её `handoff`. Auto-merge без прямой
просьбы не включай. Сообщение коммита, которым вливается PR, собери командой `render commit/message --change <PR>`
([тексты агента](../../../.harness/docs/templates.md#тексты-агента)) и передай при мерже так, как требует [`.harness/CONTRIBUTING.md` §3](../../../.harness/CONTRIBUTING.md#3-pull-requests): номер
запроса в коммите слияния нужен релизу. Принятые правки после апрува команда перечислит в теле сама.

### pr-event

Если работа началась из события PR, правь его head branch. Когда запись туда не разрешена, открывай
stacked PR с base на head исходного PR, а не новый PR в `{{git.baseBranch}}`.

### review-comments

Перед исправлением прочитай весь thread и актуальный diff. Тело вердикта короткое: контекст находки - журнал
прохода и его ответ - лежит в артефактах по строке `Workflow` вердикта. Исправь код, выполни релевантный gate,
ответь фактом и ссылкой на commit. Ответ собери командой
`./.harness/hooks/python.cmd .harness/scripts/text/text_templates.py render comment/thread-reply --set-file ThreadReply=<файл> --commit <SHA> --out <ответ>`
и опубликуй готовый файл без правок: метку автора команда уже поставила. Thread закрывает тот, кто внёс исправление. Не закрывай отклонённое
замечание без ответа и не отвечай обещанием вместо результата. Состав ответа, в том числе при несогласии, - строка
"Ответ на замечание PR" раздела "Задачи, изменения и ответы агента" в `docs/platform/standards/text.md`.

### issue-event

Новый комментарий может уточнять scope или отменять прежнее решение. Сначала сопоставь его с текущим
head и открытым PR; не начинай параллельную реализацию той же задачи.

### after-merge

Проверь, что PR действительно merged. Для завершающего PR проверь закрытие issue через `Closes`
([кто закрывает](../../../.harness/docs/ci-cd.md#закрытие-задач)); PR в базу входа `--base`
задачу не закрывает: она остается открытой до слияния интеграционной ветки, и ее не закрывай вручную;
для промежуточного PR с `Refs` issue остается открытой: оставь в ней комментарий со ссылкой на PR,
коммитом слияния и пунктами приемки, которые PR оставил незакрытыми; после выката их находят по
[отчету релиза](../../../.harness/docs/ci-cd.md#релиз). Комментарий собери командой
`./.harness/hooks/python.cmd .harness/scripts/text/text_templates.py render comment/merge-note --set-file MergeNote=<файл> --change <PR> --commit <SHA слияния> --out <файл>`:
ссылку на PR и коммит подставит она. Удали remote branch только если это принято
repository и ветка больше не нужна: удаление основной remote-ветки остается политикой поставщика
кода. Сразу после наблюдаемого merge выполни `task-worktree.py cleanup --change <номер>` из
основного клона: [что она убирает и когда еще вызывается](../../../.harness/README.md#авторская-рабочая-копия).
В удаленной сессии с одноразовой машиной шаг не нужен: копия исчезнет вместе с машиной, а привязку
резерва SDD на origin снимет уборка при старте следующей сессии с доступом к поставщику кода.

### release

Шаги релиза, хотфикса и обратного слияния - [`.harness/CONTRIBUTING.md` §11](../../../.harness/CONTRIBUTING.md#11-релиз-и-хотфикс),
состав - композиция `release` в [`.harness/pipelines.json`](../../../.harness/pipelines.json), исполнители -
ее процессы в [`.harness/methodology.json`](../../../.harness/methodology.json),
устройство - [`ci-cd.md`](../../../.harness/docs/ci-cd.md#релиз). Здесь только то, что касается агента.

{{#if module:release/tag-flow}}Релиз по просьбе человека ведет skill [`release`](../release/SKILL.md). {{/if}}Для задачи на релиз внутри
конвейера выбери план `release`; для хотфикса используй правила ветки и целевого PR из `.harness/CONTRIBUTING.md` §11. Release PR и PR обратного слияния открывает конвейер. Без доступа к его
запуску срежь релиз командой `release.py cut --push`: она создает ту же ветку и черновой PR твоими
учетными данными поставщика кода.
Release PR в Ready переводит `pipeline-run.py run release` с `--task`, `--change`, `--until ready`
и каждым обязательным `--required-check`.

## Чего конвейер не делает

- не заводит issue на находку: с ней поступают по §10;
- не расширяет scope ради улучшения, которое ничего не чинит;
- не объявляет checks зелёными без наблюдаемого результата;
- не переводит PR в Ready и не мержит при незакрытом условии.
