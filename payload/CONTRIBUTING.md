# Contributing

<!-- harness:begin core -->
Правила действуют во всем репозитории. Изменчивые детали остаются в исполняемых конфигурациях,
а этот файл задает порядок работы и критерии готовности. Устройство платформы описано в
[`docs/README.md`](docs/README.md), SDD - в [delivery/sdd](docs/platform/delivery/sdd.md).

## 1. Сообщения коммитов

Используйте Conventional Commits:

```text
<type>(<scope>)?<!>?: <краткое описание>
```

- `type`: `feat`, `fix`, `docs`, `refactor`, `arch`, `perf`, `test`, `build`, `ci`, `chore`,
  `style` или `revert`.
- `scope`: область, модуль или ADR. Он нужен, если без него заголовок неоднозначен.
- `!` или футер `BREAKING CHANGE:` отмечает несовместимое изменение.
- Описание пишется по-русски, по существу; заголовок целиком не длиннее 72 символов.
- Содержание и объем тела - по [стандарту текста](docs/platform/standards/text.md).
- Агент собирает сообщение командой
  `./.harness/hooks/python.cmd .harness/scripts/text/text_templates.py render commit/message --set CommitSubject=<заголовок> --set-file CommitBody=<файл> --out <файл>`
  и коммитит `git commit -F <файл>`; без тела - `--set CommitBody=`.

```text
fix(pricing): исключить закрытые тарифы из расчета
arch(storage): отделить контракт хранилища от EF Core
```

Формат заголовка, объем и текст сообщения проверяет
[`commit-format.sh`](.harness/scripts/check/commit-format.sh). Гейт `commit-format` в
[`check-all.py`](.harness/scripts/check/check-all.py) и Check прогоняет через него каждый коммит ветки,
кроме слияний, поэтому коммит мимо хука, из веба площадки или с `--no-verify` формат не обходит.
Коммиты старше установки harness - предки коммита, который добавил `.harness/state/lock.json`, -
гейт не проверяет: их историю не переписать, а первый release PR после установки их несет. Остальные
коммиты, в том числе коммиты, которыми площадка вливает PR в базовую ветку, проверяются в release PR.
Предел длины заголовка Check только предупреждает: squash площадки дописывает к заголовку номер
запроса, а такой коммит уже не переписать.
{{#if module:githooks/commit-msg}}
Хук `commit-msg` проверяет то же до коммита и добавляет трейлеры, в том числе коммиту слияния (`Merge ...`):
`Issue` с включенным трекером, `PR` с включенным поставщиком кода, а коммиту агента - `Agent` для замера автономии
([ci-cd](docs/platform/delivery/ci-cd.md#замер-автономии)). Хуки включает установщик harness и хук начала
сессии агента; вручную - `git config core.hooksPath .githooks`. Номер issue выводится из имени ветки
или берется из рабочей копии задачи (`task-worktree.py start --issue`). Номер PR за веткой записывает
конвейер, когда узнает PR: `task-worktree.py`, шаги `pipeline-run.py` и `forge.py open-change`; номер
PR, открытого вне конвейера, записывает `git config branch.<ветка>.<префикс>-pr <номер>` с префиксом
`project.gitConfigPrefix`. Первые
коммиты могут остаться без трейлера PR: ради него история не переписывается.
{{/if}}
Тело коммита, которым PR вливается, собирает `render commit/message --change <PR>` (§3).

## 2. Ветки

- База PR - `{{git.baseBranch}}`; напрямую в `{{git.baseBranch}}` и `{{git.releaseBranch}}` не коммитят. В `{{git.releaseBranch}}` идут только
  `release/vX.Y.Z` от {{git.baseBranch}} и хотфикс от {{git.releaseBranch}}: push в `{{git.releaseBranch}}` запускает
  релиз (§11). Серию связанных PR человек ведет в своей интеграционной ветке: создает ее сам,
  задает базой задач флагом `--base` при входе в конвейер и сам вливает в `{{git.baseBranch}}`. Задачу
  с закрывающей ссылкой закрывает это слияние, а не мерж PR в интеграционную ветку.
- Имя ветки задает конвенция проекта - поле `git.branchConvention` манифеста, сейчас
  `{{git.branchConvention}}`; ее выбирает владелец при настройке harness. Одна конвенция действует и для
  агента, и для человека:

  | Конвенция | С задачей | Без задачи | Префикс |
  | --- | --- | --- | --- |
  | `conventional` | `{тип}/{задача}-{слаг}` | `{тип}/{слаг}` | тип Conventional Commits заголовка PR из §1 |
  | `gitflow` | `{поток}/{задача}-{слаг}` | `{поток}/{слаг}` | `feat` - `feature`, `fix` - `bugfix`, исправление в `{{git.releaseBranch}}` - `hotfix`, остальные типы - `chore` |

  `{задача}` - ключ задачи трекера как есть: {{#if module:tracker/jira}}`PROJ-42`{{else}}номер `123`{{/if}}.
  `{слаг}` - кебаб-кейс по смыслу задачи, до 64 символов: строчная латиница, цифры, одиночные дефисы.
  Слаг ветки без задачи не начинается с ключа задачи трекера (у номеров - с `<число>-`): такое имя
  читалось бы как ветка задачи, и `task-worktree.py` его отклоняет.
  Примеры `conventional`: {{#if module:tracker/jira}}`feat/PROJ-42-form-field-drag`{{else}}`feat/42-form-field-drag`{{/if}}, `chore/harness-1-1-0`;
  `gitflow`: {{#if module:tracker/jira}}`feature/PROJ-42-form-field-drag`{{else}}`feature/42-form-field-drag`{{/if}}, `hotfix/123-payment-timeout`.
- Ветки `release/vX.Y.Z` и `back-merge/...` задает процесс релиза (§11), конвенция их не меняет.
- Ветку агента выделяет до запуска и убирает после мержа только `task-worktree.py`:
  [авторская рабочая копия](.harness/README.md#авторская-рабочая-копия). Тип агент берет из типа
  будущего заголовка PR, задачу - из постановки, в том числе из ссылки на карточку задачи трекера. В
  сессии, которую открыл человек, ветку выделяет сам агент на шаге claim, когда задача понятна;
  событие задачи в CI выделяет ветку до сессии: тип - по метке типа задачи
  (поле `commit` метки в `policies.issues.types` методологии), без такой метки - `fix`, слаг - по заголовку задачи. Даты и запасные суффиксы
  не добавляются.
- Агент коммитит в ветку конвенции только из выделенной копии; чужую ветку открытого PR он
  продолжает копией `task-worktree.py start --change <номер>`. Вне конвенции агент коммитит в текущую
  ветку, если она не общая: базовая, релизная, `release/` или `back-merge/`.
- Промежуточный PR, после которого приемка задачи продолжается, идет из ветки задачи и несет {{#if module:tracker/jira}}`Refs PROJ-N`{{else}}`Refs #N`{{/if}}: стадия `claim` подтверждает ветку ключом задачи в имени. Закрывающая связь остается завершающему PR: мерж промежуточного не
  закрывает задачу. Если PR уже открыт из ветки задачи, имя ветки сохраняется, а связь становится
  промежуточной.
- Трек SDD своей ветки не заводит: его ведут в копии, которую выделил `task-worktree.py start`
  ([нумерация SDD](docs/platform/delivery/sdd.md#правило-нумерации)).
- Работу с базой задает стадия `sync-base` выбранного плана.

Связь ветки с задачей, привязку к сессии, уборку, хуки и гейты строит та же конвенция
([`tracker.py`](.harness/lib/tracker.py)). Полный поток задачи описан в
[`issue-dev`](.agents/skills/issue-dev/SKILL.md).

## 3. Pull Requests

- PR несет одну тему: новая несвязанная работа идет отдельным PR.
  {{#if setting:agents.findings=same-pr}}Попутная находка остается здесь, каким бы ни был ее объем (§4 и §10).{{else}}С попутной находкой поступают по §10.{{/if}}
- Предел размера PR задает `policies.size` методологии: число файлов и строк диффа без путей
  `docs.generatedSegments` и `docs.generatedPrefixes`, вендорного `.specify/` и skills `docs.vendoredSkills`,
  шаблонов `policies.size.exclude`, файлов с ролями `managed` и `json` в `.harness/state/lock.json` и
  содержимого блоков harness в файлах с ролью `block`: их пишет установщик из комплекта, а строки
  блока project считаются. PR сверх предела делится в стек: следующий PR открывается с
  base на head предыдущего и несет свою часть темы. Превышение без стека допустимо только с причиной,
  записанной в теле PR строкой с меткой `policies.size.reason` (агент пишет ее в разделы формы и
  пересобирает описание с `--change`): гейт читает текущее тело с площадки по номеру запроса. Объем
  находок, которые политика
  `agents.findings` оставляет в этом PR, - такая причина: предел не выводит находку из PR вопреки
  политике. Предел проверяет гейт `pr-size` локальным прогоном гейтов конвейера на стадии `draft-pr`: Check в CI
  данных запроса не читает. Release PR и обратное
  слияние несут уже проверенные PR и не считаются.
- PR открывается черновиком. Заголовок - одна строка по правилу заголовка коммита из §1: он станет
  заголовком коммита слияния, и проверка текста агента отклоняет другой. Разделы тела задает форма
  описания площадки ([где лежит](docs/platform/agents/templates.md#где-лежат)), текст пишется по
  [стандарту текста](docs/platform/standards/text.md#задачи-изменения-и-ответы-агента). Агент
  берет заготовку формы командой `text_templates.py form ChangeBody`, заполняет ее слоты и собирает
  описание командой
  `text_templates.py render change/description`: она сверяет заполнение с формой, а строки связи с
  задачей (`--issue`, `--refs`), ссылку на сессию и затраты разработки (`--session`) подставляет сама.
  Что пишется в разделах формы:
  - "Проблема" - коротко и прикладным языком: что не работает, при каком условии и почему; текст
    понятен разработчику без истории сессии агента.
  - "Что сделано" - факты сделанного: по пункту на каждый пункт "Что сделать" задачи, без задачи - на
    пункт поручения, в том же порядке и о том же предмете; со ссылками на код, спеку, ADR и документы.
  - "Что не сделано и почему" - пункты "Что сделать", которым нет факта в "Что сделано", и отступления
    от них с причиной; без таких пунктов раздел удаляется, а не заполняется отпиской.
  - "Проверки" - что проверено и чем, несколько строк; ограничения - только те, что меняют решение
    о мерже. Чтение кода, локальный запуск, CI и наблюдение в рабочей среде различаются.
  - "Связанные артефакты (SDD)" - спека и FR, ADR, если меняются принятые решения или границы
    (операционная величина ADR не заводит), и план трека; строка без артефакта удаляется, а без артефактов - весь раздел.
  - "Критерии приемки" - строка на пункт постановки, адрес - файл с символом либо строка документа;
    незакрытый пункт называется незакрытым, а не обосновывается.
  - "Находки" - {{#if setting:agents.findings=ignore}}строка на дефект, внесенный этим PR и починенный в нем; находки вне
    постановки здесь не называются{{else}}находки по пути по §10{{/if}}; без них раздел удаляется.
  - "Чеклист" - по [разметке формы](docs/platform/agents/templates.md#где-лежат): набор пунктов задают
    отмеченные типы изменения, правило пункта - источник, который пункт называет. `[x]` ставится,
    только когда изменение выполнило правило; пункт набора, который изменение выполнить не может, не
    отмечается и называет причину.
- Тело коммита, которым вливается PR, не пустое: оно повторяет итог PR - что изменено, зачем, что снято и чем
  заменено. Агент собирает его той же командой `render commit/message` (§1) с `--change <PR>`
  ([тексты агента](docs/platform/agents/templates.md#тексты-агента)). {{#if module:forge/gitlab}}Сообщение при мерже GitLab
  заменяет шаблон проекта целиком, поэтому агент передает вывод целиком, а заголовок заканчивает номером
  запроса `(!N)`.{{else}}При мерже агент передает только тело - строки вывода после заголовка: заголовок
  коммита слияния с номером запроса `(#N)` ставит площадка.{{/if}} По этому номеру релиз находит влитые PR.
- PR без мержа закрывается только командой `forge.py close-change <PR> --body-file <файл>`: она публикует
  комментарий `text_templates.py render comment/close-note` и только после него закрывает запрос.
  Закрытие коннектором, CLI площадки или вызовом API хук агента отклоняет.
- Стадии публикации и готовности выполняйте по выводу `pipeline-run.py plan change`; инструкции
  находятся в полях `doc` выбранного плана.
- Изменение принятой архитектурной границы оформляется правкой действующего ADR.
- Исполнитель и способ передачи мержа находятся в `processes.merge.steps`; параметры
  выбранной композиции печатает `pipeline-run.py plan <имя>`.

Критерии code review задает [`REVIEW.md`](REVIEW.md), устройство CI и кругов ревью -
[`docs/platform/delivery/ci-cd.md`](docs/platform/delivery/ci-cd.md). Исполняемый состав проверок находится в
workflow, `.harness/methodology.json`, композициях `.harness/pipelines.json` и конфигурации
затронутой области.

## 4. Коммиты ИИ-агентов

Агент соблюдает те же правила веток, коммитов и PR. Стейджатся только явно названные файлы;
`git add -A` не используется. Чужие изменения не включаются и не откатываются.

{{#if setting:agents.findings=same-pr}}Попутную находку агент исправляет в текущем PR по §10 и разрешения на это не спрашивает. Описание
находки в теле PR, в комментарии или в ответе агента правку не заменяет и находку не закрывает.{{else}}С попутной находкой агент поступает по §10 и разрешения на это не спрашивает.{{/if}}
Push, создание PR и другие внешние изменения выполняются только в пределах поручения.

Пуш агента - завершенный этап, а не сохранение: промежуточные коммиты остаются локальными.

Порядок один и с issue, и без нее - его способы выполнения описывает
[`issue-dev`](.agents/skills/issue-dev/SKILL.md).

## 5. Локальные hooks

Git-хуки - модуль `githooks` harness, каждый хук - его расширение; без модуля те же гейты дерева
идут в Check и вручную командой из §6.

{{#if module:githooks/commit-msg}}- `commit-msg` проверяет формат, объем, текст и трейлеры (§1), а у сессии агента в ветке конвейера
  (ветка конвенции, §2) еще выделенную копию и связь `Task-Branch` - [авторская рабочая копия](.harness/README.md#авторская-рабочая-копия).
{{/if}}{{#if module:githooks/pre-push}}- `reference-transaction` запрещает автору обновлять посторонние локальные ветки; `post-merge`
  ставит версию комплекта из lock и очищает завершенные задачи после обновления базы, `post-checkout`
  ставит версию комплекта из lock после переключения ветки. Все три поставляются с расширением `pre-push`.
  Локальные хуки не заменяют серверные права на создание refs.
- `pre-push` гейтов не запускает ([состав](.harness/README.md#слой-платформы)): их запускают CI и
  команды из §6.
{{/if}}{{#if module:githooks}}- `--no-verify` допустим только по явной причине; CI остается обязательным.

Реализация находится в [`.githooks/`](.githooks), разбор проверок - в
[`docs/platform/delivery/ci-cd.md`](docs/platform/delivery/ci-cd.md).

## 7. Человеческий текст и машинный

- Не менять тексты инструкций, specs, ADR и документации без влияния на логику работы.
- Текстовый diff делать минимальным: только необходимый фрагмент, без повторов и лишних пояснений.
- Не переименовывать термины, заголовки и имена без функциональной необходимости.

Требования к смыслу, адресату, ошибкам, оформлению и объему задает
[стандарт текста](docs/platform/standards/text.md). Он применяется к коду, скриптам и публикациям.
Порядок вычитки - скилл [docs-text](.agents/skills/docs-text/SKILL.md).
Машинные файлы задаются `docs.machineTextPrefixes` в [манифесте](.harness/project/manifest.json).

## 9. Верификация: чем она меряется

Верификация воспроизводит исходный наблюдаемый симптом, а не подтверждает наличие правки. Если
симптом нельзя проверить, это явно указывается в PR с причиной.

Асинхронная граница проверяется на стороне потребителя: публикация события, запись в outbox или
ответ `2xx` доставку не доказывают. Доказательством служит результат, журнал или состояние дальней
стороны.

## 10. Находки по пути

Legacy-код не сохраняется "на потом": изменение сразу реализует целевую архитектуру, переводит
всех потребителей и удаляет прежние ветви, модели и адаптеры. Переименование маркера не заменяет
переход. Правило целевой архитектуры запрещает `legacy` в именах, строках, комментариях и путях C#, а в
TypeScript - в идентификаторах и строках; тесты входят в область проверки. Неизменяемые идентификаторы уже примененных миграций сохраняются как история
БД, а данные переводятся новым шагом. Новые миграции такого исключения не получают.


Дефект, который внес сам этот PR, и принятый совет его ревью - работа этого PR и чинятся в нем
всегда, каким бы ни был объем переделки. С попутной
находкой - ошибкой, недоделкой или огрехом вне постановки, своим и чужим, - поступают по политике
`agents.findings` манифеста:

{{#if setting:agents.findings=same-pr}}Находка, по теме задачи и не по теме, чинится в текущем PR, если человек не попросил ее отложить.
Объем выходом не считается: сотня файлов, которых PR не касался ни одной строкой, - это тот же PR.
Доводы "было до меня" и "гейт этого не ловит" выходом тоже не служат.
В теле PR назовите находку и что сломалось рядом.
{{/if}}{{#if setting:agents.findings=separate-pr}}Находка чинится отдельным PR от `{{git.baseBranch}}`, а текущий PR держится постановки. Отдельный
PR открывается в той же работе, его тело называет исходные задачу и PR; тело текущего PR называет
находку и ссылку на отдельный PR.
{{/if}}{{#if setting:agents.findings=report}}Находка не чинится: тело PR называет ее в разделе "Находки" - что замечено, где и что ломается
рядом. Решение о починке принимает человек.
{{/if}}{{#if setting:agents.findings=ignore}}Находка не чинится и в PR не называется: работа держится постановки.
{{/if}}
Нехватка решения, обнаруженная по ходу работы, ее не останавливает. Если выбор между вариантами не
выводится ни из кода, ни из документации, ни из соседнего образца, а цена ошибки не отыгрывается,
сделайте выводимую часть, а вопрос с вариантами задайте в теле PR. То, что читается из кода, документации или
соседнего образца, нехваткой решения не считается.

Отдельная задача появляется, только когда о ней просит человек. Ее тело ссылается на исходные
задачу и PR, а ответ в review thread называет заведенную задачу; после этого thread можно закрыть.{{#if setting:agents.findings=same-pr}}
Такую отсрочку текст объявляет строкой `Отложено по просьбе: <где просил>`: без нее хук текстов
поставщика кода слова отсрочки не пропустит.{{/if}}

Отклоненный совет задачи не порождает: разногласие остается открытым до решения человека.

## 11. Релиз и хотфикс

{{#if module:release/tag-flow}}
Релиз запускает push в `{{git.releaseBranch}}`, а код попадает туда только через PR. Срез, обратное
слияние, версия, major и откат - [ci-cd.md](docs/platform/delivery/ci-cd.md#релиз); состав и условия
Ready печатает `./.harness/hooks/python.cmd .harness/scripts/pipeline/pipeline-run.py plan release`.

Баг, найденный в release PR, чинится задачей в {{git.baseBranch}} с обычным ревью. После мержа фикса release PR
закрывается, ветка удаляется, и релиз срезается заново.

Хотфикс - ветка `fix` по конвенции (§2) от `origin/{{git.releaseBranch}}` и PR в `{{git.releaseBranch}}` с обычным ревью. Его мерж
запускает релиз хотфикса. Задача хотфикса закрывается после обратного слияния в
`{{git.baseBranch}}` ([закрытие задач](docs/platform/delivery/ci-cd.md#закрытие-задач)): PR в `{{git.releaseBranch}}` ее не закрывает.

[Сессия релиза](docs/platform/delivery/ci-cd.md#сессия-релиза) (`/release`) ведет обе правки сама, без
задачи, из ветки без задачи по конвенции (§2): фикс в {{git.baseBranch}} проходит обычный круг ревью, а хотфикс упавшего релиза в
`{{git.releaseBranch}}` идет без кругов ревью. Гейты PR, в том числе размер, держат обе.
{{else}}
Публикацию выполняет конвейер проекта. Точки входа и ручные подтверждения определяются
конфигурацией CI и проектной инструкцией релиза. Модуль `release/tag-flow` harness не подключен.
{{/if}}

## 12. Задачи

- Заголовок - одна фраза о проблеме или результате прикладным языком, без префиксов: тип и
  приоритет задачи несут метки.
- Метка типа - ровно одна из `policies.issues.types` методологии, метка приоритета - из
  `policies.issues.priorities`, когда приоритет известен. Там же значение каждой метки; в GitHub Issues
  метки создает `forge-setup.py`.
- Разделы тела задает форма задачи ([где лежит](docs/platform/agents/templates.md#где-лежат)), текст
  пишется по [стандарту текста](docs/platform/standards/text.md#задачи-изменения-и-ответы-агента).
  Агент берет заготовку командой `text_templates.py form IssueText`, заполняет ее слоты и собирает
  тело командой
  `text_templates.py render issue/task`. Что пишется в разделах:
  - "Проблема" - коротко и прикладным языком: при каком условии что происходит, что ожидается и к
    чему это ведет; данные наблюдения или способ воспроизведения. Известная причина отделена от
    гипотезы, недостающие данные названы.
  - "Что сделать" - инструкция исполнителю: что и как изменить, со всем контекстом - ссылками на
    код, спеку, ADR и документы.
  - "Готово, когда" - проверяемые критерии завершения списком.
{{#if module:alert-triage}}
- Задачу алерта заводит конвейер разбора алертов: заголовок - `<имя алерта>: <summary>`, метка -
  метка алерта, тело - шаблон `issue/alert`.
{{/if}}

## 13. Принципы кода

Принципы действуют в любой задаче, не только в треке SDD. Вес нарушения задает
[`REVIEW.md`](REVIEW.md#вес).

### SoT

У каждой сущности один источник истины (SoT): у файла, модуля, класса, типа, функции, метода,
значения, списка, ключа конфигурации, сообщения, спеки, документа, раздела, правила и формулировки.
До создания или правки сущности автор находит ее источник; если его нет, источником становится
новая сущность. Граница областей проходит по пути в дереве
([area-map](docs/platform/architecture/area-map.md)), факт документа живет у владельца по
[карте ролей](docs/platform/standards/documentation.md#карта-ролей), ADR правится на месте по
[жизненному циклу](docs/platform/adr/README.md#жизненный-цикл).

### DRY

Найденный источник используется вызовом, ссылкой или расширением, а не копией. Второй экземпляр -
дефект: копии расходятся молча. Копия допустима, только когда ее сверяет с источником гейт.
Документ не пересказывает код, конфигурацию и вывод команд, а ссылается на источник: пересказ -
такая же копия.

### KISS

Решение - простейший алгоритм, который закрывает задачу: без велосипеда - своей реализации того,
что уже есть в коде, SDK или платформе, - и без костыля - обхода причины вместо ее устранения.

### Безопасность и приватность

Персональные данные обрабатываются по минимизации и не попадают в открытые логи, консоль клиента
или сторонний трекинг. Секреты живут в конфиге, секрет-сторе и переменных окружения, не в коде,
спеке или git; гейт `secret-scan` проверяет дерево и историю ветки. Права проверяются до обработки,
клиент не источник прав. Данные без необходимых прав и секреты не передаются модели. Правка, которая
трогает права, данные пользователей или внешние входы, несет проверяемые сценарии допуска и отказа;
архитектурные границы и контракты обработки фиксирует ADR.
