# SDD workflow - Spec-Driven Development

> **Тип (Diataxis):** Справочник - **Аудитория:** ИИ-агенты + разработчики всех областей

Документ описывает, **как вести разработку через спецификацию** с использованием
[GitHub Spec Kit](https://github.com/github/spec-kit) поверх существующей культуры репозитория
(ADR + исполняемый арх-контроль + продуктовые спеки). Конвейер один на репозиторий: областных
редакций этого документа нет, различия областей названы здесь и в [CONTRIBUTING.md §6](../../../CONTRIBUTING.md#6-профили-областей).
Для людей и ИИ-агентов (Claude Code, Cursor, Codex).

Companion-доки: [README.md](../../README.md), [gates.md](../architecture/gates.md),
[adr/](../adr/README.md). Принципы конвейера -
[`.specify/memory/constitution.md`](../../../.specify/memory/constitution.md).

Спека - источник истины; ADR - источник архитектурных решений; verify-гейт области - **исполняемая
проверка** против спеки.

## Конвейер: чего проект требует сверх поставки

Команды, их аргументы и артефакты описывает сама поставка, и здесь не пересказываются: скиллы
[`.agents/skills/speckit-*`](../../../.agents/skills) (надстройка платформы -
[`speckit-market`](../../../.agents/skills/speckit-market/SKILL.md)), шаблоны
[`.specify/templates/`](../../../.specify/templates) (адаптированы под методологию: русский, EARS,
module-first layout), порядок шагов - `.specify/workflows/speckit/workflow.yml`.

Минимальный поток - `specify => plan => tasks => implement`. Но для всего, что сложнее тривиального:

- **`/speckit-market` - сверка заказа с рынком.** Идет хуком перед `clarify`
  ([`.specify/extensions.yml`](../../../.specify/extensions.yml)) и пишет `market.md`: чем требования
  расходятся с практикой продуктов рынка, что из расхождений оспорено и какие вопросы уходят
  в `clarify`. Решение по расхождению принимает человек - спеку шаг не правит.{{#unless setting:agents.pushback=none}}
- **Нелогичный ответ на `clarify` оспаривается.** Вопрос без цены ошибки и альтернативы
  возвращается тем же вопросом. Возражение - один раз внутри того же вопроса, а не новый вопрос;
  повтор ответа закрывает спор и уходит в спеку с основанием. Что оспаривается при значениях
  `agents.pushback`, описывает `speckit-market`.{{/unless}}
- **`/speckit-clarify` - не пропускать.** Снимает слепые зоны до дизайна. Отвечать конкретно, не
  "потом решим".
- **`/speckit-checklist Security` - минимум один** для фичи, которая трогает права, данные пользователей или внешние входы.
  Для UI-частей фичи - чек-лист i18n и UX в области фронтенда.
- **`/speckit-analyze` - обязательный шаг перед `implement`.** Кросс-сверка spec<=>plan<=>tasks ловит
  конфликты и пропуски до кода. После правок - прогнать повторно.
- **`/speckit-implement` - по фазам, не все разом.** Одна фаза => verify-гейт области => коммит (один
  задание ≈ один коммит, Conventional Commits, CONTRIBUTING.md) => при необходимости новая сессия/`/clear`.
- **`/speckit-converge` - после `implement`, если фича делалась в несколько сессий или частично вручную.**
  Добор остатка обязателен.
- **Preview - не `after_implement` hook и не условие готовности.** Стенд preview, если он есть,
  поднимается только по прямому запросу человека; контракт шага живет в
  [`issue-dev`](../../../.agents/skills/issue-dev/SKILL.md#ready), а не дублируется здесь.

**Следующий шаг конвейера называет агент.** Завершив любую `speckit`-команду, агент заканчивает ответ
рекомендацией следующей: `specify` => `/speckit-market` => `/speckit-clarify` => `plan` => `/speckit-tasks` (опционально `/speckit-analyze` после) =>
`/speckit-implement` => verify. Остался несделанный объем - `/speckit-converge`.

## Два трека без дублирования

SDD-конвейер один, но артефакты "приземляются" по-разному в зависимости от трека.

| Слой SDD | Продуктовый трек (фичи) | Платформенный трек (архитектура/рефакторинг) |
| -------------------------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| **constitution** | `.specify/memory/constitution.md` (общая, ссылается на ADR/NetArchTest) | то же |
| **specify** `spec.md` (EARS, FR) | каноничная спека в `specs/<трек>/spec.md`; `docs/features/<feature>/` **ссылается** на нее | requirements фиксируются и переносятся в **Context/Decision** ADR - действующего или нового |
| **market** `market.md` | реестр расхождений с рынком и очередь вопросов; находка, полезная всему продукту, уезжает в документ продукта отдельной задачей | то же; расхождение с принятым решением - вход для правки ADR |
| **plan** `plan.md` | технический дизайн фичи (затронутые модули/хосты/события) | технический дизайн рефакторинга в `specs/<трек>/plan.md` + **правка действующего ADR или новый ADR** (`docs/platform/adr/`), если решение проходит порог |
| **tasks** `tasks.md` | чек-лист реализации (vertical slices + DoD) | последовательность PR (PR-A/B/C) |
| **implement** | код по плану | код по плану |
| **verify** | тесты фичи по критерию полезности + архитектурный гейт стека | архитектурный гейт стека + тесты затронутого модуля |

Гейт и смоук каждой области - [CONTRIBUTING.md §6](../../../CONTRIBUTING.md#6-профили-областей); арх-контроль исполняем везде,
но инструментом стека ([gates.md](../architecture/gates.md)): точки входа `analyze` и `architecture` у .NET,
ESLint у TypeScript, гейт проекта у стека без адаптера. Спека интерфейса описывает поведение экрана, а не
верстку; приемка UI - смоук по `quickstart.md`.

### Свидетельства трека

Протоколы и итоги приемки трека лежат в `specs/<трек>/evidence/`: ссылки на разрешенное
хранилище, хеши, времена и агрегаты. Все дерево `specs/` - текст `.md`, `.txt` и `.json`; исходные
изображения, персональные данные и секреты в него не попадают. Формат, имена секретов и, если проект включил `size` в `docs.checks`, размер
файлов проверяет [`check-docs.py --area docs`](../../../.harness/scripts/check/check-docs.py).

### Правило источника истины

- **Спека живет в одном месте.** Продуктовая спека - в `specs/<трек>/spec.md`; в
  `docs/features/<feature>/` ставится **ссылка**, а не копия.
- **Номер сквозной, закрытая спека уходит из дерева** - [правило нумерации](#правило-нумерации).
  Полный список с номерами, областями и статусами - [`specs/README.md`](../../../specs/README.md).
- **Кросс-репозиторный трек.** Спека все равно одна: SoT - в одном репо; в остальных - **только
  ссылка** строкой в `CLAUDE.md`/`AGENTS.md`. Ни каталога `specs/<трек>`, ни карты локального
  участка, ни второй нумерации `FR-NNN`; участки всех репозиториев описываются в самой спеке.
- **ADR описывает действующее правило:** изменение принятого решения правит его тело в PR трека по
  [жизненному циклу](../adr/README.md#жизненный-цикл) реестра.
  `plan.md`/`tasks.md` - мутабельные рабочие артефакты.
- **Граница сервера и интерфейса.** Домен, контракты, события и миграции живут в серверной области;
  спека UI описывает контракт экрана, а не доменные инварианты сервера.

## Трассируемость (FR-NNN)

Требования нумеруются `FR-NNN` (и `NFR-NNN`) в `spec.md`. Связь требования с работой держат
документы: задача в `tasks.md` ссылается на требование и называет файлы, PR несет закрывающую ссылку на задачу трекера
({{#if module:tracker/jira}}`Closes PROJ-N`{{else}}`Closes #N`{{/if}}), сообщение коммита - `[FR-NNN]`. **Пометок `FR-NNN` в комментариях нет** - ни в
прикладном коде, ни в тестах, ни в скриптах и конвейерах ([standards/code-comments](../standards/code-comments.md#7-что-не-пишут-в-комментарии) §7).

**Чем требование закрыто - маршрут по документам, не по `grep`.**

1. Реестр требований `docs/platform/requirements/registry.md`, если проект его ведет, - строка
   `FR-NNN`: столбец "Свидетельство" называет файлы и тесты, столбец "Спека" - трек, где требование
   заведено. Это живой документ, PR, меняющий поведение, правит запись; повод открыть запись печатает
   [`check-requirements-registry.py`](../../../.harness/scripts/check/check-requirements-registry.py).
2. `tasks.md` спеки - задачи по этому требованию с путями файлов; строка задачи и есть acceptance
   ([критерий полезности теста](../standards/test-usefulness.md)).
3. Задача GitHub и PR трека - разбор решения и его причина.
4. `git log -S FR-NNN` и `git blame` по названному файлу - от строки к коммиту, дальше к связанному
   PR или трейлерам `Issue:` и `PR:`.

**Колонка "Статус as-is" в спеке в этот маршрут не входит.** Она фиксирует, от какого состояния
трек отталкивался, и после реализации не пересматривается: требование, построенное треком, остается
в ней со статусом "нет" навсегда. Принимать ее за текущее состояние продукта нельзя - для этого
есть шаги 1 и 2 маршрута. Каждая спека несет эту оговорку под заголовком требований, шаблон ее
задает.

Acceptance требования - зеленый тест по критерию полезности и закрытые критерии спеки, а не `grep`
по комментарию.
Правило исполняется гейтом `comment-layer` (правило `traceability`), когда проект задал `docs.comments`,
стандарт слоя - [standards/code-comments](../standards/code-comments.md) §7.

## Что относится к чему (быстрый ответ)

- **"ЕСЛИ ... ТО ...", "КОГДА ... система ДОЛЖНА ..."** - это EARS, формат требований в `spec.md`.
- **"куда что переносим, какие проекты, порядок PR"** - это `plan.md`.
- **"можно ли так по зависимостям модулей"** - это архитектурный гейт стека
  ([gates.md](../architecture/gates.md)), гейт области.
- **"меняем принятую границу/решение"** - это **правка действующего ADR**, не правка спеки. Операционная величина
  границей не является и ADR не заводит.

## Правило нумерации

Номер трека выдает сам Spec Kit: `feature_numbering: timestamp` в [`.specify/init-options.json`](../../../.specify/init-options.json) дает каталогу префикс времени создания `YYYYMMDD-HHMMSS`. Номер уникален без счетчика и резерва, поэтому параллельные копии и клоны его не согласуют, а занятый номер не переиспользуется, даже если трек отклонен. Трек своей ветки не заводит: его ведут в копии, которую выделил `task-worktree.py start`. Активная спека живет в корне `specs/`; каталог закрытого трека из дерева удаляется, а его номер и итоговый статус остаются строкой архивной таблицы [реестра спек](../../../specs/README.md) **с исходным номером**. Треки до перехода на `timestamp` сохраняют трехзначные номера `NNN`.

## Поставка

`.specify/` и скиллы `speckit-*` ставит комплект harness. Версия Spec Kit объявлена в
[`.specify/init-options.json`](../../../.specify/init-options.json); CLI `specify` нужен только для
обновления поставки, работа конвейера его не требует.

Что в поставке сливается, а не накатывается, перечислено в
[индексе скиллов](../../../.agents/skills/README.md#spec-kit). Там же перечислены исключенные скиллы.
**Git-расширения Spec Kit в поставке нет.** Git-стандарт проекта -
[CONTRIBUTING.md](../../../CONTRIBUTING.md), а единственный норматив имен веток - его
[§2](../../../CONTRIBUTING.md#2-ветки).
