| [methodology.json](methodology.json) | Реестр правил `modules`, процессы `processes`, промпты `prompts` и политики `policies.findings`, `policies.size`, `policies.authorship`, `policies.permissions`, `policies.text`, `policies.issues` |

| [lib/hook.sh](lib/hook.sh) | Рамка хуков по одному файлу: корень, разбор ввода, объясненный пропуск, решение агенту |
| [lib/forge.py](lib/forge.py), [lib/tracker.py](lib/tracker.py) | Интерфейсы поставщика кода и трекера задач для python, обертка `forge.sh` - для shell; реализацию дает адаптер включенного расширения ([harness.md](docs/harness.md#поставщик-кода-и-трекер)) |
| [state/](state/lock.json) | Запись установки harness: `lock.json` с версией комплекта, манифестом установки, включенными путями модулей и ролями файлов, каталог модулей `modules.json`. Установщик в проект не ставится и запускается из архива комплекта ([harness.md](docs/harness.md)) |
| [provisioning/](provisioning/scripts/cloud-setup.sh) | Подготовка окружения сессии агента и раннера: установщики тулчейна и их реестр сообщений ([environment.md](docs/environment.md)) |
| [dotnet/](dotnet/Harness.Build.targets) | Адаптер стека .NET: журнал диагностик SARIF для гейта `build-diagnostics` ([gates.md](../docs/platform/architecture/gates.md#net)); ставится с расширением `backend/dotnet` |

В `project/manifest.json` поле `apps[].check` задает полный гейт приложения для CI и ручного локального
запуска. `pre-push` проверяет у сессии агента отправляемые refs и SHA, а в ветке конвейера и регистрацию рабочей копии, у всех -
пробелы и маркеры конфликта через `git diff --check`; команды приложений он не запускает.

Границы областей здесь не описаны: они живут в [`.harness/project/area-map.json`](../.harness/project/area-map.json), у которого свой контракт. Здесь - идентичность проекта, там - раскладка дерева.

## Два разных отказа

**Идентичность проекта - обязательна.** `project.gitConfigPrefix` и адреса модулей `forge` и `tracker` нужны механизму трейлеров: `commit-msg` собирает из них ссылки на задачу и PR, конвейер - имена ключей конфигурации ветки, в которые пишет номер PR, когда узнает его. Запасных значений у них нет. Нет манифеста - `commit-msg` завершается с ошибкой и коммит не проходит, а номер PR за веткой не записывается. Обход: `git commit --no-verify`.

**Необязательные настройки гейтов имеют запасные значения.** Читатель, не нашедший ключа или интерпретатора, возвращает значение, переданное аргументом. Так ведут себя константы `check-docs.py` и `vale-lint.py`; `check-comments.py` без `docs.comments` не запускается, а при неполном наборе отказывает. Проверки конфигурации и гейтов выполняются в CI и вручную через `check-all.py`.

**Реестр правил - обязателен.** Набор правил методологии одинаков во всех проектах на ней: полноту `methodology.json` против комплекта сверяет `verify` установщика, а [`check-all.py`](../.harness/scripts/check/check-all.py) отказывает на записи, чей гейт не найден, и на выключенной записи без причины и замены.

**Запреты объявлены один раз.** `policies.permissions` в [methodology.json](methodology.json)
задает общую декларацию для адаптеров Claude Code, Codex и Cursor. Включенные адаптеры сверяет
[check-agent-permissions.py](scripts/check/check-agent-permissions.py); обязательное правило, которое адаптер
не может выразить, блокирует проверку. Адаптеры ставятся для агента разработки; сессия агента в CI собирает запреты при запуске.

Компилятор пишет `permissions.deny` в `.claude/settings.json` и `.cursor/cli.json`, правила
`prefix_rule` - в `.codex/rules/harness.rules`. Посторонние настройки JSON и дополнительные запреты
сохраняются. У Cursor запреты shell-команд проверяет также `preToolUse` в `.cursor/hooks.json`
с `failClosed: true`, для IDE и облачной сессии. `check-agent-permissions.py --write` повторно применяет
эту декларацию. CI-сессия также добавляет общие запреты к набору инструментов исполнителя.

Запрет начала shell-команды ограничивает этот способ вызова. Запись в площадку кода защищают также
права учетной записи и доверенный публикатор: модель ревью возвращает JSON, а статусы и вердикты
пишет обвязка круга. Правило Codex по argv-префиксу может запрещать и дополнительные аргументы;
альтернативные API и формы флагов не покрываются одним shell-префиксом. Разрешение в клиенте
не выдает право на мерж.

**Имена веток задает только [`CONTRIBUTING §2`](CONTRIBUTING.md#2-ветки).** Конвенцию - поле `git.branchConvention` манифеста - и разбор имени держит [`tracker.py`](lib/tracker.py); его читают выделение копии, `commit-msg`, `pre-push`, уборка, проверка связи PR с задачей, и привязка ветки к задаче.

Опечатка в пути внутри манифеста неотличима от осознанного отказа от значения: гейт промолчит и возьмет запасное. Пропущенные записи называет поименно самопроверка читателей. Самопроверки слоя идут в репозитории комплекта harness до выпуска и в проект не ставятся.

**Читатель держится своего слоя.** По умолчанию корень он берет от собственного файла, независимо
от текущего каталога. `task-worktree.py --root <проект>` явно выбирает манифест и каталог модулей
целевого проекта до загрузки адаптеров; исполняемый код остается из вызванного комплекта.
Удаленный круг ревью идет оснасткой выложенной базовой ветки, а сессия прохода работает в каталоге
выложенной головы. Локальный круг зовет гейт из `.review-base`, копии базовой ветки в дереве головы.
Случай стережет самопроверка читателей.

Удалять `project/manifest.json` из рабочего дерева для этой проверки нельзя. Самопроверка кладет копию `lib/` во временный каталог вне git, где искать манифест негде.

## Что объявляет конвейер

[pipelines.json](pipelines.json) содержит только композиции: каждый шаг ссылается на процесс из
`methodology.json`. Порядок задает `requires`, а не позиция в массиве. Состав и переходы выбранной композиции
печатает `./.harness/hooks/python.cmd .harness/scripts/pipeline/pipeline-run.py plan <имя>`.

[methodology.json](methodology.json) хранит определения процессов в `processes`. Ссылка шага `ref: "процесс/шаг"` использует единственное определение; локальное `requires`
задает зависимости в вызывающем процессе. Проходы ревью объявляются непосредственно в
`processes.review.steps`. Циклы и неоднозначные ссылки отклоняются.
Порядок и подтверждение шагов задают только `pipelines.json` и `methodology.json`: кода под
конкретный шаг у исполнителей нет. `actor` называет исполнителя (`agent`, `command`, `human`,
`pipeline`), `produces` - факты, которыми шаг подтверждается:

| Факт | Гейт сессии (`next`) | `pipeline-run.py run` и `verify` |
| --- | --- | --- |
| `branch` | ветка задачи привязана к сессии | задача назначена, ветка связана с ней |
| `clarified` | уточнение закрыто | - |
| `merged-base` | база входит в историю головы | то же |
| `commits` | копия чиста, есть коммиты сверх базы | то же |
| `simplification-checkpoint` | копия чиста | то же |
| `pushed-head` | голова лежит в удаленной ветке | - |
| `draft-pr` | PR ветки открыт, описание несет запись затрат сессии | черновой PR открыт на голове и связан с задачей |
| `release-pr` | - | черновой PR среза открыт на голове |
| `ready-pr` | PR в Ready либо в Draft после локального круга, который не поручил человек | готовность подтверждена; PR в Ready переводит исполнитель |
| `merge-authorization` | - | открытый PR в Ready с подтвержденной готовностью |
| `merged`, `master-push`, `base-merge` | PR влит | PR влит |
| `closed-issue` | - | PR влит, задача по `Closes` закрыта |
| `retired-workspace` | копия убрана | исполнитель убирает копию после шага |
| `version-tag`, `release-notice`, `back-merge-pr` | - | только workflow релиза |

Шаг без известного факта закрывает `actor`: `agent` - отметка `--done` или сессия агента с аудитом,
`command` - успешная команда на голове, `human` - метка `handoff` или наблюдаемый факт. Шаг
`scope: round` закрывается раз на круг ревью, шаг `session: true` ведет только гейт сессии, шаг `ref`
засчитывается подтверждением того же шага в стадии процесса-источника. `audit: true` включает процесс в аудит CI; аудиту нужны одна стадия
`review`, процесс из одного шага с фактом `draft-pr` и шаг `ready-pr` без `requires` и `gates`.

Поле `method` шага задает способ слияния связанного запроса; `handoff.method` задает способ
при передаче другому исполнителю. Оба поля входят в вывод плана.
Параметры круга
и его проходы лежат в `processes.review`, проходы - в `steps`. У каждого процесса свои предусловия,
результаты и ссылки на инструкции; длинные инструкции остаются в skills и документах.
Промпты объявлены в `prompts.agents` и `prompts.phrases`; это машинный текст по
[project/manifest.json](project/manifest.json). Где лежат промпты, как конвейер их собирает и где проверяется ответ -
[справочник промптов](docs/prompts.md). `processes.review.verdicts` задает слова
решения для публикатора и читателей.

`policies.findings` хранит словарь отсрочки и строку исключения, которые читает
[forge-text-lint.py](hooks/forge-text-lint.py). Хук проверяет текст перед отправкой: предел слов
([кроме вердикта ревью и разбора алерта](../docs/platform/standards/text.md)), подпись агента и
правила письма - всегда, слова отсрочки - только при `agents.findings=same-pr`
(код, цитаты и тело задачи на них не проверяются). Тело и описание без маркера данных с суммой хук
отклоняет всегда ([тексты агента](docs/templates.md#тексты-агента)), а мерж PR, чье
тело коммита не передано или не несет трейлер `PR` со ссылкой на этот PR, - там, где адаптер площадки
называет инструмент мержа; способ слияния без своего коммита (`rebase`) и мерж запроса в другой
репозиторий, чем репозиторий проекта, трейлера не требуют. Запрос на
слияние без описания и заголовок запроса не по правилу заголовка коммита хук тоже отклоняет
([проверка текста](docs/ci-cd.md#агент-задач)).
`policies.authorship`
объявляет подписи агента для [замера автономии](docs/ci-cd.md#замер-автономии).
`policies.issues` - метки типа задачи с описанием и типом ветки (`about`, `commit`) и метки приоритета
с описаниями: правило задает
[`.harness/CONTRIBUTING.md` §12](CONTRIBUTING.md#12-задачи), метки в GitHub Issues создает `forge-setup.py`.

Процессы и промпты ссылаются полем `runner` на исполнителя: усилие по нему задает `efforts`
методологии, инструменты агентов в CI - `agents.tools` файла [project/manifest.json](project/manifest.json), модель -
комплект по провайдеру модуля `ci-agent` ([модуль `ci-agent`](docs/harness-parameters.md#ci-agent)).
Переменную `AGENT_PROVIDER` файлам CI пишет установщик. Все исполнители
запускаются через [agent-run.py](scripts/agent/agent-run.py)
([исполнитель сессии](docs/ci-cd.md#исполнитель-сессии-агента)); бюджеты, промпты
и публикация вердиктов остаются общими.

Круг ревью читает методологию и промпты с базовой ветки. Правку правил самого круга проверяет Check.
Апрув прохода постоянен ([ci-cd.md](docs/ci-cd.md#бюджет-кругов)), кроме коммитов после
апрува всех проходов сверх [правки после апрува](docs/ci-cd.md#правка-после-апрува). История решений
помогает не повторять советы, но апрува не дает.

[check-pipeline.py](scripts/check/check-pipeline.py) сверяет ссылки, зависимости и параметры процессов.
Исполнение и проверку стадий ведет [pipeline-run.py](scripts/pipeline/pipeline-run.py): отметка агента о
завершении сама по себе не доказывает результат. Команды, аудит и действия на площадке требуют
своих подтверждений; отсутствующее обязательное подтверждение блокирует продолжение.

## Авторская рабочая копия

`task-worktree.py start --type <тип> --key <слаг>`, с задачей еще `--issue <ключ>`, создает одну ветку
конвенции и worktree до запуска модели; тип - тип Conventional Commits будущего заголовка PR. Без
задачи и `--change` тип и слаг обязательны, с задачей их без флагов дают метка типа и заголовок задачи
([`.harness/CONTRIBUTING.md` §2](CONTRIBUTING.md#2-ветки)), а ветку задачи, уже выделенную или существующую на origin, выделение переиспользует при
любых `--type` и `--key`. Без задачи копию находит только точное имя `{тип}/{слаг}`. `--base origin/<ветка>` задает базу стека; `--change <номер>` продолжает
открытый PR. JSON результата содержит путь рабочей копии. Коммит агента в невыделенной ветке
конвенции и в сессии исполнителя `commit-msg` отклоняет с этой командой. В невыделенной ветке вне
конвенции, кроме общих, агент коммитит без выделения и без `Task-Branch` и
пушит только текущую ветку, и Check такой коммит принимает. В общей ветке - базовой, релизной, `release/` и
`back-merge/` - хуки отклоняют коммит и отправку сессии агента и называют переход на свою ветку.
Проверки копии и трейлера `Task-Branch` касаются только сессий агента: окружения из `policies.authorship.agentEnv` или `HARNESS_TASK_BRANCH` локально и коммитов, которые `policies.authorship.commitTrailers` или `commitEmails` называют коммитами агента, в Check. Человек коммитит, пушит, удаляет ветки и теги из любой ветки без выделения; сессии агента `pre-push` пропускает только ее ветку. После мержа копию убирает `cleanup` (ниже). `agent-run.py --mode agent` выделяет копию сам
([исполнитель сессии](docs/ci-cd.md#исполнитель-сессии-агента)). Запуск из уже выделенной копии
переиспользует ее независимо от текста очередной стадии. Режим `review` не меняется; `reply` отвечает на комментарии без авторской ветки и с запретом записи в дерево, так же как на события закрытого PR и PR из другого репозитория; ревью и конец круга на открытом PR своего репозитория идут в авторскую сессию; маркер исходного комментария и его текста предотвращает повторный ответ на повторную доставку. `pipeline-run.py run change` выделяет копию
до первой стадии. Авторская сессия держит блокировку задачи. `release.py cut --push` создает ветку среза через API поставщика кода, а не push из копии задачи.

Ветку можно передать в другую зарегистрированную рабочую копию того же репозитория. Сначала
освободите ветку в прежней копии через `git switch --detach`, затем переключите новую копию
на эту ветку и выполните:

```bash
./.harness/hooks/python.cmd .harness/scripts/pipeline/task-worktree.py handoff
```

Команда сверяет HEAD, реестр задачи и чистоту прежней копии. Основная рабочая копия также
поддерживается; автоматическая очистка не удаляет ее и не архивирует ее игнорируемые файлы.

`Task-Branch` проверяется hooks и общим входом CI. Значение читается Git из блока трейлеров сообщения: упоминание в теле второго трейлера не создает. Коммит слияния, созданный площадкой внутри ветки задачи, Check принимает после сверки через API: состояние merged, точный merge/squash SHA, репозиторий и целевая ветка запроса. PR, созданные до внедрения механизма в целевую ветку, сохраняют имена и после обновления базы.
Их прежние коммиты без `Task-Branch` принимаются по SHA, которые площадка подтвердила до внедрения: GitHub - ревью или запуском Actions, GitLab - версией diff.
Коммит должен входить в историю такого снимка и текущей головы PR. Дата Git не подтверждает давность; без доступного снимка исключение не применяется.
Для сохранения прежних коммитов без трейлера такой снимок в GitHub должен появиться до первого внедрения; CI читает Actions с правом `actions: read`. Новые коммиты автора в ветках конвенции требуют привязку. Выделение включает `.githooks` в клоне без `core.hooksPath`, поэтому привязку ставят и сессии CI; без хука `commit-msg` Check ее не проверяет. Момент внедрения - позднее из двух
слияний в целевую ветку: механизма выделения и поля `git.branchConvention` манифеста. С перехода на
конвенцию проверка охватывает и ручные ветки `<тип>/<слаг>`. На ветке открытого PR вне конвенции принимается `Task-Branch`
этой ветки. Чужая метка сама по себе не снимает проверку. CI освобождает унаследованный коммит
только после подтверждения API, что исходный PR слит, его merge входит в текущую базу,
а коммит достижим из проверенной исходной головы этого PR. Так проходят интеграционная ветка,
обратное слияние и дочерний PR стека после squash родителя; новая подделка чужой метки отклоняется. Локальные хуки отключаются
настройкой Git; запрет создания произвольных удаленных refs требует серверных правил доступа.
Уже существующую ветку `start` принимает, если ее ведет открытый PR либо все ее коммиты от базы несут
`Task-Branch` этой ветки: так продолжаются копия разработчика и прерванный прогон CI. Отставшая
локальная ветка догоняет origin, ветку с новыми локальными коммитами сохраняют, разошедшиеся и занятые
другой копией ветки отклоняются. Ветка, чьи изменения уже есть в базе после squash прошлого PR,
сразу подтягивает базу слиянием. Если PR перевели на другую базу, реестр берет ее из PR; after-merge
слитого PR без записи реестра идет в вызывающей копии. Закрытый без слияния PR освобождает запись для
следующего PR той же ветки.

`task-worktree.py cleanup --change <номер>` проверяет merge и сохранность head, создает и проверяет
bundle, удаляет игнорируемые файлы копии и убирает только зарегистрированную чистую неактивную
копию, затем удаляет ветку, bundle, каталог локального круга `.sessions/review/<PR>/` с его
деревьями и запись задачи; повтор для уже убранного PR завершается без действий.
Локальная ветка, отставшая от головы влитого PR, сначала догоняет ее, если своих коммитов в ней нет;
ветку с коммитами вне головы PR уборка не трогает. База стека, удаленная после слияния родителя,
проверяется через влитый PR этой базы: слияние дочернего PR входит в голову родителя, а родитель -
в свою базу. Если коммиты вне головы PR есть или слияние до основной ветки не подтверждается, запись
остается, а отказ называет следующее действие: перенести коммиты в новый PR или удалить ветку,
проверить, дошли ли изменения до основной ветки; после него `cleanup` повторяют. Запись, чей каталог
копии удален мимо `cleanup`, убирается по голове PR, если ветку задачи не держит другая копия.
Запись без PR, у которой нет ни ветки локально и на origin, ни своей копии, уборка удаляет;
своей копии нет и тогда, когда путь записи - основной клон на другой ветке.
Запись влитого PR, чей путь - основной клон на другой ветке, уборка снимает вместе с артефактами
и деревьями локального круга без сверки ветки с головой PR: ветку она не трогает, а
запись конвейера до стадии `after-merge` оставляет, как `cleanup`.
Файлы `.lock` и `.pipeline.lock` в `harness/tasks` остаются: они сохраняют общую блокировку процессов
при повторном выделении той же ветки. `cleanup` без `--change` убирает так все слитые задачи;
его вызывают хук старта сессии в фоне, хук `post-merge`, `start` перед выделением и
`pipeline-run.py run change` после мержа PR. Занятые, грязные и не подтвержденные
копии остаются с причиной отказа. Очистка из авторской сессии откладывается до следующего запуска без ее привязки. Фаза удаления сохраняется до удаления каталога и возобновляется после прерывания. Реестр и bundle лежат вне исходников в общем Git-каталоге
`harness/tasks`; рабочие копии - вне Git-каталога, в соседнем с основным репозиторием
`.harness-worktrees/<16-символьный-хэш-репозитория>/<16-символьный-хэш-задачи>`. Полная ветка и полный
хэш задачи сохраняются в реестре; совпадение короткого пути вызывает отказ, а не замену чужой копии.
Путь одинаков для всех linked worktree этого
репозитория. Это сохраняет стандартные ограничения инструментов, запрещающих читать исходники
внутри `.git`.

Старую зарегистрированную копию с полным 64-символьным именем, внутри `.git` или вне его,
переносят после остановки ее авторской сессии и конвейера:
`task-worktree.py relocate --root <основной-репозиторий> --branch <ветка>`. Команду запускают из
каталога вне переносимой копии. Она берет блокировки выделения, конвейера и сессии, выполняет
`git worktree move` и атомарно обновляет реестр. Ветка, HEAD, индекс, конфигурация worktree,
исходники, незарегистрированные и игнорируемые файлы сохраняются. Занятая копия или занятый путь
назначения вызывают отказ. После прерывания повторяют ту же команду; `start` до переноса
продолжает использовать старую запись. Реестр и блокировки остаются в общем Git-каталоге.

## Исполнение и подтверждения стадий

Сохрани постановку в файл вне конфигурации, затем запусти конвейер с обязательными именами проверок CI:

```bash
./.harness/hooks/python.cmd .harness/scripts/pipeline/pipeline-run.py run change --task <файл> --change <номер> --base origin/<базовая-ветка> --required-check check --reviewer <логин-публикатора>
./.harness/hooks/python.cmd .harness/scripts/pipeline/pipeline-run.py verify change --task <файл> --change <номер> --base origin/<базовая-ветка> --required-check check --reviewer <логин-публикатора>
```

Задача определяется сначала по `--issue`, затем по ветке, затем по единственной связи PR с задачей.
Допустимы `Refs` для промежуточного результата и `Closes` для завершающего. Противоречивые или
неоднозначные ссылки, отсутствие нужной связи, назначенного исполнителя или фактической привязки
ветки блокируют продолжение и без явного `--issue`. После мержа `Closes` требует закрытия задачи;
`Refs` ее не закрывает. Прямое поручение без задачи допускается, когда фактической связи с задачей нет. Вне CI обязателен
`--reviewer <логин>` доверенного публикатора: учетная запись автора не заменяет учетную запись ревью. `--required-check` повторяется для каждого обязательного
контекста CI: пустой список или отсутствующая проверка не разрешают Ready. По умолчанию `--until` - шаг с фактом `ready-pr`;
можно остановиться на процессе или `процесс/шаг`. Мерж команда по умолчанию не выполняет.

Ветку задачи подтверждает связь в трекере или номер задачи в имени ветки ([привязка ветки к задаче](docs/ci-cd.md#привязка-ветки-к-задаче));
текущий `Refs` или `Closes` в описании остается обязательным.

`run` запускает сессии через `agent-run.py` и команды гейтов, объявленные процессом. Аудиты идут
отдельными сессиями только для чтения с `--review-purpose process-audit` и возвращают структурированный
результат с описанием проверенных свидетельств даже при апруве без находок. Прочитанное вердикта и
аудита `agent-run.py` снимает с журнала инструментов сессии: сессия прохода ревью без чтения файла дерева - отказ
(аудит процесса - нет: его наблюдения в промпте), а непрочитанный файл диффа вердикт называет строкой. Подтверждение связано с постановкой, head,
текущей удаленной базой, снимком дерева и правилами. Обвязка записывает аргументы
команд, код выхода и хэши журналов; перед принятием действий перечитывает состояние PR и задачи.

Повтор того же вызова продолжает прогон по `.git/harness/pipelines/<хэш-контекста>/state.json`.
`verify` проверяет подтверждения и перечитывает внешнее состояние, отсутствующее или устаревшее
подтверждение блокирует стадию. Состояние и журналы остаются артефактами, в git их не добавляют.

Успешная сессия удаленного ревью оставляет `log.receipt.json` после проверки неизменности дерева и
текущего PR; отложенный публикатор требует эту квитанцию. Зеленый статус публикует доверенный
workflow с отдельными учетными данными: публикация требует CI, `REVIEW_TRUSTED_PUBLISHER=true` и
адреса своего прогона, а локальный журнал остается изменяемым автором средством продолжения. Что
подтверждает `pipeline/ready` и чем его не заменить -
[подтверждение стадий](docs/ci-cd.md#подтверждение-стадий-в-ci) и
[локальный круг](docs/ci-cd.md#локальный-круг-ревью); апрув прохода
учитывается на любой голове ([бюджет кругов](docs/ci-cd.md#бюджет-кругов)).

В CI независимый аудит текущих результатов и публикацию `pipeline/ready` выполняют отдельные
задания; ручному PR история агентских команд не приписывается
([подтверждение стадий](docs/ci-cd.md#подтверждение-стадий-в-ci)).

Релизные действия продолжают выполнять `release.py` и workflows. Неподтвержденное внешнее действие
релиза блокирует `pipeline-run.py`; обхода через обычное ревью разработки нет.

## Сессия конвейера

Хук [`agent-gate.py`](hooks/agent-gate.py) ведет сессию агента по конвейеру `change` с первого вызова
`pipeline-run.py next change` до `--leave`; срабатывает на сообщение человека, вызов инструмента и
остановку. Сессии `agent-run.py` хук не ведет.
Состояние сессии лежит в `.git/harness/sessions/` и `.git/harness/watch/`.

`pipeline-run.py next change --session <идентификатор>` выводит первый незакрытый шаг по
[фактам шагов](#что-объявляет-конвейер): инструкцию шага из промпта `prompts/session/`
([промпты](docs/prompts.md#где-лежат)). Стадию `review` закрывает последний вердикт каждого прохода;
молчащий удаленный круг повторяется до `retries`, затем шаг ведет к
[локальному кругу](docs/ci-cd.md#локальный-круг-ревью). Апрув у всех проходов
без статусов `review/<проход>` на голове ведет к кругу переноса. Шаги отмечают `--done`, `--run`,
`--run review` (`--local <ключ>` - локальный круг, ключ причины из `LocalReason` реестра шаблонов) и `--wait`; уточнение - `--question`,
`--assume`, `--clarified` и `--sdd`. Условия задачи человек задает при входе, до выделения ветки:
`--base <ветка>`, `--review ci|local`, `--rounds <N>|max` и `--merge human|agent`. Вызов `/release` при модуле `release/tag-flow` начинает
[сессию релиза](docs/ci-cd.md#сессия-релиза) с единственным флагом `--merge`. Флаги читает хук `agent-gate.py` из сообщения
человека, которое начинается с вызова скилла; `next change` их применяет, а сам таких флагов не
принимает, поэтому агент условия не задает. Без хука сообщения и в сессии `agent-run.py` действуют
значения по умолчанию. Ревью без флага задает настройка `agents.review`
([параметры](docs/harness-parameters.md)); база и мерж настройки не имеют. Условия хранятся в состоянии сессии:
режим ревью записывается при выделении ветки и до конца задачи не перечитывается. Новая ветка той же сессии берет условия последнего сообщения человека, только если оно начинается с вызова скилла: сообщение без вызова их снимает, и следующая задача получает значения по умолчанию. Дальше их применяет
гейт, а не агент: `task-worktree.py start --session` берет базу и отказывает на другой, `--run review`
при `local` идет локальным кругом с причиной `direct`. Когда локальные круги по поручению
человека одобрили все проходы, шаг `ready` называет команду `--run ready`. Стадия `merge` при
`agent` называет `--run handoff`: команда ставит на PR в Ready метку передачи мержа. Условия обеих команд -
[локальный круг ревью](docs/ci-cd.md#локальный-круг-ревью). Обе выполняются,
только когда конвейер дошел до своего шага на текущей голове; оценка шага и отчет состояние PR не
меняют. Выделение другой ветки в той же сессии условий
входа не наследует: новая задача режется от базовой ветки проекта, свои условия ей задает вход после
`--leave`. После
выделения ветки условия из нового сообщения человека дают отказ, а в сессии `agent-run.py` действуют
значения по умолчанию. Итоговый отчет собирает `--report -`: гейт заново оценивает шаг
и подставляет в `report/session` состояние, PR, условия задачи, вердикты, допущения и затраты сессии, а агент дает только
итог на вход команды. Вне итогового шага и без трех повторов шага команда отказывает. Вызов с
`--report` сессию не заводит: после конца сессии он отвечает, что сессии нет. `--wait` ждет вердиктов
удаленного круга до 100 секунд: столько выдерживает синхронный вызов агента. С `--background` - для
фоновой задачи - он ждет, пока придут вердикты или истечет `waitMinutes`, и перечитывает состояние PR
раз в `pollMinutes`, не позже срока. `task-worktree.py start --session` привязывает ветку к сессии,
`task-worktree.py await-merge --change <номер> --detach` ждет мержа и выполняет `cleanup`.

Пока PR открыт и не все проходы одобрены, `sync-base` базу не требует: подлив не прерывает идущий
круг, а апрув прохода переходит на новую голову. Предел кругов - флаг `--rounds`, без него `maxVisits`
перехода `changes`: он считает круги с правками - головы с вердиктом `changes`, и после круга, которым
предел достигнут, ведет человек; запуск без вердикта предел не тратит. `--rounds max` снимает предел,
`--rounds 0` снимает стадию ревью: шаг `ready` называет `--run ready` без вердиктов
([условия и защита базы](docs/ci-cd.md#локальный-круг-ревью)). Флаг не меняет
шаги, проходы и способ круга.

Хук правки отклоняет правку до `claim` и `clarify` (после `--sdd` - кроме каталога трека) и вне
рабочей копии задачи; каталог локального круга `.sessions/review/` основного клона он не проверяет.
Он видит инструменты правки агента; запись командой оболочки его минует, и к шагу агента возвращает
хук остановки: шаг считается по состоянию Git, а не по вызовам инструментов.
Если гейт не смог оценить шаг сессии, которую ведет, он не молчит: правку отклоняет с текстом
ошибки, на сообщении человека возвращает ошибку в ответе хука, а на остановке - один раз на каждую
новую ошибку, пока остановка снова не пройдет без сбоя. В Cursor ответ хука на сообщение человека
текста не несет, и ошибку там дает остановка. Сессию вне конвейера сбой гейта не задевает: ее
правки проходят.
Хук запретов и хук текстов поставщика кода при сбое своей проверки тоже отказывают с причиной.
Хук остановки возвращает агента к шагу. Когда вопросы ждут человека, он отпускает агента без отчета,
а с итоговым отчетом - когда идет ожидание мержа, PR влит или закрыт, состояние PR недоступно,
исчерпан предел кругов, круг переноса не поставил статусы, шаг повторился трижды. Сообщение человека
снимает счет повторов, и гейт снова ведет агента. Пока идет фоновая команда конвейера
(`pipeline-run.py`, `review-local.py`) или фоновый субагент, хук остановки отпускает агента без текста
и без счета повторов: к шагу его вернет уведомление о завершении. Такие задачи хук видит в журнале
сессии Claude Code: запуск с `backgroundTaskId` или `isAsync` не старше двух часов без
`<task-notification>` с тем же `tool-use-id`. Прочая фоновая команда, например сервер, остановку не
держит. Промпты долгих шагов - гейтов, ожидания вердиктов и локального круга - велят запускать их
одной фоновой задачей и ждать уведомления без `sleep` и опроса.

Затраты PR записывает каждая сессия по ходу работы, и прежние затраты не переписываются
([`change_cost.py`](scripts/text/change_cost.py)). Черновой PR несет последним разделом описания
затраты первоначальной разработки и упрощения: их подставляет `text_templates.py render
change/description --session <id>`, а маркер описания хранит запись затрат сессии. Без `--session` раздела
нет, поэтому шаг `draft-pr` конвейера не засчитывается, пока описание PR не несет запись затрат
(`change_cost.kept`), а у агентов, чьи хуки передают журнал сессии (Claude Code, Codex), - и пока запись
своей сессии пуста и собрана без журнала (`change_cost.missing`, `change_cost.journaled`): гейт просит собрать описание заново с
`--change <номер> --session <id>`, и команда считает запись, которой в описании нет или которая пуста без журнала ([`templates.md`](docs/templates.md#тексты-агента)).
Запись из прочитанного журнала несет пометку `journal`: пустой она остается, когда журнал агента не несет расхода и
времени (Cursor), гейт ее принимает, а блок статистики пишет, что затраты агента недоступны. Запись, маркеры
вердиктов и итога затрат несут разбивку по тарифам: модель (с пометкой `fast` для быстрого режима),
вход без кеша, чтение кеша, запись кеша и ее часть со сроком в час, выход; итог не пишет разбивку
стороны, у части записей которой ее нет. Тексты затрат показывают токены таблицей по моделям: вход,
выход, чтение кеша, запись на 5 минут и на 1 час; чего провайдер не отдает - прочерк, запись без
срока идет пометкой под таблицей. Правленое описание
собирается той же командой с `--change <номер>`: блок статистики, затраты записи и все, что стоит после
маркера описания (например, текст, который дописали человек или задание CI), она переносит без
изменений, а прочитанное своей сессии вне CI с `--session` считает заново: опрос телеметрии берет его
из описания при первом переводе в Ready. Строки связи с задачей она переносит, если не заданы `--issue` и `--refs`. Когда круг ревью
закончился - последние вердикты всех проходов одобряют PR или на голове последнего вердикта есть
запрос правок, - гейт один раз на сессию, голову круга и итог публикует результат круга
`comment/round-result`: номер круга, итог значком и словом ("Ревью пройдено" или "Правки"), модель,
время и токены доработки с прошлой записи этой сессии. Пока у Claude Code или Codex нет пути
журнала сессии, результат круга откладывается до запуска, где путь известен, и итог `comment/cost`
на этой голове ждет его. Голова круга - голова последнего вердикта, а
не ветки, и гейт проверяет конец круга до остальных шагов: подлив базы после одобрения или новый
коммит до проверки результат не теряют. Итог входит в ключ, потому что на одной голове бывает
несколько кругов: после правки описания PR или удаленный круг после локального. Маркер
результата несет накопленные затраты сессии. Решение берется из записей PR, а не из памяти сессии,
поэтому его принимает и сессия, которая продолжила PR на другой машине. Когда все проходы одобрили
голову, гейт после результата круга один раз на эту голову публикует итог `comment/cost` - до Check и
перевода в Ready, потому что PR с апрувами может влить и человек. Итог складывает последнюю запись
каждой сессии (описание или результат круга), живые затраты сессии, которая его публикует, и затраты
вердиктов ревью; прежний итог снимается, новый встает в конец ленты. Комментарии доработки
`comment/cost-revision`, опубликованные до перехода, итог тоже читает. Ревью - сумма маркеров
опубликованных вердиктов PR, круг - SHA, на котором они опубликованы. Разработка - журнал сессии из
хука остановки и журналы ее субагентов с момента, когда сессия взяла задачу (`since` состояния),
кроме ревьюеров, чей `agentId` назван в маркере вердикта. Время разработки - активное: паузы журнала
длиннее 10 минут не считаются, окна ревью вычитаются: каждый проход - от публикации вердикта минус
его `SessionSeconds`, каждый запрос круга - до первого вердикта на его SHA.

## Как снять правило

Реестр правил складывается из двух файлов. `.harness/methodology.json` целиком принадлежит комплекту:
`apply` пишет его версией комплекта, и правка проекта в нем до следующей установки не доживает. Решения
проекта о правилах живут в разделе `rules` манифеста `.harness/project/manifest.json`; `check-all.py`, `verify`
установщика и гейты, которые читают реестр, применяют их поверх записей комплекта.

Правило комплекта не удаляется: `verify` установщика назовет пропавшую запись. Снимает его запись
`rules.disabled` с полями `id` (правило комплекта), `reason` (почему правило к проекту не применимо) и
`replacement` (кто или что делает работу правила вместо него). Запись без причины или замены и запись с
`id`, которого в реестре комплекта нет, отклоняет `verify` установщика, а снятое без причины правило -
и `check-all.py`. Правило путей модуля, которого манифест не включил, снимает сам установщик записью
`enabled: false` в `methodology.json`: причину и замену он берет из текстов выключения каталога модулей,
а в `disabledBy` пишет невключенный путь - модуль, `<модуль>/<расширение>` или `stack/<стек>`.
`check-all.py` печатает причину и замену у снятого гейта, а под таблицей - одну строку с этими путями и
командой, которая их включает: `"$KIT/payload/.harness/hooks/python.cmd" "$KIT/ah.py" configure --target . --reopen <модуль> --next` из архива установленной версии
у модуля и расширения, та же команда с `--reopen apps` у стека - его включает приложение этого стека.
Правило, которое снял проект, возвращает удаление его записи `rules.disabled`.

Замена на свое правило - две записи. Правило комплекта снимается записью `rules.disabled`, `replacement` которой называет новое; гейты комплекта зашиты в план `check-all.py`. Собственное правило проекта - запись `rules.own` с `id`, `title`, `doc`, `gate` (путь, который `verify` установщика и `check-all.py` сверяют с деревом) и `command` - списком аргументов команды гейта: ее `check-all.py` запускает в каждом прогоне; `copies` называет файлы, которые сверяет гейт копий. `id` своего правила не повторяет `id` правила комплекта. Запись без поля `gate` - правило, у которого механической проверки нет вовсе: оно живет слоем суждения, скиллом или документом, и в прогоне не участвует.

```json
"rules": {
  "disabled": [{"id": "prose", "reason": "<почему не применимо>", "replacement": "<что делает работу>"}],
  "own": [{"id": "<правило>", "title": "<что держит>", "doc": "<документ>", "gate": "tools/check.py",
           "command": ["python3", "tools/check.py"]}]
}
```

Раздел `rules` - часть манифеста: правку руками `configure --target . --next` переносит в ответы
настройки, как и другие правки манифеста, а `apply` ставит слой по новому манифесту.

Полноту реестра по скиллам стережет `check-docs.py --area agents`: у каждого проектного скилла из [индекса](docs/skills.md) обязана быть запись, и область скилла задают его `description` и ссылки.

Гейты реестра запускает `check-all.py` в CI и при ручном локальном запуске. Конвейер [check.yml](../.github/workflows/check.yml) и задача GitLab `harness-check` читают реестр через `check-all.py`: выключение правила действует в CI, а замена встроенной полной проверки оформляется двумя записями.

## Установка и обновление

Слой ставит и обновляет комплект harness: установщик раскладывает файлы, пишет
[`state/lock.json`](state/lock.json) и пишет файлы и блоки комплекта его версией. Порядок и роли
файлов - [harness.md](docs/harness.md). Новую версию из выпуска ставит
`python3 .harness/ah.py upgrade`: ветка задачи, `apply` новой версией и PR, который открывает
`scripts/pipeline/kit-upgrade.py` с описанием по шаблону `change/kit-upgrade`.

Скиллы `.agents/skills/` делятся на вендорные - поставка Spec Kit и пакеты модуля `skills`, которые обновляются своей поставкой, - и проектные; перечень - [индекс скиллов](docs/skills.md).

Разбор Markdown использует закрепленные pure-Python архивы из `.harness/vendor/libraries.json`. Они загружаются без pip; перед импортом сверяется SHA-256. Лицензии поставлены рядом с архивами.

При достижении штатного предела вложенности Markdown разбор отклоняется целиком. Ошибка чтения
входов снимает прежние статусы ревью и Ready через доверенного публикатора после сверки открытого
PR, головы и базы. Отказ сохраняется в результате команды; прежнее одобрение не переиспользуется.
