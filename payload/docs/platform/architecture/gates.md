# Архитектурные гейты по стекам

> **Тип (Diataxis):** Справочник

Архитектурное правило проверяет тест, а не ревью на глаз: отступление не аргументируется словами в
PR, а оформляется правкой действующего ADR. Конвенция области - экспорты, импорты, именование, границы
слоев - тоже проверяется линтером или тестом; правило без гейта не вводится, реестр правил и их
гейтов - [`.harness/methodology.json`](../../../.harness/methodology.json) и раздел `rules` манифеста.
Правило одно на все проекты методологии, инструмент задает стек приложения, а
включает - путь модуля манифеста: стек приложения в `apps[].stack`, решение .NET в
`backend/dotnet.solution`, правила кода и архитектуры - конфиги и точки входа самого проекта
([точки входа](../agents/harness-parameters.md#точки-входа-приложения)).

| Стек | Границы слоев | Целевая архитектура и подавления | Где идет |
| --- | --- | --- | --- |
| `dotnet` | точка входа `entries.architecture` приложения | анализаторы и политика сборки проекта, журнал SARIF | гейты `build-diagnostics`, `dotnet-format` и роль `architecture` после `check` приложения |
| `node` | `layerBoundaries` в ESLint приложения | правила ESLint проекта: модули настройки `<сторона>/node.rules` с экспортом `required` | `check` приложения; подключение сверяет гейт `node-adapter` |
| без адаптера | точка входа `entries.architecture` приложения | гейты дерева | роль `architecture` после `check` приложения |

## .NET

**Подключение.** Установщик пишет блок импорта `.harness/dotnet/Harness.Build.targets` в ближайший к
решению `Directory.Build.targets` (новый файл - в каталоге решения); каталог без такого файла импорт
получает повторным `apply`. Цель включает журнал SARIF каждой компиляции: его читает
`check-build-diagnostics.py`, и норма - ноль диагностик любого уровня. На каждое нарушение гейт
печатает описание правила из журнала: что правило отклоняет и какие настройки его меняют.

**Правила проекта.** Анализаторы, архитектурные тесты, раскладку и политику сборки задает проект в
своих `Directory.Build.*` и проектах решения; комплект их не несет. Сборку с анализаторами гейт кода
получает точкой входа `analyze` приложения, архитектурные тесты - точкой входа `architecture`
([точки входа](../agents/harness-parameters.md#точки-входа-приложения)); без них проверки показаны как
"не настроено". Конфиги политики называет `apps[].configs`: `diagnostic-integrity` принимает
`NoWarn` и список рукописных входов компилятора только в них.

Подавители Roslyn снимают диагностику только в описанном контракте, и `check-build-diagnostics.py`
засчитывает их подавления без записи в манифесте: пары кодов он читает из исходников подавителей
решения, а подавители из пакетов называет `backend/dotnet.suppressions`.

Журнал диагностик читает сборки конфигурации `backend/dotnet.configuration` и идет после `check`
приложения, который их собирает в той же конфигурации.

## node

Границы слоев задает модуль [`.config/eslint-boundaries.js`](../../../.config/eslint-boundaries.js), который
`eslint.config` приложения подключает сам. Обязательные правила задает проект: настройка
`<сторона>/node.rules` называет модули, каждый экспортирует `required`, и `eslint.config` каждого
приложения стороны их импортирует. Свой экспорт `required` может нести и сам конфиг:

```js
import { layerBoundaries } from "../../.config/eslint-boundaries.js";

import { defineConfig } from "eslint/config";
import tseslint from "typescript-eslint";

export const required = {
  "@typescript-eslint/no-floating-promises": "error",
};

export default defineConfig(
  {
    extends: [...tseslint.configs.recommended],
    files: ["src/**/*.{ts,tsx,mts,cts}"],
    languageOptions: { parserOptions: { projectService: true, tsconfigRootDir: import.meta.dirname } },
    rules: { ...required },
  },
  ...layerBoundaries({
    source: "src",
    layers: [
      { name: "domain", forbidden: ["application", "ui"] },
      { name: "application", forbidden: ["ui"] },
    ],
  }),
);
```

- `layerBoundaries` - слой перечисляет слои, из которых ему импортировать нельзя; шаблон ловит и
  алиас, и относительный путь.
- `required` - правила, которые проект не дает ослабить ни одному исходнику. Состав и смысл правил
  задает проект; комплект своих правил ESLint не несет.

Гейт `node-adapter` ([`check-node-adapter.py`](../../../.harness/scripts/check/check-node-adapter.py)) сверяет
действующий конфиг ESLint: для каждого исходника TypeScript в каталоге `source` из `layerBoundaries`,
кроме сгенерированных путей манифеста, конфиг держит каждое правило из `required` на уровне `error`.
Правило, добавленное в `required` или снятое, гейт сверяет без другой правки. Параметры правила - ровно
объявленные в `required`: лишний ключ или другое значение - отказ, а в списки (селекторы, шаблоны
запретов) проект добавляет свои элементы. Модуль настройки, который конфиг не импортирует, - отказ: приложение не снимет правила проекта, убрав импорт. Набор `required` гейт собирает из модулей, которые конфиг импортирует локальным путем. Пустая настройка и конфиг без `required` - гейт сверяет только слои.
Собранный конфиг применяет `layerBoundaries` хотя бы к
одному слою, и в каждом слое действуют правила слоя на уровне `error` со всеми его запретами - и на
пробе, и на каждом исходнике слоя. Слой без исходников TypeScript - отказ.
Приложение без слоев (сквозные тесты, плоский пакет) объявляет причину в `architectureWaiver`:
тогда гейт не ждет `layerBoundaries` и сверяет правила на каждом исходнике TypeScript приложения. Пути
импорта зависят от глубины каталога приложения; относительный путь выше - для `apps/<app>/`.

## Целостность диагностики

Гейт `diagnostic-integrity`
([`check-diagnostic-integrity.py`](../../../.harness/scripts/check/check-diagnostic-integrity.py)) идет в
Check и доступен для ручного локального запуска. Гейты данных запроса на слияние входят в план только
при заданном `PR_NUMBER` ([ci-cd](../delivery/ci-cd.md#гейт-проекта)).

- Рукописный TypeScript и JavaScript не отключает диагностику директивами `eslint-disable` и
  `@ts-*`. Гейт ищет директивы в токенах комментариев парсеров: литералы, JSX и HTML-текст
  директив не создают. Парсер ищется от каталога приложения и выше: приложение, от которого он не
  найден, становится находкой гейта. Проект без стека `node`
  ESLint и TypeScript не запускает, и его JavaScript, например скрипт шаблона Blazor, гейт не разбирает.
- Конфигурация проекта не ослабляет severity правил и не отключает проверки MSBuild. Гейт сравнивает
  конфигурацию с базой ветки, файлы и блоки комплекта - так же, в том числе в запросе обновления
  комплекта: ослабление в них отказ гейта, а не исключение. Не проверяются только файлы и блоки
  комплекта первой установки, когда в базе ветки еще нет `lock.json`.
- `NoWarn` и список рукописных входов компилятора задают только конфиги проверок приложения
  `apps[].configs`: в другом csproj, `.props` или `.targets` гейт их отклоняет.
- Рукописный файл не объявляется сгенерированным. Сгенерированный файл - путь из
  `docs.generatedPrefixes` или `docs.generatedSegments` манифеста.
- Измененные конфигурации, гейты и анализаторы гейт перечисляет в отчете CI; их проверяет
  независимое ревью.
- Изменение правила требует изменения исполняемого контракта; текст обоснования исключения не
  разрешает.
- SARIF-гейт `check-build-diagnostics.py` принимает только программное подавление с объявленным
  исполняемым контрактом и диагностику сгенерированного файла. Ручное подавление рукописного кода
  ошибку сборки не скрывает.

## Реестры текста

Текст для человека принадлежит корню и лежит в его реестре; вызов передает ключ и значения. Корни -
каждое приложение манифеста, `.harness/scripts`, `.harness`, подсистема скриптов со своей
библиотекой хелперов (`.harness/provisioning`), скилл со своими скриптами, `.config`. Гейт
`text-registry` ([`check-text-registry.py`](../../../.harness/scripts/check/check-text-registry.py))
проверяет литералы в shell, Python, PowerShell, JS-инструментах, run-блоках воркфлоу и исходниках
приложений стека node, а также неиспользуемые, необъявленные и повторные ключи и переменные шаблонов. Реестры кода других
стеков проект объявляет сам и проверяет правилом своего анализатора. В конвейерах GitLab CI гейт
регистрирует и проверяет ключи `MSG_` из `variables:`, литералы `script:` не разбирает.

| Читатель | Реестр корня | Формат |
| --- | --- | --- |
| оператор скрипта sh, py, ps1 | `messages.env` подсистемы | `MSG_<key>='...%s...'`, хелпер принимает `@key` |
| разработчик JS-инструмента | `messages.mjs` рядом с инструментом | именованные функции |
| агент CI | `.harness/prompts` и `methodology.json` | шаблоны `${Name}`, реестр `variables.json` |
| читатель текста, который конвейер публикует целиком | `.harness/templates/` | шаблоны `${Name}`, реестр `variables.json` ([шаблоны](../agents/templates.md)) |
| модель в коде приложения | `Prompts/<scenario>.v<N>.txt` | части `@@ <ключ>`, подстановки по имени |
| человек в интерфейсе стека node | словарь в каталоге `locales/` приложения, формат - выбор проекта; гейт читает код интерфейса, в том числе экранированную кириллицу `\uXXXX`, а файлы каталога `locales/` и JSON-данные, в том числе `manifest.json`, - не читает; манифест PWA с текстом интерфейса - `.webmanifest`, его гейт читает | ключи словаря |
| журнал, отказ операции, письмо | реестр приложения по его стеку | код и шаблон |

- Ключ имеет вид `<корень>.<snake_case>` или `MSG_<key>` реестра скриптов и уникален среди всех
  реестров дерева: повтор ключа в другом реестре гейт отклоняет.
  Проверки и самопроверки сверяют ключ, а не формулировку.
- Одна копия: текст, который видят интерфейс и канал вне его, живет в серверном реестре, и API
  отдает его отрисованным. Текст только для интерфейса живет в словаре приложения, сервер отдает
  код и аргументы.
- Запись, которую покажут человеку, хранит ключ и типизированные аргументы; форматирование - при
  выдаче. Ответ модели хранится текстом.
- Вход модели не повторяет текст человека: промпт получает коды и числа.
- Версия промпта - имя файла `<scenario>.v<N>.txt`, один действующий файл на сценарий. Файл на месте
  не правится: новая версия - новый файл.
- Язык реестров - язык проекта. Перевод - правка реестров, а не кода.
- Вне реестра остаются текст объявления, данные, тесты и вендорный код. Текст объявления - описание
  API, `--help` из заголовка скрипта, имя шага воркфлоу, справка аргументов командной строки.
  Описание инструмента метрики живет в реестре метрик корня.
- Скрипт, который на хосте не видит репозиторий, держит блок `MSG_*` в начале файла в том же
  формате.
- Новый корень заводит реестр тем же изменением, что и первый текст в нем.

## Стек без адаптера

Для `python`, `go`, `jvm` и `other` комплект своих архитектурных тестов не несет, и правило не
снимается молча: приложение обязано назвать замену.

- `entries.architecture` - точка входа гейта, который держит границы приложения: тест импортов
  (`import-linter` у Python, `go-arch-lint` или `depguard` у Go, ArchUnit у JVM) или свой скрипт.
  `check-all.py` зовет ее после `check` приложения, если она не входит в `check` звеном; установщик
  проверяет рабочий каталог и первую программу команды
  ([точки входа](../agents/harness-parameters.md#точки-входа-приложения)).
- `architectureWaiver` - причина, по которой гейта пока нет.

Без одного из двух полей установщик отказывает.
