Файлы CI ставит поставщик кода, остальные модули добавляют свои поверх него. Расширение `github`
модуля `forge` ставит `.github/workflows/`. Расширение `gitlab` ставит `.gitlab/ci/` и блок
`include` в `.gitlab-ci.yml`; задачи идут в стадии `test`, задачи релиза - в стадии `deploy`, образ
задает переменная `HARNESS_CI_IMAGE`, операции у поставщика - переменная `GITLAB_TOKEN`. Без поставщика кода файлы CI не
ставятся: свой CI проекта зовет тот же [гейт проекта](#гейт-проекта), а круг ревью, агент задач,
релиз и разбор алертов требуют модуль `forge` и выключаются вместе с ним.

## Гейт проекта

Состав проверок задает один вход - [`check-all.py`](../../../.harness/scripts/check/check-all.py): `check.yml` и `harness-check` ставят toolchain и зовут его, другой CI зовет его той же командой. Своей копии списка гейтов у файлов CI нет.

```bash
./.harness/hooks/python.cmd .harness/scripts/check/check-all.py --base origin/{{git.baseBranch}}
./.harness/hooks/python.cmd .harness/scripts/check/check-all.py --list
```

Порядок прогона:

1. Изменения ветки - рабочее дерево и неотслеживаемые файлы против точки ветвления с базой - раскладываются по областям [`areas.py`](../../../.harness/scripts/check/areas.py) по карте [area-map](../architecture/area-map.md).
2. При корневом `package.json` без `node_modules` первым идет `npm ci`.
3. Гейты реестра [`.harness/methodology.json`](../../../.harness/methodology.json) идут всегда или по своей области, перечень печатает `check-all.py --list`; `docs` и `agents` - по своей области, правила письма - по измененной прозе. Гейты, которым нужны данные запроса на слияние с площадки, - связь PR с задачей (`pr-issue-link`), размер PR с причиной из описания (`pr-size`) и сверка коммитов с веткой задачи (`task-worktree.py ci` гейта `pipeline`), - входят в план только при заданном `PR_NUMBER`: его передают прогоны гейтов конвейера (стадия `final-gates` в сессии агента и у исполнителя `pipeline-run.py run` - флагом `--change`, который оставляет в плане только эти гейты, а у исполнителя еще полный гейт шага `draft-pr`) и агент в CI, а Check в CI описание, ветку, метки и номер запроса не читает и токена площадки не требует. Гейт невключенного модуля не ставится, его запись в реестре выключена с причиной. Правило проекта с полем `command` в реестре идет в каждом прогоне своей командой ([как завести](../../../.harness/README.md#как-снять-правило)).
4. Приложения поднятых областей проходят свой `check` из [`.harness/project/manifest.json`](../../../.harness/project/manifest.json) командой `bash -c` в каталоге приложения, на Windows - Bash из Git for Windows; после него идут гейты адаптеров ([gates.md](../architecture/gates.md)): у стека `node` - подключение адаптера ESLint, у стека `dotnet` - [журнал диагностик](#ноль-предупреждений-и-сообщений-сборки) и формат C#; анализаторы и архитектурные тесты проекта идут его точками входа `analyze` и `architecture`.
5. Точки входа приложения `apps[].entries` ([роли](../agents/harness-parameters.md#точки-входа-приложения)) идут гейтами кода после гейтов адаптеров, каждая командой `bash -c` в своем рабочем каталоге. Роль, команда которой входит звеном `&&` в `check` и идет в каталоге приложения, второй раз не запускается. Роли без точки входа таблица итога печатает строкой `NONE` с перечнем "не настроено": проверка, которой в проекте нет, не засчитывается пройденной и не роняет прогон.

Если CI проекта уже выполнил команды приложений своей параллельной фазой, он зовет этот вход с `--gates-only` после нее. Такую фазу проект кладет шагами `.harness/project/ci/check/*.sh` ([расширения проекта](../agents/harness.md#расширения-проекта)): задание `check` файла `check.yml` и задача `harness-check` запускают их по имени перед гейтами в той же рабочей копии, базу гейтов шаги фазы и гейты получают переменной `HARNESS_BASE` (ее же `check-all.py` кладет из `--base` в окружение своих команд, и базу видит локальный прогон), целевую ветку запроса - переменной `HARNESS_TARGET`, отказ шага роняет Check, а при хотя бы одном шаге гейты идут с `--gates-only`. База гейтов - целевая ветка запроса, а у release PR из ветки `release/*` - базовая ветка `git.baseBranch`: формат коммитов, бюджет тестов и другие гейты политик уже прошли на PR, которые релиз несет. Приложения и гейты кода release PR отбираются по диффу против целевой ветки (`--since`), поэтому сборка и тесты идут на весь состав релиза; шаги фазы проекта отбирают области по `HARNESS_TARGET`. Флаг пропускает только `apps[].check`: отбор областей, все гейты реестра, команды правил проекта и завершающие проверки адаптеров сохраняются. Сборка приложений должна завершиться до этого вызова, чтобы гейт диагностик проверил ее журналы. Флаг `--tree`, взаимоисключающий с `--gates-only`, оставляет только гейты дерева: без `apps[].check` и гейтов кода - диагностик сборки, архитектурных тестов и адаптеров стеков. Флаг `--docs`, взаимоисключающий с ними, оставляет только гейты документации и запускает гейты дерева на полном охвате, а не на диффе, а гейты истории - на коммитах ветки от `--base`: ссылки и якоря во всех отслеживаемых Markdown проекта, структуру и индекс документов и имена кода в документах их областей, ссылки на ADR в документах, Vale по документам, контракт конвейера, разрешения агентов, реестр требований, скан секретов истории ветки и формат коммитов (список печатает `check-all.py --docs --list`); это готовность этапа 2 установки harness, а весь `check-all.py` - этапа 3.

Флаг `--since <ревизия>` сужает по диффу от нее только приложения и гейты кода, а гейты дерева по-прежнему видят весь дифф против `--base`. Ревизия, которая не предок `HEAD`, игнорируется, и отбор идет от базы. Полный прогон в сессии агента не идет: шаг `gates` стадии `final-gates` ждет Check в CI на одобренной голове и зовет вход только с `--change` ([правка после апрува](#правка-после-апрува)); локально полный `check-all.py` разработчик запускает по своему решению. CI зовет вход без флага и проверяет весь дифф ветки.

Правило, снятое записью `rules.disabled` манифеста или установщиком за невключенный путь, снимается и здесь, но не молча: гейт печатает его причину и замену, под таблицей - невключенные пути и команду, которая их включает, а снятие без причины и замены - отказ. Пропавшая из реестра запись обязательного правила - тоже отказ: правило снимается записью `rules.disabled`, а не удалением записи ([как снять правило](../../../.harness/README.md#как-снять-правило)). Прогон не останавливается на первом отказе и в конце печатает таблицу всех гейтов; под GitHub Actions каждый гейт - своя группа журнала, а отказы - аннотации; под GitLab CI гейт - сворачиваемая секция журнала.

Скан секретов берет `gitleaks` с PATH или из `~/.local/bin`, иначе из образа, закрепленного digest в `check-all.py`. На Linux бинарь копируется из образа. На macOS и Windows скан идет в контейнере над смонтированным деревом и общим каталогом git. Без `gitleaks` и Docker гейт отказывает. Правила и исключения - [`.gitleaks.toml`](../../../.gitleaks.toml), исключение называет файл и строку точно. Скан рабочего дерева пропускает файлы, которые git игнорирует: журналы сессий `.sessions/`, локальный `.env` и выходы сборки в коммит не попадают, а скан истории их и так не видит.

## Подтверждение стадий в CI

В круге ревью GitHub задание `process-audit`, у GitLab - `review-process-audit`, выполняет
`pipeline-run.py audit change`. Наличие вызовов аудита и `check-ready` для обоих поставщиков
проверяет `check-pipeline.py`. Независимые сессии только для чтения проверяют результаты
`develop`, `simplification` и `verification` на текущем снимке PR. Для ручного PR это аудит
результата: он не утверждает, что автор запускал агентский конвейер или сохранил историю его команд.
Автоматический `run` сохраняет собственные команды и подтверждения по
[контракту исполнения](../../../.harness/README.md#исполнение-и-подтверждения-стадий).

Отчет `.review-round/pipeline-audit.json` с журналами и квитанциями передается артефактом того же
прогона; у GitHub его имя - `review-pipeline-audit`. Доверенное задание `pipeline-readiness`
(`review-pipeline-readiness` у GitLab) вызывает `check-ready`: сверяет head, базу, правила, хэши
журналов и происхождение отчета, актуальные вердикты ожидаемого публикатора, обязательный Check
(`check` у GitHub, `harness-check` у GitLab) и незакрытые обсуждения. Оно публикует защищенный
статус `pipeline/ready` на текущей голове, связывая его также с текстом PR и связанных задач.
Правка требований требует нового подтверждения, даже если SHA кода прежний. Проверка Check
подтверждается типом задания и ожидаемым публикатором. Нет обязательной проверки, подтверждения или доступа
к их чтению - Ready закрыт.

В GitHub ожидание обязательных результатов продолжается только после успешных аудита и
публикатора ревью. Если одно из этих заданий отказало, готовность проверяется без ожидания:
недостающие подтверждения дают отказ и освобождают очередь для следующего круга.
Отмененный круг агента задач не будит.

Адаптер GitHub ограниченно повторяет безопасные чтения при временном сетевом отказе или
недоступности сервера. REST GET и запросы GraphQL на чтение отмечены в вызывающем коде;
изменяющие операции автоматически не повторяются. Отказы доступа, неверные аргументы и
постоянные сетевые ошибки остаются отказами.

Агенты задач и алертов читают commit statuses и Checks через `GITHUB_CHECKS_TOKEN`, которому workflow
передает встроенный `GITHUB_TOKEN` с правами `statuses: read` и `checks: read`. Fine-grained PAT
не поддерживает Checks API. Учетная запись агента и операции записи используют прежний токен;
отдельный токен чтения не меняет автора push, комментариев или проверку собственного логина.
Без отдельного токена локальный адаптер использует обычную авторизацию GitHub CLI.
GitHub-адаптер признает заданием CI только check-run приложения GitHub Actions. Результат другого
приложения сохраняется как отдельная проверка и не заменяет обязательное задание с тем же именем.

При чтении GitHub API подтверждает репозиторий, workflow и событие прогона. Для
`pull_request_target` проверяется единственная связь с точными PR, HEAD и BASE. Выбранный BASE
считается доверенным снимком контроллера и политики: stacked PR может опираться на ещё не влитую
ветку. Это не изоляция от вредоносного кода BASE: задания подготовки и публикации исполняют его
с правами записи. Для `issue_comment` и `workflow_run` источник должен принадлежать истории
ветки по умолчанию. План, квитанция и итог исполнителя подтверждают апрув конкретного прохода;
для `pipeline/ready` также нужны успешное задание публикатора и результаты аудитов.
Имя `github-actions[bot]`, текст квитанции и ссылка на прогон этого не заменяют. Для проверки
нужен доступ на чтение Actions. Артефакты круга хранятся 7 дней, метаданные заданий прогона - дольше. После
истечения артефакта решение прохода подтверждает шаг `approved <PR> <голова>` задания прохода: он
исполняется только при апруве. Отзыв засчитывается, когда его решение совпадает с этим шагом. Отзыв, не прошедший проверку, не учитывается вовсе: бюджет
он не тратит и круг не блокирует. В решенное прежних кругов попадают только подтвержденные отзывы. GitLab
сохраняет проверку родного конвейера MR.

Задание `pipeline-readiness` передает свое имя через `--ignore-check`, чтобы не ждать собственного
завершения до публикации результата. Этот флаг не исключает явно обязательные проверки:
совпадающее имя из `--required-check` продолжает проверяться.

Изменение заголовка, описания или базовой ветки PR/MR запускает доверенную инвалидацию:
`pipeline/ready` и `review/*` переходят в ожидание, метка `processes.review.label`
снимается. Новая метка запускает аудит актуальных входов. Инвалидация действует при наличии
прошлого защищенного результата ревью, сохраняя применимость обычного release PR. Апрув прохода она
не снимает: следующий круг переносит его на голову ([бюджет кругов](#бюджет-кругов)).

Правка текста связанной задачи не создает событие PR/MR. `ready` и проверка перед мержем
перечитывают постановку и отвергают прежний отпечаток. Сохраненный статус сам по себе не дает
атомарной защиты от правки задачи через другой интерфейс между последней проверкой и мержем.

Отпечаток постановки включает полные человеческие комментарии PR, построчные обсуждения и
ответы, итоги ревью, текст связанных задач и их комментарии. Служебные записи определяются по
метаданным бота или системы, по метке автора и по служебному маркеру последней строкой: маркеру
данных шаблона `harness-text` и маркерам круга. Терминальные подписи и сообщения жизненного цикла
не дописывают требования. Цитирование служебного маркера в человеческом комментарии сохраняет его в постановке. Из тела PR в отпечаток не
входят блок "Статистика сессии" и маркеры `harness-text` (`change_cost.authored`): их переписывает конвейер,
поэтому пересборка затрат апрувы не сбрасывает, а правка остального тела сбрасывает.

У GitHub создание, правка и удаление человеческого комментария PR (`issue_comment`) также вызывают
доверенную инвалидацию. Создание, правка и удаление построчного комментария, публикация, правка и
отзыв ревью сначала поднимают [`review-inputs.yml`](../../../.github/workflows/review-inputs.yml) на
пуле проверок, без прав доступа и без выкладки кода. Его завершение запускает `code-review` на
пуле ревью с доверенной ветки:
события ревью выбирают определение workflow из PR, поэтому писать статусы прямо в них нельзя.
Публикатор перечитывает прогон через API, сверяет его workflow, событие, репозиторий и текущие head
и base связанного PR. Событие завершения и API должны указывать ровно один и тот же PR: по номеру
из события workflow получает группу concurrency. Подтвержденный прогон для прежнего снимка
или закрытого PR пропускается без изменения статусов. Данные артефактов и текст комментария не дают
права на запись. Затем свежая постановка сверяется с отпечатками результатов: неизменные входы
и служебные записи агента не меняют результаты круга. Оба workflow должны уже находиться в ветке
по умолчанию; отключенный или измененный в PR сигнальный workflow и отсутствие связи прогона
с PR в API могут задержать инвалидацию, но живое чтение Ready все равно отвергает устаревший
отпечаток. Изменения связанных задач также проверяются при живом чтении Ready:
отдельного диспетчера по связанным PR для них нет.

У GitHub подготовка круга, публикация вердиктов, готовности и инвалидация одного PR выполняются
под общей группой concurrency `code-review-<номер>` до конца workflow. Настройки `queue: max`
и `cancel-in-progress: false` ставят новые запросы круга, повторы и изменения входов в очередь,
сохраняя текущий прогон. Устаревший снимок не дает опубликовать апрув или готовность. События
`issue_comment` с автором типа `Bot` не занимают эту группу и не запускают инвалидацию;
тип отправителя события не заменяет тип автора комментария. Публикатор использует `GITHUB_TOKEN`,
чьи служебные комментарии и ревью не запускают рекурсивные workflow.

Очередь GitHub вмещает до 100 ожидающих прогонов: при переполнении новые прогоны отменяются
и не дают нового подтверждения; отмененный запрос круга нужно повторить. Очередь идет по времени
начала ожидания группы, поэтому порядок отправки событий не гарантирован. Живое чтение Ready
остается обязательным и отвергает прежний отпечаток при изменившихся входах.

У GitLab изменение входов запускает отдельный конвейер `HARNESS_INVALIDATE`. Его защищенный
публикатор на раннере ревью держит ту же группу ресурса `harness-review-<MR>-publish`, что
подготовка круга, страж и публикация готовности: их записи одного MR выполняются по одной.

После круга агент задач вызывает `pipeline-run.py ready`: перечитывает внешние подтверждения и
`pipeline/ready`, затем идемпотентно переводит PR в Ready. Локальный журнал автора служит
продолжению работы и аудиту; полномочий опубликовать себе зеленый статус он не дает.

## Релиз

Описанный ниже поток относится к модулю `release/tag-flow`.
{{#unless module:release/tag-flow}}В этом проекте модуль выключен; порядок публикации определяют проектная конфигурация CI и инструкция релиза.{{/unless}}

Ниже описан базовый конвейер комплекта. Проектный обработчик может использовать общие функции
`plan` и `output_plan` из `release.py` и добавлять свои цели, отчет и проверку безопасности отката.
Его параметры и отличия от базового конвейера описываются в runbook выкладки проекта; правила
репетиции и совместимости схемы БД не входят в переносимый план.

Релиз - push в `{{git.releaseBranch}}`. Разработка, Check и ревью идут на `{{git.baseBranch}}`; в релиз уходит только то, что влилось в `{{git.releaseBranch}}`. Шаги релиза держит [`release.py`](../../../.harness/scripts/release/release.py) над интерфейсом поставщика кода; GitHub зовет его из `release.yml`, GitLab - из задач `harness-release-*` дочернего конвейера `.gitlab/ci/release-pipeline.yml`, который запускает задача `harness-release` файла `.gitlab/ci/release.yml`. Релизы идут по одному: у GitHub - группа `concurrency` `release`, у GitLab - группа ресурса `harness-release` задачи `harness-release`, она держит дочерний конвейер до его конца.

**Версия.** Источник истины - git-тег `vX.Y.Z` на выложенном коммите. Задача плана (`plan` у GitHub, `harness-release-plan` у GitLab) считает следующую командой `release.py next`: старший тег по semver плюс одно повышение - `feat` в диапазоне от тега дает minor, иначе patch. Major - решение человека: ручной запуск с `major`. Тег ставит задача тега (`tag`, `harness-release-tag`) командой `forge.py tag` после успешной выкладки; упавший релиз тега не получает, и повтор берет тот же номер. Существующий тег второй раз не создается. Без единого тега план останавливается: первый тег ставит человек на выложенный коммит.

**Выкладка.** У GitHub задание `deploy` зовет [`project-deploy.yml`](../../../.github/workflows/project-deploy.yml). Его создает установщик заготовкой, которая отказывает, пока выкладка не подключена. Дальше файл принадлежит проекту: замена задания своей выкладкой - штатная настройка, а не расхождение с комплектом. Проект, которому выкладывать нечего, заменяет задание шагом, который это объявляет. Удалить заготовку можно только вместе с вызовом из `release.yml` и ссылками этого документа, снятыми правкой проекта: висящий вызов отклоняет `check-pipeline.py`, висящую ссылку - гейт документов. У GitLab выкладку несет задача `harness-release-deploy` файла [`.gitlab/ci/project-deploy.yml`](../../../.gitlab/ci/project-deploy.yml). Установщик пишет его заготовкой, которая зовет `release.py no-deploy` и отказывает; дальше файл принадлежит проекту, и замена `script` - штатная настройка. Задача расширяет `.harness-release-deploy`: уже выпущенный коммит она пропускает, получает переменные плана `RELEASE_MODE`, `RELEASE_TAG`, `RELEASE_VERSION`, `RELEASE_PREVIOUS` и `RELEASE_SHA` и стоит на коммите `RELEASE_SHA`.

**Отчет.** Задача отчета (`report`, `harness-release-report`) идет и после отказа выкладки или тега: `release.py report` печатает итог релиза в сводку прогона и передает его [уведомлениям](#уведомления); исход задачи - исход релиза. Задачи релиза `release.py` берет у трекера по PR диапазона: закрывающие ссылки - строкой задач, а ссылки без закрывающего слова (`Refs`; у Jira - любое упоминание ключа) - отдельной строкой задач, которые ждут приемки после выката; ее видят тело release PR и уведомление. Без модуля `tracker` или при отказе трекера релиз идет дальше: прогон получает предупреждение, а текст называет только PR.

**Ветки.** В `{{git.releaseBranch}}` приходят `release/vX.Y.Z`, срезанная `release.py cut` с `{{git.baseBranch}}`, и хотфикс от `{{git.releaseBranch}}`; шаги - [CONTRIBUTING §11](../../../CONTRIBUTING.md#11-релиз-и-хотфикс). Release PR и PR обратного слияния открывает конвейер, вливает их человек.

**Срез.** {{#if module:forge/gitlab}}Ручной конвейер на `{{git.baseBranch}}` с `HARNESS_RELEASE=cut` запускает задачу `harness-release-cut`{{else}}Ручной запуск `release-cut.yml` на `{{git.baseBranch}}` запускает задание `cut`{{/if}}: оно зовет `release.py cut --push`. Команда создает ветку `release/vX.Y.Z` на голове `{{git.baseBranch}}` через API поставщика кода и открывает черновой PR в `{{git.releaseBranch}}` с напечатанными заголовком и телом. Тело называет PR диапазона по сообщениям коммитов, в том числе коммитов слияния, кроме PR потока релиза - из `release/*`, `back-merge/*`, `{{git.releaseBranch}}` и `{{git.baseBranch}}`. Без `--push` команда показывает состав; номер в имени ветки - прогноз, окончательный тег считает задача плана. Без изменений после последнего тега срез печатает уведомление, и прогон проходит. Повтор возвращает уже открытый PR того же среза. Другой открытый release PR и ветка того же имени на другом коммите - отказ, который называет, что убрать.

**Обратное слияние.** После тега задача обратного слияния (`back-merge` у GitHub, `harness-release-back-merge` у GitLab) зовет `release.py back-merge`. Если выпущенный коммит несет коммиты вне `{{git.baseBranch}}`, считая коммиты слияния (после обычного релиза это коммит, которым release PR вошел в релизную ветку), команда создает ветку `back-merge/vX.Y.Z` на точном SHA выпуска, сверяет ее голову и открывает PR в `{{git.baseBranch}}`: head - эта ветка, а не `{{git.releaseBranch}}`, чтобы удаление head после мержа не удалило `{{git.releaseBranch}}`; отчет называет этот PR. Откат и уже выпущенный коммит обратного слияния не открывают.

**Токен записи.** Задания среза и обратного слияния зовут команды с `--release-token`: ветку и PR создает токен из секрета, который называет настройка `release/tag-flow.token` ([параметры](../agents/harness-parameters.md#release)). Состав среза читает токен задания. Без флага - у агента задач или человека - ветку и PR создают учетные данные поставщика того, кто запускает команду. {{#if module:forge/gitlab}}У GitLab это токен с правом `api`: MR от него запускает конвейер, подходит и `GITLAB_TOKEN`.{{else}}PR от `GITHUB_TOKEN` не запускает Check сам: прогон на нем ждет ручного одобрения. Поэтому секрет держит fine-grained PAT с правами Contents, Pull requests и Workflows на запись. Workflows нужен, потому что создание ref GitHub относит и к этому праву: ветку, коммиты которой меняют `.github/workflows`, токен без него не создаст. Автор PR - учетная запись владельца токена.{{/if}} Пустой секрет роняет задание с именем секрета, недостающее право - с веткой и ответом площадки; оба отказа называют нужные права.

**Ручной запуск и откат.** У GitHub ручной запуск `release.yml` с `major` повышает major, с `version=vX.Y.Z` - выкладывает коммит этого тега без нового тега. У GitLab ручной конвейер на `{{git.releaseBranch}}` несет переменную `HARNESS_RELEASE`: `head` - релиз головы ветки, `major` - релиз с повышением major, `vX.Y.Z` - откат на выпущенную версию.

### Сессия релиза

Релиз по просьбе человека ведет skill `release`: вызов `/release` или просьба словами начинает сессию
релиза командой `pipeline-run.py next release`, и дальше шаги называет она. Без открытого release PR -
срез `release.py cut --push`; пока PR открыт - ожидание Check и мержа; зеленый Check у чернового PR без упавших и незавершенных
проверок, кроме статусов ревью и контекста агента, - `--run ready`, если голова PR - предок базовой ветки, а release PR с коммитами вне среза сессия в Ready
не переводит и заканчивается отказом: его готовность дает ревью. Мерж release PR остается за человеком. После мержа сессия ждет, пока закончится
прогон релиза на коммите слияния в ветке выпуска: исход его заданий - исход релиза, имя задания отчета
роли не играет. Прогон, который не начался за три часа, например из-за фильтра путей `release.yml`, заканчивает
сессию с причиной: очередь группы `concurrency` и долгая выкладка в этот срок укладываются. Ждет команда `--wait --background`: раз в `processes.review.fallback.pollMinutes`
минут она перечитывает PR и проверки и возвращается, когда состояние сменилось.

Сбой правит агент сессии сам, по [CONTRIBUTING §11](../../../CONTRIBUTING.md#11-релиз-и-хотфикс), без
конвейера `issue-dev`, в копии задачи от нужной базы; основной клон сессия релиза не правит:

- релиз прошел - агент читает журналы выкладки и отчета и оставляет в release PR итог: версию, PR
  обратного слияния и задачи, ждущие приемки после выката; PR обратного слияния вливает человек;
- упало задание Check release PR - агент открывает PR правки в базовую ветку и передает его номер
  флагом `--fix`. Защита базовой ветки требует `pipeline/ready`, поэтому правка проходит круг ревью по
  [skill review](../../../.agents/skills/review/SKILL.md): агент запрашивает круг командой
  `--run review` и правит находки, а сессия считает круг идущим от запроса до
  `processes.review.fallback.waitMinutes`, повторяет его `retries` раз и затем останавливается с причиной.
  Влитый тем временем release PR важнее правки: сессия наблюдает его выкат, а правку доводит человек. После мержа правки `--run close` закрывает release PR как неактуальный
  комментарием `comment/close-note` и удаляет ветку, и сессия срезает релиз заново;
- упал прогон релиза после мержа - агент открывает хотфикс PR в ветку выпуска без кругов ревью и
  передает его номер флагом `--fix`; мерж хотфикса запускает релиз, и сессия наблюдает его так же.

Релиз ведет одна сессия: захвата release PR нет, и вторая сессия, начатая тем временем, подхватила бы
тот же PR и свою правку сбоя. Это правило, а не проверка: релиз запускает человек.

{{#if module:forge/gitlab}}Исход релиза - задания последнего конвейера коммита слияния: адаптер GitLab отбора по файлу
конвейера не дает.{{else}}Исход релиза - задания прогона файла из гейта процесса `release-deliver`: прогоны других workflow на
коммите слияния, например стенда по закрытию PR, сессия не считает.{{/if}}

Упал Check PR правки - агент чинит его в той же ветке. Упало после мержа только уведомление или
отчет, а выкладка и тег прошли - хотфикс не нужен, агент называет сбой в итоге и завершает приемку. PR
правки вливает человек, а с флагом `/release --merge agent` - агент сессии: правку в базовую ветку -
после `pipeline/ready` и зеленого Check, хотфикс - способом мержа release PR, когда Check прошел. Номер правки `--fix` принимает из копии
правки на голове PR после зеленого `check-all.py --tree` с данными этого PR: гейты размера PR и связи
с задачей идут и здесь. Наблюдение снимают итог релиза, закрытая без мержа правка и не начавшийся прогон.

## Уведомления

Уведомление собирается один раз и уходит во все каналы, которые ему назначил манифест. Каналы -
расширения модуля `notifications`; рассылает [`notify.sh`](../../../.harness/notify/notify.sh), план
рассылки и контракт адаптера держит [`notify.py`](../../../.harness/notify/notify.py). Вид уведомления
идет в каналы из `notifications.events`, вид без записи - во все включенные каналы. Доставка идет только через адаптер канала: прямой вызов API канала или его action мимо `notify.sh` манифест не выключит.

Текст уведомления пишется обычным Markdown по [шаблону](../agents/templates.md) `notify/<вид>`, а
заголовок - без значков. Разметку своего канала делает адаптер: он переводит жирный текст и ссылки
в разметку канала и ставит значок по `NOTIFY_STATUS` (`release`, `release-failure`, `rollback`,
`rollback-failure`), канал `forge` и итог шага CI публикуют Markdown как есть.

Отказ канала с `onFailure: fatal` роняет шаг, с `warn` остается предупреждением. Канал, который
здесь не адресован - у выката нет своего PR, у канала нет токена, - пропускается, и это не отказ.
У GitHub релиз передает шагу рассылки только секреты, которые называют включенные каналы, под
именами из манифеста; у GitLab рассылка читает переменные CI/CD проекта под теми же именами.
Значения секретов в манифест и журнал не попадают.

Канал `forge` адресует уведомление запросу `NOTIFY_FORGE_CHANGE`. `NOTIFY_FORGE_MARKER` делает запись
обновляемой: повтор правит прежнюю запись с тем же маркером. По умолчанию запись - комментарий, а с
`NOTIFY_FORGE_PLACEMENT=body` - блок между маркером и его закрывающей парой в конце описания запроса;
такому размещению маркер обязателен.

Новый канал - расширение модуля в каталоге и его адаптер `channels/<имя>.sh`, который переводит
Markdown в разметку канала; уведомления при этом не меняются, а сверка комплекта отклоняет канал без адаптера и адаптер без расширения.

## Переключатели раннеров

Пул раннеров задания задает модуль `runners` манифеста ([параметры](../agents/harness-parameters.md#runners)):
расширение `github-actions` - метки `runs-on`, расширение `gitlab-runner` - теги `tags`. Установщик
пишет пул вида задания в файлы CI. Без модуля `runners` задания идут на `ubuntu-latest` у GitHub и
на раннерах без тегов у GitLab.

| Вид | GitHub Actions | GitLab CI |
| --- | --- | --- |
| `check` | `check.yml`, `link-branch.yml`, `review-inputs.yml` | `harness-check`, `harness-event` |
| `review` | `code-review.yml` | задачи `.gitlab/ci/review-round.yml`, `harness-invalidate` |
| `agent` | `issue-agent.yml` | `harness-agent-duplicate`, `harness-agent` |
| `triage` | `alert-triage.yml` | - |
| `release` | `release.yml`, `release-cut.yml`, `project-deploy.yml`, `close-issues.yml` | задачи `.gitlab/ci/release-pipeline.yml`, `.gitlab/ci/project-deploy.yml`, `harness-release-cut`, `harness-close-issues` |

Модель и усилие исполнителя переменными CI не переопределяются: модель задает комплект по
провайдеру модуля `ci-agent`, усилие - по процессу ([исполнитель сессии](#исполнитель-сессии-агента)).

Срок задания задает `timeout-minutes` соответствующего workflow. Срок сессии внутри задания
задает константа `SESSION_MINUTES` скрипта; у `pipeline-run.py` - флаг `--timeout-minutes`.
Запас уходит на публикацию вердикта и выжимку журнала.
Таймаут задания в файле CI меняется вместе с таймаутом сессии: задание короче сессии площадка
оборвет до итоговой записи, а время сверх срока сессия не использует.

## Исполнитель сессии агента

Исполнителя всех сессий агента в CI задает расширение модуля `ci-agent`: `claude-code`, `codex` или
`cursor`. Установщик пишет его в файлы CI переменной `AGENT_PROVIDER`. Модель и перевод уровня усилия
в параметр провайдера задает комплект (`KINDS` в `agent_provider.py`). Поле `runner` процесса или
промпта называет исполнителя, по нему методология задает усилие (`efforts`), а `agents.tools.<id>` в
`project/manifest.json` - инструменты агента задач и разбора алертов.

Сессию запускает [`agent-run.py`](../../../.harness/scripts/agent/agent-run.py):

- `--mode review` - только чтение: токенов поставщика кода, трекера и CI в окружении сессии нет,
  итог - JSON по [`review.schema.json`](../../../.harness/scripts/review/review.schema.json);
- `--mode agent` - правка, коммит и push: окружение получает заголовок токена поставщика кода для
  `git fetch` и `git push`. До запуска модели режим выделяет ветку и worktree задачи по `--issue`,
  `--task-type` с `--task-key`, `--change` и `--base`; вне выделенной копии без них запуск отказывает. `--detached` запускает сессию в
  `--workdir` без выделения: так идут агентские стадии конвейеров, кроме `run change` с записью задачи.
  Хуки не требуют записи задачи от такой сессии. `--read-only-fallback` при отказе выделения
  продолжает диагностику без копии задачи в режиме `reply`: окружение пересобирается без авторских
  токенов, инструменты записи запрещены, Codex получает песочницу `read-only`. Такое ограничение
  действует и без установленных git-хуков;
- `--mode reply` - только чтение без авторской ветки: правка файлов запрещена, итоговый текст
  публикует `agent-event.py` после проверки текста.

Журнал `--log` - родной поток JSONL исполнителя, последней строкой - итоговая запись
`{"type": "result", ...}`. Код возврата 0 только у успешной записи. CLI ставит
[`ensure-agent-cli.sh`](../../../.harness/provisioning/scripts/ensure-agent-cli.sh) версией из
`agents.cli` манифеста проекта: `claudeVersion`, `codexVersion`, `cursorVersion`. На раннере без
npm скрипт сначала ставит Node: версию `.node-version` корня, без файла - `agents.cli.nodeVersion`.

Секреты исполнителей и токены записи агента - [справочник параметров](../agents/harness-parameters.md#конвейер-issue-dev).
Вход `codex` - ChatGPT в `CODEX_HOME/auth.json` раннера (по умолчанию `~/.codex`; вход -
`codex login --device-auth` на машине раннера под его пользователем) или секрет `CODEX_API_KEY`; при
обоих берется вход ChatGPT. Codex с входом ChatGPT идет на своем раннере с томом `CODEX_HOME`: его
метки или теги задает модуль `runners`. Выбор провайдера без авторизации другим исполнителем не подменяется:
круг не стартует, и это видно на PR.

Серверы MCP стендов модуля `stands/mcp-stand` установщик пишет агентам разработки: `.mcp.json` у
Claude Code, `.cursor/mcp.json` у Cursor, `.codex/config.toml` у Codex; вход агента разработки -
OAuth экземпляра ([mcp-stand](../../../.harness/mcp-stand/README.md)). Сессия CI получает сервер
стенда файлом `--mcp-config` с токеном из переменной CI, которую называет поле `token` записи
стенда.
{{#if module:forge/github}}
Секреты, которые называют настройки манифеста (`{"secret": ИМЯ}`, `{"env": ИМЯ}`, поля

## События GitLab

Статусы ревью и готовности записываются в текущий `head_pipeline` конкретного MR с явными
`pipeline_id` и `ref`. Чтение использует тот же pipeline; новые посторонние pipeline на этом SHA
не заменяют его. Нужен исходный MR pipeline в том же проекте и API с фильтром статусов по
`pipeline_id`; возможности сервера проверяет адаптер. Пока MR pipeline не создан, круг отказывает
до его появления. Merged-results, fork, устаревшая голова и неоднозначная принадлежность не дают
подтверждения. Успешный рабочий pipeline базовой ветки не заменяет результаты MR pipeline.

У GitLab события MR и комментариев приходят одним вебхуком проекта (Merge request events и
Comments) на адрес триггера конвейера
`<адрес API>/projects/<id>/ref/<git.baseBranch>/trigger/pipeline?token=<токен>`. Вебхук и
токен триггера с описанием `harness-events` заводит
[`forge-setup.py`](../../../.harness/scripts/release/forge-setup.py) (`forge.ensure_event_hook()`), когда у
`GITLAB_TOKEN` есть права Maintainer; без них он печатает шаги владельцу.

Доверенная оснастка GitLab - защищенная ветка проекта, а не ветка по умолчанию площадки: они
могут различаться, как `master` и база разработки `develop`. Конвейер вебхука идет на `git.baseBranch`
с источником `trigger`; рабочий конвейер события запроса - круг, инвалидация и агент на MR - идет на
целевой ветке MR, прочие - на `git.baseBranch`. Задача `harness-event`
(`agent-event.py route`) читает событие и запускает рабочий конвейер через API:

- добавленная метка `processes.review.label`, в том числе у MR, открытого с ней, - конвейер круга с
  `HARNESS_REVIEW=<iid>`;
- обращение к агенту от участника проекта - конвейер агента с `HARNESS_AGENT=<цель>-<номер>`;
- прочее событие - строка в журнале.

Рабочий конвейер несет событие JSON в `HARNESS_EVENT` и его id в `HARNESS_EVENT_ID`. Id события:
заметка - `note:<id заметки>`, правка меток и открытие MR - `mr:<iid>:<action>:<updated_at>`, конец круга -
`round:<iid>:<id конвейера круга>`; повторная доставка вебхука и повтор задачи несут тот же id.
Перед созданием адаптер GitLab ищет конвейер с этим `HARNESS_EVENT_ID` среди всех конвейеров
источника `api` учетной записи `GITLAB_TOKEN` на ветке своего запуска, созданных после события; у конца круга и запроса разбора
алерта - новее их конвейера. Поиск читает до 1000 конвейеров; больше или у события нет ни времени, ни
конвейера - запуск отклоняется. Найденный конвейер второй раз не создается: журнал называет его адрес. Тот же поиск идет,
когда ответ на создание потерян - сетевой отказ или код 5xx. Задачи `harness-event` идут без общей
группы ресурса. Одновременные доставки одного события поиск не разводит и поднимают двойника: первым
считается конвейер с меньшим номером, а двойник - подготовка и страж круга, поиск двойника агента,
конец круга - находит его по тому же `HARNESS_EVENT_ID` и выходит без записей. Дочерний конвейер круга ищет по номеру
и времени создания родителя (`HARNESS_EVENT_PIPELINE`, `HARNESS_EVENT_PIPELINE_AT`), а итог пишет в план
круга: страж и проходы читают его оттуда.

Конвейер с `HARNESS_REVIEW` идет одной задачей `harness-review` ([`review.yml`](../../../.gitlab/ci/review.yml)):
она поднимает дочерний конвейер круга [`review-round.yml`](../../../.gitlab/ci/review-round.yml) с
переменными своего конвейера и держит группу ресурса `harness-review-<iid>` до конца дочернего
конвейера. Круги одного MR идут по одному: следующий круг ждет конца идущего. Задания круга, его
прогон в `forge.run_jobs()` и адрес статусов `review/<проход>` - дочерний конвейер.

Конец круга ревью будит агента задачей `review-after-round` дочернего конвейера круга
(`agent-event.py after-round`): она поднимает конвейер агента на MR, который ведет конвейер.
Ручной релиз и ручной запуск гейта идут источником `web`.

Конвейеры событий и работ комплекта несут переменную `HARNESS_PIPELINE`: конвейеры API ставит
`start_pipeline`, конвейеры вебхука - адрес триггера. Свои задания и `workflow` проекта лежат в файлах `include` с правилом
`if: $HARNESS_PIPELINE == null` и в эти конвейеры не попадают. `check-pipeline.py` отклоняет в
`.gitlab-ci.yml` любой ключ вне блока комплекта и `include` проекта без этого правила. Элементы проекта
продолжают список `include` после блока комплекта:

```yaml
  - local: .gitlab/ci/project.yml
    rules:
      - if: $HARNESS_PIPELINE == null
```

`workflow` комплекта в `harness.yml` ведет конвейер с `HARNESS_PIPELINE` и ручной релиз с `HARNESS_RELEASE` с
`auto_cancel: on_new_commit: none`: работа комплекта ждет группу ресурса или раннер, неначатое задание
GitLab считает прерываемым, и без правила новый коммит снимал бы ожидающий конвейер. Дочерние конвейеры
круга и ручного релиза несут такой же свой `workflow`: правило родителя на них не распространяется; у
круга его сверяет `check-pipeline.py`. Прочие конвейеры идут как без `workflow`. Свой `workflow:` проекта в
файле `include` перекрывает `workflow` комплекта, поэтому его `rules` начинаются с правил комплекта из
`harness.yml` в том же порядке, иначе `check-pipeline.py` отказывает. Правило
`workflow:rules:auto_cancel` - GitLab 16.10 и новее. Снятый или пропущенный конвейер событие не исполнил:
поиск поднятого конвейера и двойника его не засчитывает.

Рабочие конвейеры несут переменные `HARNESS_*`: роль владельца `GITLAB_TOKEN` входит в "Minimum role
to use pipeline variables" (Settings => CI/CD => Variables). Учетные записи разведены окружением
переменных ([параметры](../agents/harness-parameters.md)): вердикты, результаты и метки круга пишет только
`GITLAB_TOKEN` окружения `harness` (шаблон `.harness-pipeline-account`), поиск двойника события агента `harness-agent-duplicate` - в окружении `harness`, сессия агента
`harness-agent` - в окружении `harness-agent` с `AGENT_GITLAB_TOKEN` (`.harness-agent-account`), задания проходов
круга, которые разбирают код запроса, - с `GITLAB_READ_TOKEN`; `harness-check` токена не берет. Задания проходов идут в окружении `review-read`: секрет трекера в окружении `harness` несет токен конвейера, в `harness-agent` - отдельный токен агента, а в `review-read` - токен только для чтения. От прохода страж получает только файлы его итога и этапа отказа, без dotenv. Токены стендов видят окружения `harness*`, токены исполнителей - защищенные маскированные переменные;
базовая ветка и ветка релиза - защищенные. Минимальная роль переменных конвейера - `maintainer` или
`owner`: иначе Developer, включая агента, поднимет конвейер комплекта с подложным `HARNESS_EVENT`.
`forge-setup.py` сверяет эту роль, защиту обеих веток и Pipelines must succeed.

## Круг ревью

План без выполнения: `./.harness/hooks/python.cmd .harness/scripts/pipeline/pipeline-run.py plan change` (для релиза -
`plan release`). JSON раскрывает ссылки шагов, сортирует зависимости и показывает определения
процессов вместе с исполнителями, гейтами, готовностью, передачей мержа и параметрами ревью.
Задача, PR, учетные данные и локальный журнал для этой команды не нужны.

`check-pipeline.py` проверяет раздел `doc` каждого шага агента и отсутствие копий значений
манифеста в файлах, которые называют поля `copies` записей реестра правил - `methodology.json` и раздела `rules.own` манифеста:
тексты процесса, подсказки и строковые литералы кода. Метки и названия условий готовности ищутся
как литералы. Способ слияния, бюджеты кругов и переходов, повторы и минуты запасного круга ищутся
только в контексте своего поля из `.harness/messages.env`: слов поля, id прохода или шага, у
параметров запасного круга - слова этого круга. Общее слово или число вне такого контекста копией
не считается. Прежние номера шагов - `3c` и `4a-4d` рядом с `issue-dev` или `SKILL.md` - тоже
отклоняются. Шаблоны комплекта проверяются тем же
правилом, когда они есть в дереве; совпавший с установленным файлом побайтно шаблон не читается
второй раз, только если установленный файл вошел в охват и факты обоих деревьев совпадают. Имена полей в форме
`processes.merge.steps[merge].method` и заголовки по id шага распознаются как ссылки. Вывод плана не
повторяется в текстах.

Выражения workflow манифест не читают, поэтому литерал метки в них - копия под сверкой: в workflow
`processes.review.workflow` каждое `label.name == '<метка>'` называет метку методологии, а
`display_title` прогона ревью в любом workflow - `processes.review.label`. Способ слияния
`git-pull-request-merge-method` в `.codex/config.toml` совпадает со способом процесса `merge`.

### Проходы ревью

Планки и инструкции каждого прохода задают поля `processes.review.steps[].doc` и `prompt`.
Состав и параметры проходов печатает план выбранной композиции.

Конвейер круга (`processes.review.workflow` методологии) зовет только подкоманды
[`review-round.py`](../../../.harness/scripts/review/review-round.py): `prepare`, `pass <id>`, `guard` и у
GitLab `yielded`, который отвечает, уступил ли круг и нужен ли аудит.
Бюджет кругов, маркер вердикта, наборы инструментов и путь промпта каждого прохода объявлены
записью `processes.review` в [`.harness/methodology.json`](../../../.harness/methodology.json),
а усилие - ссылкой `runner` на `efforts` методологии; копий
в файлах CI нет, сверку держит [`check-pipeline.py`](../../../.harness/scripts/check/check-pipeline.py).

Триггер круга - метка `processes.review.label` на PR, стадию запуска задает план выбранной композиции
([issue-dev](../../../.agents/skills/issue-dev/SKILL.md)); человек ставит метку сам или командой `forge.py request-review <N>`.
Метка - кнопка, а не состояние: `prepare` снимает ее и метку `processes.review.failedLabel` первым шагом.

Задачи круга идут оснасткой базовой ветки: у GitHub каждая задача выкладывает SHA базы события, у
GitLab конвейер круга и инвалидации идет на целевой ветке MR, а публикатор (`forge.publisher()`)
отказывает, если ветка конвейера не целевая или не защищенная, а коммит конвейера - не база круга и
не ее предок: база уходит вперед, пока конвейер ждет раннер, и такой конвейер исполняет более раннюю
оснастку той же защищенной ветки. Голову PR проход получает данными: ссылку
`Change.fetch_ref` (`refs/pull/N/head`, `refs/merge-requests/N/head`) он выкладывает токеном
поставщика кода в отдельный каталог, сверяет с головой плана круга и строит дифф `pr.diff` от базы
слияния с веткой базы. Рядом [`review_inputs.py`](../../../.harness/scripts/review/review_inputs.py) кладет
карты круга; их состав называет общий промпт [`review/common.md`](../../../.harness/prompts/review/common.md),
объем ограничивает `processes.review.maps`. Проходу с `context: true` доступен полный `task-context.md`: заголовок и тело
PR, человеческие комментарии, построчные обсуждения и ответы, итоги ревью, связанные через `Refs`
или `Closes` задачи с комментариями. `context.md` содержит превью, ограниченное
`processes.review.contextChars`.

Сессия прохода - `agent-run.py --mode review` в каталоге головы. Наборы инструментов - ключи
`processes.review.allowedTools` и `processes.review.disallowedTools` методологии; набор, который открывает оболочку `Bash(...)` или
инструменты MCP, `check-pipeline.py` отклоняет: проход читает дерево и каталог данных, а оболочка пишет файлы,
git тоже (`--output`). Ответ сессии - JSON по
[`review.schema.json`](../../../.harness/scripts/review/review.schema.json): `verdict` (`approve`, `changes`
или `blocked`), `body` и массив построчных находок `comments` с полями `path`, `line`, `side` и
`body`; `side: LEFT` привязывает находку к удаленной строке базы. `blocked`, ответ не по схеме и тело
длиннее `processes.review.bodyChars` или не по-русски вердиктом не считаются: публикатор ставит
результату `error`.

Прочитанное модель не называет: `agent-run.py` снимает его с журнала инструментов сессии. Чтение -
путь вызова Read, Grep, Glob у Claude Code и Cursor, а у Codex и оболочки - путь из команды чтения
(`cat`, `sed`, `head`, `rg`, `grep`, `ls` и подобных), который называет существующий файл дерева
головы. Чтение `input/pr.diff` и карт чтением файла не считается. С `--inputs` (каталог входов круга)
прочитанное сверяется с файлами диффа без удаленных, сгенерированных, вендорных, файлов комплекта и
`policies.size.exclude` - тем же отбором, что у размера PR (у копии payload засчитывается и
установленная копия), и с местами `impact.md`.
Итоговая запись несет `coverage`: источник журнала, прочитанное, ожидаемое и непрочитанное. Полный
разбор печатается в журнал прогона и уходит в артефакт `review-result-<проход>` вместе с журналом сессии
прохода (`<проход>.result.jsonl.session.jsonl`: рассуждения и вызовы инструментов), в комментарий не
идет. Сессия, в журнале которой нет ни одного чтения файла дерева, - отказ: результат `error`. Тело
вердикта собирает шаблон [`review/verdict`](../../../.harness/templates/review/verdict.md), требование к
телу - раздел "Ответ" [промпта прохода](../../../.harness/prompts/review/common.md). Строки `Workflow` и
`SHA` и затраты сессии свернуты в раскрываемый блок "Статистика сессии" после суждения: `Workflow`
ведет на прогон с шагами и артефактами проходов (у GitLab - конвейер с заданиями проходов).
Непрочитанное в тело не идет: его список лежит в артефакте результата. Непрочитанный файл апрув сам
по себе не отклоняет. Проход и слово решения лежат в маркере данных `<!-- harness-text: ... -->`:
читатели вердикта берут их из него, а у вердикта старого формата - из первой строки.

Вердикт публикует не модель, а [`review_verdict.py`](../../../.harness/scripts/review/review_verdict.py) по
строке `VERDICT:` итоговой записи: ревью учетной записи круга на голове с находками комментариями к
строкам и статус коммита `review/<проход>`. У GitLab ревью - комментарий вердикта; отказ прохода
снимает одобрение MR. Само одобрение учетной записи круга GitLab ставит только вместе с успешным
`pipeline/ready` на той же голове и снимает при новом круге, отказе готовности и правке входов:
правило одобрения этой учетной записи делает его условием слияния. Автор MR, совпавший с учетной
записью круга, круг не получает. Находку, позицию которой площадка отвергла, публикатор пишет в тело строкой
`path:line - текст`. Учетная запись круга - учетная запись токена прогона (`forge.login()`).

У GitHub задание прохода `pass <id>` ведет сессию и публикует вердикт. У GitLab задание прохода -
только сессия: `pass <id> --defer-publish` кладет итоговую запись сессии файлом
`.review-round/<id>.result.jsonl`, он уходит артефактом задания. Вердикты круга публикует
`review-guard` (`guard --publish-deferred`) из этих файлов, поднятому проходу без файла он ставит
результат `error` с причиной; вердикты GitLab появляются, когда закончилась самая долгая сессия
круга. `review-prepare` и `review-guard` держат группу ресурса `harness-review-<iid>-publish`:
ожидание и пропуск подготовки, вердикты со всеми повторами записи, метка и комментарий стража одного
MR идут по одному, в том числе при повторе отдельного задания. `check-pipeline.py` сверяет, что
публикацию откладывают все проходы или ни один; с отложенными - что страж зовется с
`--publish-deferred`, а подготовка и страж держат группу `harness-review-$HARNESS_REVIEW-publish`;
без отложенных - что страж зовется без `--publish-deferred`.

Проход, которому в диффе нечего разбирать, круг не поднимает: отбор по прозе и исключения держит [`review_policy.py`](../../../.harness/scripts/review/review_policy.py); его таблицу сценариев проверяет комплект harness до выпуска.

### Отказ круга виден на PR

Страж круга - `verdict-guard` у GitHub, `review-guard` у GitLab (`review-round.py guard`) - ждет подготовку и все проходы. Результат `review/<проход>` несет адрес прогона своего круга: страж засчитывает поднятый проход только результатом этого круга и вердиктом этого круга на запросе - результат пишется до тела вердикта, и тело, которое до запроса не дошло, круг не засчитывает. У GitLab заметка вердикта ложится после реплик к строкам, а у вердикта `changes` - и после снятия одобрения; одобряющий вердикт одобрения не ставит; реплика несет скрытую строку круга, прохода и отпечатка своего пути, строки и текста, и повтор записи реплику учетной записи круга с этой строкой второй раз не кладет. В тексте вердикта и реплик у GitLab строка с косой черты в начале получает обратную косую: быстрой командой учетной записи круга она не исполняется. Вердикт поверх результата более нового круга не публикуется. Сверяются результаты на голове круга и на текущей голове запроса: круг новой головы вытесняет круг прежней. У GitHub проход сверяет владельца результата при старте и перед публикацией. Подготовка и страж сверяют круг до первой записи, у GitLab под группой ресурса публикации: круг, чей результат прохода на голове уже оставил более новый круг, не пишет ни меток, ни результатов, ни вердиктов, ни комментария - повтор его задания, подготовки тоже, владения ему не возвращает; такая подготовка не поднимает проходы, а страж и сессия выходят с нулем. Подготовка ставит каждому результату на голове адрес своего прогона, а незаписанный результат роняет ее; идущий статус GitLab с чужим адресом она снимает и заводит заново. Непрочитанные результаты на голове и непрочитанная голова запроса право на запись не подтверждают: проход не публикует вердикт, страж не пишет ни вердиктов, ни метки, ни комментария и выходит с ошибкой. Вердикт несет скрытую строку `<!-- harness-round: <адрес круга> <проход> -->`: повтор подготовки, прохода или стража того же круга второй вердикт прохода на голову не кладет, а результат `review/<проход>` ставит по решению лежащего вердикта; проход GitHub, который публикует сам, при повторе и сессию не ведет. Своим круг считает только вердикт учетной записи круга с этой строкой, непрочитанный список ревью публикацию останавливает. Очередь запросов круга, готовности и инвалидации одного PR у GitHub - [подтверждение стадий в CI](#подтверждение-стадий-в-ci). Если подготовка или проход отказали, были сняты или не оставили вердикт, страж вешает метку `processes.review.failedLabel` и оставляет один комментарий на пару "голова и причина". Запрос правок - завершенный проход: его `failure` блокирует Ready, но не означает отсутствие вердикта. Инвариант держит [`check-review-label.py`](../../../.harness/scripts/check/check-review-label.py). Повторный круг запрашивает шаг review [issue-dev](../../../.agents/skills/issue-dev/SKILL.md).

### Бюджет кругов

Бюджеты проходов задает `processes.review.steps[].budget` методологии. Бюджет считает `prepare` по вердиктам этого PR на текущих голове, базе, правилах круга и постановке - ревью учетной записи круга и комментариям участников проекта, у которых есть проход и слово решения: у вердикта - в маркере данных `review/verdict`, у вердикта старого формата и заметки участника без маркера - в первой строке. Проход, выбравший бюджет, не стартует; проход, который держит блокировку, идет и сверх бюджета. Порог `processes.review.stallRounds` называет число кругов подряд с запросом правок, после которого человек получает предупреждение на PR.

**Апрув прохода постоянен.** Первый круг после чернового PR поднимает все проходы, следующий - только
проходы без апрува. Новый коммит, подлив базы, смена правил круга и постановки апрув не снимают:
план переносит его статусом `review/<проход>` на текущую голову. Исключение - коммиты после апрува
всех проходов, которые не укладываются в [правку после апрува](#правка-после-апрува): тогда круг
снова поднимает все проходы, и они разбирают дифф от одобренной головы. Если апрув есть у всех проходов,
а статусов на голове нет, круг запрашивается ради переноса и проходы не исполняет;
`pipeline-run.py run` запрашивает его сам. Запрос правок держит проход до
нового результата. Исчерпанный бюджет и отказ среды не открывают Ready.

### Правка после апрува

Порядок задачи: код, упрощение, ревью, вердикты; после апрува всех проходов - Check в CI. Шаг `gates`
сессии ждет Check (`check`, у GitLab `harness-check`) на одобренной голове, а не запускает `check-all.py`
локально; рядом он гоняет только гейты данных PR (`check-all.py --change`). Упавший Check агент чинит
коммитом после апрува. Правило считается для каждого прохода от головы его апрува: правка не
снимает этот апрув и не запускает новый круг, только если ее дифф от одобренной головы меньше
`policies.postApprovalFix.lines` строк (по умолчанию 50) и трогает только файлы, которые назвали
упавшие гейты в журнале Check этой головы, или файлы тестов и сборки (`policies.postApprovalFix.build`).
Иначе проход идет в новый круг и разбирает дифф от своей одобренной головы. Апрув, выданный новой
голове одним проходом, апрувы других проходов не продлевает.

В дифф правки входят только коммиты ветки (`--first-parent`): слияние базы без ручного разрешения
конфликта правкой не считается, а слияние с ручным разрешением и переписанная история, где одобренная
голова уже не предок головы, требуют нового круга. Названные файлы берутся только из журнала Check
одобренной головы, из разделов гейтов, которые итог `check-all.py` отметил `FAIL` или `ERR`; без итога
журнал читается целиком. Путь совпадает целиком, с номером строки или как конец абсолютного пути.
Журналы промежуточных голов правки файлов не добавляют. Дифф или журнал, которые не прочитаны, правку
не принимают, и проход идет в новый круг. Решение одно у плана круга в CI (`review_policy.route`) и у
сессии ([`post_approval.py`](../../../.harness/scripts/review/post_approval.py)); плану в CI, где
клонирована только база, недостающие коммиты PR правило дозагружает по `fetch_ref` запроса.

Если Check на голове не идет (задания нет, оно пропущено или под его именем пришел статус),
шаг `gates-missing` ждет его и после нескольких одинаковых ответов сообщает человеку. Локальный
`check-all.py` остается по явному решению разработчика.
Принятые правки конвейер называет в описании PR и в теле коммита слияния: шаблоны `change/description`
и `commit/message` с `--change` перечисляют их частью `parts/change-fixes`.

### Реестр решенного

`prepare` раскладывает прошлые вердикты по проходам и отдает каждому его собственные подстановкой `${ReviewDecided}`; проходу с `threads: true` он дописывает закрытые построчные треды учетной записи круга цитатой. Закрытая находка не повторяется без нового доказательства в текущем коде. Реестр раздельный. Длина записи - `processes.review.decidedChars`. История одобрения не дает.

### Локальный круг ревью

Когда удаленный круг не состоялся или человек поручил локальные круги, [`review-local.py`](../../../.harness/scripts/review/review-local.py) готовит пакет: закрепленные деревья PR и базы, промпты проходов и `round.json`. Независимые агенты провайдера авторской сессии разбирают пакет без истории разработки, ответы собирает `--collect`. Каталог круга всегда лежит в `.sessions/review/<PR>/` основного клона, где его видит ведущая сессия из любой рабочей копии; `--work` вне этого каталога скрипт отклоняет. Исключения два: скрипт базы при делегировании, запущенный из `control/.review-admin` этого каталога круга в служебном репозитории `control`, и пакет первой установки `ah.py review`, который лежит вне проекта. Сбор с `--publish`, принявший все ответы, удаляет деревья круга; сбор без `--publish`, недостающий ответ или `--keep` оставляют их для повторного сбора. Делегированный сбор скрипт базы ведет с `--keep`, а деревья после публикации удаляет внешний вызов. Выключенный модуль `review` ставит локальный круг сразу: проходы идут параллельными агентами авторской сессии. Модель проходов - модель комплекта для провайдера сессии (`KINDS` в `agent_provider.py`); для неизвестного провайдера проходы идут моделью сессии. С `--execute` скрипт запускает сессии через `agent-run.py --mode review`: исполнитель - `AGENT_PROVIDER`, иначе аргумент `--provider`, иначе провайдер авторской сессии, иначе агент разработки (модуль `agents`). Маркер вердикта называет исполнителя, который разбирал PR.

База пакета - снимок базы PR у поставщика кода (`base_sha`), а не свежая ветка в origin: база, ушедшая
вперед, круг не роняет. `--base` должен указывать на тот же снимок, иначе скрипт откажет. Исключение -
круг, переданный раннеру базы с другой структурой правил: он сверяет снимок с концом ветки базы в
origin и при ушедшей вперед базе отказывает.

Если база использует другую структуру правил, пакет готовит и собирает ее собственный раннер в изолированной копии на голове PR. Он берет инструменты и настройки из закрепленного Git-снимка базы; `--execute` доступен только при поддержке этого режима раннером базы. Для `--collect` сохрани тот же `--work`, исходный файл `--context` и неподвижные ветки PR и базы в origin.

```bash
./.harness/hooks/python.cmd .harness/scripts/review/review-local.py --pr <номер> --reason <ключ> --provider <провайдер> --context TestResults/review-context.md
./.harness/hooks/python.cmd .harness/scripts/review/review-local.py --pr <номер> --collect --work <каталог круга из вывода подготовки>
./.harness/hooks/python.cmd .harness/scripts/review/review-local.py --pr <номер> --collect --work <каталог круга из вывода подготовки> --publish
./.harness/hooks/python.cmd .harness/scripts/review/review-local.py --pr <номер> --reason <ключ> --execute --publish --context TestResults/review-context.md
```

`--reason` - ключ причины из записи `LocalReason` реестра
[`variables.json`](../../../.harness/templates/variables.json): в строку `Способ запуска` вердикта после
метки локального круга скрипт ставит его название, неизвестный ключ отклоняет. Свободного текста причины нет: технические
подробности отказа удаленного круга шлюз дает агенту в сообщении шага, а не в вердикт.

`--publish` публикует каждый собранный вердикт комментарием по тому же шаблону со строкой `SHA:`
проверенной головы и ставит метку круга. Хэш постановки, провайдер круга и ключ причины круга лежат в
маркере данных. Ready по локальным кругам решает ключ причины `direct`: вердикт без ключа, в том числе
опубликованный до его появления, Ready не дает: такой проход заново поднимает человек командой
`review-local.py --pr <номер> --reason direct --pass <проход>`.

Пакет несет карты `removed.md` и `impact.md` в каталоге `input` рабочего каталога. У подготовленного
круга журнала раннера нет: рядом с ответом кладется журнал сессии агента прохода `<проход>.journal.jsonl`
(путь `journal` в `round.json`) - транскрипт в формате провайдера: поток или транскрипт Claude Code,
`codex exec --json`, исходный журнал Codex Desktop, поток Cursor. В журнале Desktop чтения берутся
из завершенных успешных команд с учетом их рабочей папки; неоднозначная команда чтением не считается.
`--collect` разбирает журнал и ответ тем же кодом, что и `agent-run.py`: тело вердикта длиннее
`processes.review.bodyChars` или не по-русски разбор отклоняет; тело аудита процесса эти проверки не
проходит. Ответ без журнала или с журналом без чтения файла дерева сбор не принимает; чтение копии
базы `.review-base/` чтением дерева не считается. С `--execute` журнал пишет `agent-run.py`. Разбор прочитанного печатается
в вывод `review-local.py` и ложится файлом `<проход>.coverage.json` в рабочий каталог круга;
в тело вердикта непрочитанное не идет. Строка `Workflow` локального круга называет его рабочий каталог
в `.sessions/review/<PR>/` основного клона: журналы, разбор прочитанного и ответы проходов
с построчными находками лежат там, на машине, где шел круг, до уборки задачи после мержа, а в CI - адрес
прогона. Построчные находки JSON-ответа идут в тело вердикта локального круга списком "путь:строка -
текст", как у удаленного круга при отказе треда; у текстового ответа без JSON их нет, а
запрос правок без текста суждения сбор не принимает; затраты сессии
считаются по итоговой записи `agent-run.py`, а у подготовленного круга - по журналу агента прохода:
токены несут транскрипт Claude Code, поток `codex exec --json`, журнал Codex Desktop (`token_count`)
и итог потока Cursor. Модель и уровень рассуждения строки "Модель:" вердикт CI и круг `--execute` берут
из запуска `agent-run.py`, подготовленный круг - из журнала: `message.model` и `effort` у Claude Code,
`turn_context` у Codex, `system/init` у Cursor. Модель и уровень пишутся так, как их отдает агент. Чего источник не несет, той
строки нет. Маркер данных вердикта несет те же токены, время в секундах, модель и `agentId` журнала
подготовленного прохода: по ним суммируются затраты ревью.
Где GraphQL GitHub отвечает отказом 403, который называет маршруты `ccr` (облачная сессия Claude Code), закрываемые задачи PR берутся только из ключевых слов тела с предупреждением: связи панели Development не читаются, учетная запись читается через REST `GET /user`, треды и снятие черновика идут через REST и маршруты `ccr`. Любой другой отказ GraphQL останавливает операцию.

Отличия от удаленного круга: без `--pass` скрипт поднимает все проходы, с `--pass` - только названные; вердикт живет комментарием с пометкой круга, статусов `review/<проход>` нет, реестра решенного нет; разрешенные инструменты сессии - `processes.review.fallback.allowedTools`, запреты - общие `processes.review.disallowedTools`, а свой список запретов в `fallback` отклоняет `check-agent-permissions.py`. Апрув локального круга проход для `pipeline-run.py` не закрывает, запрос правок держит. Гейт
сессии засчитывает и апрув локального круга, по тому же правилу постоянства, и передает
`--pass` только для проходов без апрува. PR с таким кругом несет метку `processes.review.fallback.label`. Величины - `check-pipeline.py --emit-fallback`, порядок - [skill review](../../../.agents/skills/review/SKILL.md), готовность - [issue-dev, раздел ready](../../../.agents/skills/issue-dev/SKILL.md#ready).

Локальные комментарии, метка и журнал круга, которым заменен несостоявшийся удаленный, не разрешают
автоматический Ready: нужны текущие доверенные результаты проходов и защищенный `pipeline/ready`.
Исключение задает человек: вход в конвейер с `--review local`, настройка проекта `agents.review` со
значением `local` или выключенный модуль `review` делают локальные круги основными. Тогда круг идет с
причиной "человек поручил только локальные круги", и после одобрения всех проходов команда
`pipeline-run.py next change --run ready` переводит PR в Ready. Она выполняется только на своем шаге и
сверяет последний коммит PR, закрытые обсуждения, зеленое задание обязательной проверки Check (статуса с
тем же именем недостаточно) и остальные проверки головы: упавшая или идущая дает отказ, и команду
повторяют, когда проверки закончатся. Вход с `--rounds 0` снимает круги: та же команда с той же сверкой
идет без вердиктов.
Команда передачи мержа `--run handoff` повторяет ту же сверку на голове, которую вливают: коммит после
Ready метку мержа без зеленых проверок не получает, а коммит после метки снова ведет к передаче со
сверкой, а не к мержу; мерж идет с ожидаемой головой, которую сверила передача. При ревью в CI она требует и успешный статус
`pipeline/ready` на этой голове, а статусы ревью в сверку проверок входят. Режим освобождает от вердиктов ревью из CI и статуса
`pipeline/ready`, но не от Check и остальных проверок; вердикт
запасного круга и в этом режиме Ready не дает. Защиту базы режим и вход с `--rounds 0` не снимают: на базу, защита которой
требует статусы ревью из CI, PR дойдет до Ready, но мерж она остановит. Поэтому на такую базу режим
рассчитан вместе с интеграционной веткой `--base` или в проекте, где защита статусов ревью не требует. PR, все проходы которого одобрены в CI, идет в Ready
обычным путем. Недоступность публикатора блокирует
продолжение; отключение модуля ревью не снимает обязательный процесс композиции.

### Закрытие обсуждений ревью

Замечание закрывает автор PR парой действий: ответ в треде плюс resolve. Запрос тредов и мутации собраны в [`pr-threads.py`](../../../.harness/scripts/review/pr-threads.py) (`list`, `reply --resolve`, `resolve`). У GitHub в сессии с сервером MCP github те же действия делают `pull_request_read`, `add_reply_to_pull_request_comment` и `resolve_review_thread`.

## Агент задач

### Кто раздает задачи

Задачу отдает человек своей сессии агента, а не конвейер: создание issue сессию не запускает. За конвейером - реакция на обращение к агенту и конец круга ревью на PR, который ведет конвейер: PR открыт учетной записью агента или несет метку `processes.review.managedLabel`. Такой PR агент доводит до Ready сам.

Обращение `@claude`, `@codex` или `@cursor` открывает комментарий или ревью участника проекта - проверяется начало тела, а не вхождение: цитата чужого обращения прогон не поднимает. Участник проекта у GitHub - автор с ассоциацией `OWNER` или `MEMBER`, у GitLab - доступ Developer и выше. Исполнителя задает модуль `ci-agent`, а не имя в обращении. Бот агента не будит. Конец круга будит агента, когда страж круга в прогоне не пропущен.

Решение и сессию держит [`agent-event.py`](../../../.harness/scripts/agent/agent-event.py): `gate` решает, будить ли агента, `account` называет учетную запись токена агента, `workdir` клонирует репозиторий токеном агента, `session` собирает промпт записи `prompts.agents.issue-agent` методологии рядом с журналом и ведет сессию `agent-run.py`. Комментарий, а также событие закрытого PR и PR из другого репозитория получают ответ без правок: `workdir` ставит клон на head открытого PR без ветки, в остальных случаях оставляет ветку по умолчанию, сессия идет в режиме `reply`, а ответ публикует обвязка. Ответ, отклоненный проверкой текста, сессия переписывает один раз по причине отказа; после второго отказа в обсуждении появляется уведомление. Ревью и конец круга на открытом PR своего репозитория, как и событие задачи, ведут авторскую сессию в выделенном worktree ветки PR или ветки задачи по конвенции `git.branchConvention`: тип и слаг - по задаче ([`CONTRIBUTING.md` §2](../../../CONTRIBUTING.md#2-ветки)). Наборы инструментов агентов живут в `agents.tools` манифеста проекта; `agent-event.py session` и `check-pipeline.py --emit-agent <id>` собирают сессию одной функцией. Оснастка и промпт идут с ветки по умолчанию у GitHub, а у GitLab - с целевой ветки MR для события запроса и с `git.baseBranch` для события задачи; агент работает в своем клоне. У GitLab двойника события ищет `duplicate` отдельной задачей, `harness-agent` получает его выход через dotenv, а `gate` и сессию ведет в группе ресурса. Новое событие той же задачи или PR у GitHub снимает идущую сессию (группа `concurrency`), у GitLab ждет ее конца (`resource_group` задачи `harness-agent`).

Поставщик кода и трекер доступны агенту командами [`forge.py`](../../../.harness/lib/forge.py) и
[`tracker.py`](../../../.harness/lib/tracker.py): перечень команд печатает `--help`, аргументы команды -
`<команда> --help`.

Комментарий `forge.py comment` и `tracker.py comment`, ответ `pr-threads.py reply`, задача
`tracker.py create` и ее тело `tracker.py update`, описание PR `forge.py open-change` и `forge.py edit-change`, комментарий
закрытия `forge.py close-change` проходят ту же проверку
текста, что публикация коннектором: хук
[`forge-text-lint.py`](../../../.harness/hooks/forge-text-lint.py). Отказ печатается, и текст не
публикуется. Текст агента собирает `text_templates.py render`
([справочник шаблонов](../agents/templates.md#тексты-агента)): тело без маркера данных с суммой и
тело, правленое после сборки, проверка отклоняет. Запрос на слияние без описания она не открывает, а
заголовок запроса при открытии и переименовании сверяет с правилом
[`CONTRIBUTING.md` §3](../../../CONTRIBUTING.md#3-pull-requests).

### Где смотреть работу агента

Ход рассуждений в журнал прогона не попадает. После каждой сессии [`session-log-digest.py`](../../../.harness/scripts/agent/session-log-digest.py) печатает выжимку структурного лога сессии: исход, ходы, длительность, токены, отказы по правам, веер субагентов и прочитанные файлы дерева по тому же разбору журнала, что и у круга ревью. Граница печати проходит по роли аргумента: путь и шаблон печатаются, у команды - только голова, тело не печатается вовсе. Последней строкой идет запись `agent-session-record` - ее читает опрос телеметрии, если проект его подключил. Токены и длительность считает [`session_cost.py`](../../../.harness/scripts/text/session_cost.py): токена, которого провайдер не отдал, в записи нет, нулем он не заменяется; длительность - время от запуска до конца сессии по замеру скрипта, который ее запустил: `agent-run.py`, а у сессии конвейера - `agent-event.py`. Время провайдера берется, только если замера нет. Сессия агента задач, которая ведет конвейер разработки, получает сумму токенов и прочитанного своих стадий.

Отказы по правам у всех исполнителей считает общий хук запретов [`agent-deny.py <вид>`](../../../.harness/hooks/agent-deny.py). `agent-run.py` подключает его к сессии Claude Code (`--settings`), Codex (`hooks.PreToolUse`) и Cursor (`hooks.json`) с запретами сессии: `policies.permissions.deny`, запреты вида из `KINDS` в `agent_provider.py` и `--disallowed-tools`. Из тех же запретов собираются правила самого исполнителя. Хук дописывает каждый отказ в журнал сессии из переменной `AGENT_DENIALS`, а `agent-run.py` переносит их в поле `denials` итоговой записи. У Claude Code к ним добавляется его `permission_denials` без повторов по `tool_use_id`. Журнал заводит первый вызов хука; если хук ни разу не вызывался и исполнитель своего перечня не дал, выжимка отказы не считает и говорит об этом. Если в итоге Claude Code нет `permission_denials`, выжимка предупреждает и при журнале хука, а пустой журнал тогда не ноль: отказы вне `--allowedTools` видны только в этом перечне.

### Замер автономии

Замер отвечает на вопрос, какая доля PR агента доходит до Ready без человека. След человека - комментарий, ревью с телом или коммит до перевода в Ready без подписи агента. Подписи объявлены записью `policies.authorship` в [methodology.json](../../../.harness/methodology.json): комментарию агента без подписи отказывает хук [forge-text-lint.py](../../../.harness/hooks/forge-text-lint.py), коммиту агента `commit-msg` ставит трейлер `Agent: <среда>` по переменной окружения среды. Опрос, считающий долю, проект подключает сам: формат записей выжимки и подписи стабильны.

- PR агента - PR, в котором до перевода в Ready есть коммит агента.
- Записи ботов и коммит слияния базы следом не считаются.
- PR, открытый сразу готовым, в замер не идет.

## Разбор алертов

Модуль `alert-triage` разбирает горящие алерты агентом; источник алертов и телеметрии - Grafana
(`alert-triage.grafana`), issue алерта ведет GitHub. Конвейер -
[`alert-triage.yml`](../../../.github/workflows/alert-triage.yml), шаги и инструмент агента -
[`alert-triage.py`](../../../.harness/scripts/agent/alert-triage.py), промпт -
[`agent/alert-triage.md`](../../../.harness/prompts/agent/alert-triage.md), сессию - запись `alert-triage` в
`prompts.agents` методологии, тексты issue и комментариев - шаблоны `issue/alert`, `comment/alert-episode`
и `comment/alert-note`. Модуль требует `forge/github` и `tracker/github-issues`: issue ведет трекер под
`github.token`, автор issue отбора - учетная запись этого токена. Записи отбора и финализатора машинные,
по шаблону, и адаптер пишет их без подписи и проверки текста; подпись и проверку проходят записи агента
через `tracker.py`; прогоны Actions и запрос круга ревью на голове PR читает поставщик кода.

1. Отбор (`select`) раз в 10 минут или ручным запуском без номера issue читает через Grafana горящие
   алерты без сайленса и подавления со значением `severity` из `alert-triage.severities`. Ключ issue -
   `alertname`, метка `alert-triage.component` и, у алерта с меткой `alert-triage.group`, ее значение.
   На ключ заводится одно issue с меткой `alert-triage.label`; новое срабатывание дописывается
   комментарием, закрытое issue открывается снова. Разбор запрашивается не больше
   `alert-triage.limit` за прогон, первым идет первое значение `severities`; новое срабатывание
   открытого issue после завершенного разбора ждет `alert-triage.cooldownHours`, упавший разбор -
   10 минут. Без токена выбранного исполнителя срабатывания записываются без разбора.
2. Ссылка (`link`) отвечает на срабатывание ссылкой на issue рассылкой `alert-triage.notify`, без нее -
   рассылкой модуля `notifications`. Канал - `alert-triage.notifyChannel`, родителя треда ищет
   выражение `alert-triage.notifyThread`; токен канала - секрет `alert-triage.notifyToken`.
3. Разбор - сессия `agent-run.py --mode agent` на issue. Телеметрию агент читает подкомандами
   `prom`, `loki`, `traces`, `trace`, `metrics`, `labels` и `alerts` только по путям словаря
   `GRAFANA_OPS_PATHS` из файла `alert-triage.pathsFile`: маршрут раннера к Grafana открывает
   только их. Учетные данные маршрута - секрет `alert-triage.auth` с заголовком `alert-triage.header`.
   При включенном модуле `release/tag-flow` подкоманда `release --at <момент>` называет по тегам
   `vX.Y.Z` релиз, работавший в этот момент, и его изменения от предыдущего релиза; без модуля она
   сообщает, что релизы по тегам не ведутся. Тег ставит успешная выкладка, поэтому коммиты ветки
   релиза без тега подкоманда показывает отдельно с их изменениями: это выкладка, которая шла или
   не удалась. Тег несет время коммита релиза, а не конца выкладки: для релиза моложе часа
   подкоманда называет и предыдущий. Ручной откат на прежнюю версию нового тега не ставит и этой
   подкоманде не виден.
   Шаги после сессии идут из копии `.harness`, снятой до нее. Разбор и итог агент публикует
   подкомандой `analysis`: текст агента идет по шаблону `comment/note`, маркеры разбора, результата и
   PR дописывает она.
4. Итог (`published`) засчитывает разбор по комментарию учетной записи агента с маркером
   `<!-- alert-analysis: N -->` после начала сессии: подтвержденная внешняя причина
   (`alert-result: external`) или PR (`alert-result: pr` и `alert-pr`) со ссылкой на issue - в
   описании PR агента либо в комментарии агента после начала сессии. PR смержен либо открыт под
   меткой `processes.review.managedLabel` с запросом круга: меткой `processes.review.label` или
   прогоном ревью на текущей голове. Учетную запись агента дает `AGENT_GITHUB_TOKEN`: без него отбор
   считает агента выключенным, а при той же учетной записи, что у отбора, разбор не засчитывается.
   Неизвестная причина остается незавершенной. Итог - комментарий-подтверждение с маркером
   `alert-completed` или `alert-failed`.

Состояние разбора живет маркерами `<!-- alert-<имя>: <значение> -->` в теле issue: ключ, начало
последнего записанного срабатывания, очередь, запрос и номер запросившего прогона, итог. Тело issue
пишет только отбор, прогоны отбора идут по одному; подтверждения итога он переносит в тело на
следующем прогоне. `alert-completed` подтверждает время именно завершенного запроса: срабатывание во время сессии
остается в очереди. Пока запросивший прогон идет или ждет раннера, issue второй раз не
запрашивается; оборванное задание освобождает запрос завершением прогона, а удаленный прогон -
своим отсутствием. Ручной запуск с номером issue повторяет завершенный разбор без окна `cooldownHours`. Среди открытых issue ключа отбор берет
старейшее; ключ без issue он перед созданием ищет поиском с точным маркером и автором, и неполный
поиск останавливает создание. Открытые issue и подтверждения читаются целиком, закрытая история -
ограниченным числом страниц. Дубль ссылается на основное issue маркером `alert-duplicate` и закрыт с
прежней меткой: новые срабатывания и ручной разбор дубля идут в основное issue, окно и лимит
считаются по нему, начало последнего срабатывания у каждого ключа свое. Неверная ссылка дубля
останавливает отбор. Задания идут в окружении `alert-triage.environment`. Отбор
идет только с `git.baseBranch`: на раннерах переменной репозитория `alert-triage.selectRunnerVar`, и пока
она пуста, конвейер не запускается, а без настройки - на `runners.triage`. Разбор идет на
`runners.triage`; переменная вида `triage` в `runners/github-actions.variables` заменяет метки.

## Ноль предупреждений и сообщений сборки

Для стека .NET строгость сборки задает политика проекта в конфигах `apps[].configs`; ослабление вне них ловит гейт [`check-diagnostic-integrity.py`](../../../.harness/scripts/check/check-diagnostic-integrity.py), а значение `NoWarn` внутри конфигов гейт не сверяет: его проверяет сама политика проекта при сборке. Сообщения info считает [`check-build-diagnostics.py`](../../../.harness/scripts/check/check-build-diagnostics.py) по журналу SARIF, который компилятор пишет по `ErrorLog` из [`Harness.Build.targets`](../../../.harness/dotnet/Harness.Build.targets). Журналов обязано быть больше нуля.

Новое предупреждение чинится по месту: рукописные подавления запрещены. Подавитель Roslyn проекта снимает только объявленное правило: пары кодов подавителей из исходников решения гейт читает сам, подавители из пакетов называет настройка `backend/dotnet.suppressions` манифеста.

## Форматирование C#

Переносы и отступы C# задает CSharpier. Форматтер Roslyn длинные строки не переносит и хранит переносы автора, поэтому с ним раскладка файла зависит от того, кто его писал. CSharpier раскладывает выражение заново по ширине строки - `max_line_length` раздела `[*.cs]` в `.editorconfig`. Исключения задает [`.csharpierignore`](../../../.csharpierignore), версию - манифест `.config/dotnet-tools.json`, запись `csharpier` в него ставит модуль `stack/dotnet`. Правило форматирования Roslyn IDE0055 блок комплекта в `.editorconfig` выключает: оно требует раскладки Roslyn и валило бы сборку на выводе CSharpier. Ширину строки и остальные правила C# задает проект.

- Редактор форматирует файл при сохранении расширением CSharpier: в VS Code и Cursor - `csharpier.csharpier-vscode`, его выбор форматтером C# и рекомендацию ставит комплект в `.vscode/settings.json` и `.vscode/extensions.json`; в Visual Studio - расширение CSharpier с флажком Reformat with CSharpier on Save.
- Хук [`code-cleanup.ps1`](../../../.harness/hooks/code-cleanup.ps1) перед коммитом прогоняет `dotnet format style` и `dotnet format analyzers` по решению, затем CSharpier по дереву: исправления `dotnet format` выходят в раскладке Roslyn, и CSharpier возвращает их к своей во всех файлах, а не только в индексе. Проход `whitespace` хук не зовет: он переписал бы раскладку CSharpier во всем решении.
- Гейт `dotnet-format` ([`check-dotnet-format.py`](../../../.harness/scripts/check/check-dotnet-format.py)) валит Check, когда файл расходится с выводом `csharpier check`: он идет при объявленном решении .NET, когда изменение задевает приложение стека `dotnet` или вход форматтера - файл `.cs`, `.csharpierignore`, `.editorconfig` или `dotnet-tools.json`.

## Закрытие задач

Задачу трекера закрывает задание после мержа запроса в `{{git.baseBranch}}`: у GitHub -
[`close-issues.yml`](../../../.github/workflows/close-issues.yml), у GitLab - задача `harness-close-issues`
файла [`tracker.yml`](../../../.gitlab/ci/tracker.yml). Оба ставит модуль `tracker`, оба вызывают
`tracker.py close-merged --sha <голова после push> --before <голова до push>` и разбирают каждый коммит
первого родителя, который принес push: так push с несколькими мержами закрывает ссылки каждого. Без
головы до push (новая ветка, нулевой SHA) или после переписанной истории разбирается только последний
коммит. Конвейер push в `{{git.baseBranch}}` у GitLab не отменяется следующим push (`auto_cancel:
on_new_commit: none` в `workflow` файла [`harness.yml`](../../../.gitlab/ci/harness.yml)): иначе мерж,
чье задание еще ждало раннер, терял бы свои задачи. Для каждого коммита команда находит запрос по сообщению и берет закрывающие
ссылки из его описания и из описаний запросов, которые этот мерж принес в базовую ветку: их номера несут
коммиты от первого родителя коммита до головы запроса. Поэтому мерж обратного слияния `back-merge/vX.Y.Z`
закрывает задачи хотфиксов ([CONTRIBUTING §11](../../../CONTRIBUTING.md#11-релиз-и-хотфикс)), а мерж ветки
этапа - задачи запросов, влитых в нее. На мерж в `{{git.releaseBranch}}` задание не запускается; задачи GitHub
Issues того же репозитория по нему закрывает сам GitHub, если `{{git.releaseBranch}}` - ветка по умолчанию.

Номер запроса команда берет из сообщения коммита: у GitHub - из заголовка squash `(#N)` или коммита слияния
`Merge pull request #N`, у GitLab - из строки `See merge request <проект>!N` коммита слияния или `(!N)` в
конце заголовка squash. Мерж fast-forward или squash без коммита слияния, чей шаблон сообщения номера не
несет (`%{title}`), задач не закрывает: команда печатает, что коммит запроса не влил.

Открытая задача закрывается, закрытая остается как есть. Ссылки самого запроса команда пропускает, только
когда задачи ведет GitHub Issues того же репозитория, а `{{git.baseBranch}}` - ветка по умолчанию: такие
задачи GitHub закрывает сам. Jira закрывает задачу переходом в статус категории `done` или переходом из
настройки `tracker/jira.doneTransition` ([параметры](../agents/harness-parameters.md#tracker)). Отказ трекера
или поставщика кода не роняет конвейер базовой ветки, но и не проходит молча: `close-merged` выходит с кодом 3, у
GitLab задание становится желтым (`allow_failure: exit_codes: [3]`), у GitHub шаг проходит, а сводка прогона
перечисляет незакрытые задачи и причины. Следующий push разбирает только свой диапазон, поэтому такое
задание перезапускают вручную, когда трекер снова доступен: повторный запуск безопасен, закрытые задачи он
не меняет.

## Привязка ветки к задаче

Стадия `claim` принимает ветку, которую трекер держит связанной с задачей, либо ветку, имя
которой несет номер задачи по префиксам трекера. После открытия PR [GitHub снимает связь с веткой и
показывает только PR](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-a-branch-for-an-issue),
а упоминание задачи в PR (`CrossReferencedEvent`) рождает сам проверяемый PR, поэтому
подтверждением не считается. Связь в трекере для ветки с номером задачи не требуется: ее заменяют
соглашение об именах, назначенный исполнитель открытой задачи и текущий `Refs` или `Closes` в
описании. Второй PR из ветки с тем же номером задачи этот шаг не отличает. Ветку без номера задачи
`claim` отклоняет, если трекер не держит ее связь; `Refs` или `Closes` обязателен и ей.
Автоматическое закрытие задачи для `Refs` не требуется.

[`link-branch.yml`](../../../.github/workflows/link-branch.yml) связывает созданную ветку с задачей в панели Development. Номер задачи из имени ветки называет трекер ([`tracker.py`](../../../.harness/lib/tracker.py)); ветки без номера пропускаются. Связь PR с задачей в теле ([`Refs` и `Closes`](../../../CONTRIBUTING.md#2-ветки)) проверяет [`check-pr-issue-link.py`](../../../.harness/scripts/check/check-pr-issue-link.py). Задачу репозитория, отличного от репозитория кода, тело PR называет `owner/name#N`: голое `#N` - задача репозитория кода.

GraphQL-операция `createLinkedBranch` создает связь только вместе с ref. Для существующей ветки [`link-branch.py`](../../../.harness/scripts/pipeline/link-branch.py) пересоздает ref на том же коммите через пробную ветку `link-probe/<прогон>-<попытка>`, а шаг `Restore branch` с `if: always()` восстанавливает ref по записи при отказе. Ветку мутация создает в репозитории кода (`repositoryId`), а не задачи. Если после привязки ветки у поставщика кода нет, связь снимается, прогон падает, а ветку по записи возвращает `Restore branch`. Ветки head и base открытого PR не трогаются. Если прав `GITHUB_TOKEN` недостаточно, секрет `ISSUE_LINK_TOKEN` содержит fine-grained PAT с Contents, Issues и Workflows на запись и Pull requests на чтение.
