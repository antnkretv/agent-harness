# Стандарты документации

> **Тип (Diataxis):** Справочник

Документ задает структуру и проверяемые свойства документации. Правила языка и ошибок находятся в [стандарте текста](text.md), порядок вычитки - в скилле
[`docs-text`](../../../.agents/skills/docs-text/SKILL.md), комментарии - в
[`code-comments.md`](code-comments.md), git и PR - в [`CONTRIBUTING.md`](../../../CONTRIBUTING.md).

## Тип документа

Технический документ объявляет один тип [Diataxis](https://diataxis.fr/) строкой метаданных сразу
под заголовком H1. Строка не входит в заголовок: заголовок называет предмет и тип не повторяет.
После типа строка может продолжаться аудиторией и датой обновления:

```markdown
# Порядок выката

> **Тип (Diataxis):** Практическое руководство - **Аудитория:** ops
```

| Тип | Diataxis | Назначение |
| --- | --- | --- |
| Обучение | tutorial | ведет новый сценарий от начала до результата |
| Практическое руководство | how-to | решает одну практическую задачу; runbook - диагностика и восстановление работающей системы - тоже этот тип |
| Справочник | reference | перечисляет контракт без объяснительного эссе |
| Объяснение | explanation | объясняет решение и его последствия |

- У документа один тип. Смешанный документ делится, либо получает тип основной цели, а другая часть
  выносится в отдельный документ.
- Тип не объявляют ADR, индекс `README.md`, чья задача - навигация, датированный снимок или аудит (дата в конце имени либо
  путь из `docs.historicalPrefixes`)
  и машинный текст (`docs.machineTextPrefixes`). `README.md` с собственным содержанием тип объявляет.
- ADR фиксирует действующее архитектурное решение; правку и удаление задает [жизненный цикл](../adr/README.md#жизненный-цикл) реестра, номер - [правило нумерации](../adr/README.md#правило-нумерации).
- Область, где строка обязательна, задает ключ `docs.typedPrefixes` манифеста
  [`project/manifest.json`](../../../.harness/project/manifest.json), по умолчанию `docs/`; строку и значение проверяет `check-docs.py --area docs`, если проект включил проверку `types` в `docs.checks`.

## Живой документ и снимок

Живой документ меняется вместе с кодом. Снимок аудита содержит дату и
commit; новые изменения его не переписывают. Недатированное утверждение "сейчас" недопустимо.

Ни живой документ, ни операционный снимок не копируют версии зависимостей, SDK, runtime и образов.
Точная среда расследования сохраняется машинным артефактом и привязывается ссылкой или commit.
`tool-pins` не проверяет Markdown из `docs.historicalPrefixes`; исторические снимки
проверяются на это правило при ревью.

## Архитектура и код

- C4 или draw.io используется только когда схема показывает связь лучше текста.
- Диаграмма перечислена в индексе feature и обновляется с меняемой границей.
- Имя symbol в обратных кавычках должно существовать в коде; это проверяет `check-doc-symbols.py`.
- XML-doc и JSDoc допустимы только для контракта, которого нет в сигнатуре, и подчиняются стандарту
  комментариев. Массовый `<summary>` с пересказом имени не добавляется.
- OpenAPI, generated clients и schema snapshots являются generated artifacts, а не ручной reference.

## Структура

- Новый документ добавляется в ближайший индекс ровно один раз.
- Feature documentation не дублируется в app docs; app docs описывают только свою платформенную сторону.
- ADR входит в дерево со статусом `Accepted`: `Proposed` - статус открытого PR, а не дерева ([реестр](../adr/README.md#как-завести-новое-решение)).
- Операционная величина - порог, лимит, `request`/`limit`, ретенция, имя метки, код ответа, таймаут, значение конфига - живет в чарте или конфиге и его runbook, а не в ADR.
- Ссылка должна быть не только разрешимой, но и вести на обещанный по смыслу раздел.
- Большой бинарник хранится вне repository; в индексе остается ссылка. Файл области документации не больше 1 МБ. Каталоги `legal/` и `assets/` корня документации от лимита свободны: юридические оригиналы и бинарные приложения хранятся в исходных форматах.

## Документ feature

Одна фича - одна папка. Внутри - индекс `README.md` (что фича делает и зачем, ссылка на задачу и
спеку) и разделы по приложениям, которые она затрагивает. Отсутствующая сторона пустым файлом не
заводится. Понять прикладное поведение - значит открыть документ фичи, а не читать код: правка
поведения фичи и правка ее документа - одно изменение.

```
docs/features/
└── <фича>/
    ├── README.md # индекс: что и зачем, таблица разделов, спеки, диаграммы
    ├── <приложение>.md # устройство стороны приложения из манифеста
    └── diagrams/ # диаграммы (опц.)
```

Статус относится к границе, описанной в индексе фичи:

- `complete` - описанная граница реализована;
- `partial` - в описанной границе нет исполняемого пути; точный остаток назван в индексе фичи;
- `pilot` - путь построен, но живая приемка еще не подтверждена.

## Размещение и имена

Документы платформы лежат в `docs/platform/` по папкам тем; в корне `docs/platform/` документов нет.

| Папка | Тема |
| --- | --- |
| `adr/<area>/` | принятые решения |
| `agents/` | окружение и оснастка агентов |
| `architecture/` | устройство системы, границы и гейты архитектуры |
| `delivery/` | путь изменения: SDD, CI/CD, выкладка |
| `operations/` | эксплуатация: подъем стека, алерты, дашборды |
| `standards/` | правила кода, тестов и текстов |
| `requirements/` | реестр требований и его покрытие |

Имя документа в любой папке `docs/` - английская фраза kebab-case о предмете документа: строчные
латинские буквы, цифры и дефисы, расширение отдельно (`probe.example.json`).

- Слова типа документа (`standard`, `guide`, `runbook`, `spec`, `checklist`, `catalog`, `analysis`
  и другие из `DOC_TYPE_WORDS` гейта) в имя не входят: тип виден из содержания.
- Имя не повторяет свою папку: `standards/code-comments.md`, а не `standards/code-comments-standard.md`.
- Датированный снимок оканчивается датой: `load-test-2026-10-05.md`.
- Имя ADR - `NNNN-<предмет решения>.md`: предмет, а не формулировка решения.
- `README.md`, корневые инструкции и артефакты Spec Kit в `specs/` следуют своим соглашениям.

## Проверка

```bash
./.harness/hooks/python.cmd .harness/scripts/check/check-docs.py --area docs --anchors
./.harness/hooks/python.cmd .harness/scripts/check/check-doc-symbols.py --all
./.harness/hooks/python.cmd .harness/scripts/check/vale-lint.py --files <paths>
```

Ссылки, якоря, секреты, диаграммы и инструкции агентов гейт проверяет всегда. Индекс, имена файлов,
шапку ADR, тип Diataxis, словарь статусов и размер документа он проверяет, только когда проект
включил их в `docs.checks` манифеста ([параметры](../agents/harness-parameters.md#раздел-docs)).

Якорь ссылки `файл.md#раздел` сверяется со слагом заголовка цели по правилу поставщика кода проекта
(у GitLab подряд идущие дефисы схлопываются в один, у GitHub и без поставщика - сохраняются) во всех
отслеживаемых git файлах Markdown (`*.md`, `*.mdc` и корневой `llms.txt`), а не только в области
`docs`: ссылки скиллов, промптов и корневых инструкций агент читает первыми. Сверку ведет отдельный
проход `--anchors`, а не `--area`: `check-all.py` запускает его при каждой проверке, областью он не
отбирается, локальная проверка области зовет его тем же флагом. Из охвата выходят вендорные skills
(`docs.vendoredSkills` манифеста и Spec Kit), поставка и установленная база комплекта
(`docs.payloadPrefixes`, `.harness/state/`), файлы комплекта (роли `managed` и `json` в
`.harness/state/lock.json`) и сгенерированные пути (`docs.generatedSegments`,
`docs.generatedPrefixes`). Ссылки файлов комплекта написаны по правилу GitHub, где живет комплект, и их
сверяет сверка комплекта в его репозитории. Каталог закрытого трека спек из дерева удаляется, поэтому архив треков
отдельного исключения не требует.

После структурной правки дополнительно запусти tests документации затронутой области. Review проверяет
смысл по [`.harness/review/requirements.md`](../../../.harness/review/requirements.md), но не повторяет
механические ошибки этих гейтов.
