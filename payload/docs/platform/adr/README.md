# Реестр архитектурных решений

<!-- harness:begin core -->
Указатель решений проекта. Решение (ADR) - запись о выборе с контекстом, обоснованием и последствиями. Канон документации - [standards/documentation](../standards/documentation.md), реестр спек - [specs/README.md](../../../specs/README.md).

## Правило нумерации

Номер сквозной по всему дереву и не переиспользуется никогда, даже если решение удалено. Счетчик один на все области - строка "Следующий свободный номер" реестра: новое решение берет ее значение с учетом номеров открытых пул-реквестов и поднимает ее, удаление решения ее не опускает.

Принятое решение живет в каталоге своей области с исходным номером; перенумерации нет. Коллизия номера с решением параллельного запроса исправляется до мержа: решению открытого запроса назначается свободный номер, его ссылки обновляются.

**На номер без области ссылаться нельзя** - только полным путем или парой "область + номер" вида `<область>/NNNN`. Правило исполняет [`check-adr-refs.py`](../../../.harness/scripts/check/check-adr-refs.py) по всему дереву, кроме датированных записей из `docs.historicalPrefixes` и сгенерированного по `docs.generatedSegments` манифеста ([параметры](../agents/harness-parameters.md#раздел-docs)). Области гейт берет из подкаталогов этого дерева: новая область появляется вместе с первым решением в ней.

## Порог

Решение заводится, когда меняется направление зависимости, граница модуля, контракт между хостами или норма всему дереву. Спорный случай порога решается в сторону ADR.

Решение не заводится:

- на уровне фичи;
- об операционной величине: пороге, лимите, `request`/`limit`, ретенции, имени и длине метки, коде ответа, таймауте, значении конфига. Она живет в конфиге выкладки и его runbook, ее причина - в PR.

## Как завести новое решение

Файл `NNNN-<предмет решения>.md` в каталоге своей области, где `NNNN` - значение строки "Следующий свободный номер" ([правило нумерации](#правило-нумерации)); новое решение поднимает эту строку, а имя называет предмет, а не формулировку решения ([размещение и имена](../standards/documentation.md#размещение-и-имена)). Шапка - список полей `Статус`, `Дата` и `Область` с охватом. Каталог задает пространство номеров, а охват решения может быть шире.

Решение входит в основную ветку разработки со статусом `Accepted` и датой мержа: мерж запроса на слияние, который его заводит, и есть решение владельца. `Proposed` - статус решения только в открытом запросе; в основной ветке его нет, а решение, которое владелец не принял, в дерево не входит.

Область выбирается по тому, чье поведение решение связывает: приложение из манифеста получает свой каталог по имени приложения, правило, пересекающее приложения или задающее норму всему дереву, - `platform/`.

## Жизненный цикл

1. **Реестр несет указатель:** номер, область, название со ссылкой, статус одним словом и дату.
2. **Решение описывает действующее правило.** Изменение принятого решения правит его тело в том же запросе на слияние, который меняет поведение: пункты решения, модель отказа и последствия говорят о текущем состоянии, а не о пути к нему. История изменений - в git; журнал правок, пересказ прежних редакций и отметки "отменено", "изменено" в тело не пишутся.
3. **Один предмет - одно решение.** Решение о предмете, у которого уже есть решение, правит его, а не заводит второй файл. Новое решение, задевающее чужой предмет, правит и то решение; несколько решений об одном предмете сводятся в одно.
4. **Удаление.** Решение, отмененное целиком, полностью перенесенное в другое или ниже порога, удаляется вместе со строкой реестра; тело остается в истории git.
5. **Ссылки на удаленное решение правятся в том же запросе на слияние** - на решение, которое держит правило, либо снимаются. Висящую ссылку отклоняет [`check-docs.py`](../../../.harness/scripts/check/check-docs.py).
