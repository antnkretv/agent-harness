# Установка harness агентом

Точка входа агента, который ставит комплект agent-harness {{harness.kitVersion}} в репозиторий проекта.
Установка идет тремя этапами, каждый - отдельным PR, следующий от ветки предыдущего:

| Этап | Инструкция | Ветка | Работа | Модель |
| --- | --- | --- | --- | --- |
| 1. Накатка | [STAGE-1.md](installer/stages/STAGE-1.md) | `chore/harness-install` от `<base>` | `ah init` владельца, поставщик кода, PR накатки | достаточно слабой: шаги детерминированы |
| 2. Документация | [STAGE-2.md](installer/stages/STAGE-2.md) | `chore/harness-context` от `chore/harness-install` | заготовки и документы проекта, глоссарий, предметная область, промпты, факты манифеста | сильная: работа суждением |
| 3. Код | [STAGE-3.md](installer/stages/STAGE-3.md) | `chore/harness-code` от `chore/harness-context` | подключение к коду, реестры текста, комментарии, анализаторы, форматтеры, архитектурные тесты | достаточно слабой: правило правки называет гейт |

Сессия этапа читает целиком этот файл и инструкцию своего этапа; другие этапы ей не нужны. Этап готов
по своему списку из раздела "Критерии готовности" ниже: этап не завершен, пока каждый пункт списка не
подтвержден выводом его команды.

Шаги этапа идут по порядку. Вопросы о модулях, расширениях и настройках установщик задает владельцу в
терминале командой `ah init` или `ah change`; факты, найденные в дереве, он отвечает сам. Агент на
вопросы не отвечает: он запускает эти команды без терминала только с ответами владельца в
`.harness/project/answers.json` или после своей правки фактов манифеста. Скрипты и правила
установки лежат в архиве; машину, доступ к репозиторию и поставщику кода проверяет `doctor`.
Отчет по шаблону в конце отдается после каждого этапа.

Обозначения: `KIT` - каталог распакованного комплекта, `<архив>` - путь к архиву `{{harness.archive}}`,
`<base>` - ветка разработки проекта. Установщик и скиллы обслуживания установки в проект не ставятся:
каждая команда установщика идет из `KIT`.

На Windows процедура идет из Git Bash в Git for Windows с Windows Python 3.11+. Во всех командах
этой инструкции используется поставляемый `python.cmd`. Окружение остается Windows: WSL для установки не нужен.
Вопросы `ah init` и `ah change` владелец отвечает в PowerShell или Windows Terminal: в Git Bash консоль
для них недоступна. Путь с буквой диска вместо пути от корня репозитория установщик отклоняет и в ответе,
и в манифесте. Скрипт `.sh` из PowerShell запускают Git Bash полным путем
из каталога установки Git, который `git --exec-path` называет при любом `git.exe` в PATH
(`& (Join-Path (git --exec-path) '..\..\..\bin\bash.exe') <скрипт>`): `bash` из PATH там - WSL.

Из чата процедуру запускает скилл `harness-init` из архива: агенту называют `$KIT/skills/harness-init/SKILL.md`,
путь к архиву и его sha256.

## Когда этап останавливается

Этап идет, пока каждый пункт его критериев не подтвержден выводом команды. Красный гейт своего этапа,
отказ команды и большой объем правок - работа этапа, а не повод остановиться: причина чинится по
рецепту гейта, команда повторяется. Остановиться до готовности можно только в двух случаях:

1. Действие владельца из таблицы "Ошибки и что с ними делать": доступ, токен, права, архив - то, чего
   агент сделать не может.
2. Решение владельца: вопрос установщика о модуле или настройке, а на этапе 3 - правка, которая меняет
   поведение или требует выбора по смыслу.

Отчет об остановке называет случай, строку вывода и что нужно от владельца. Отчет "этап не готов" без
одного из этих случаев - ошибка: работа продолжается.

## Обновление и смена настроек

- Новая версия комплекта из выпуска - `python3 .harness/ah.py upgrade` в клоне проекта: ветка, `apply`
  новой версией, lock и черновой PR ([установка по lock](payload/.harness/docs/harness.md#установка-по-lock)).
  Без выпуска, с ветки или коммита репозитория комплекта, - `python3 .harness/ah.py upgrade --commit develop`.
  Из архива новой версии - скилл `harness-sync` этого архива: `init` новой версии с ее новыми вопросами
  владельцу, перенос нужных правок проекта, приемка, PR.
- Смена модулей и настроек - `python3 .harness/ah.py change` владельца в терминале: все вопросы с
  прежними ответами, затем `apply` тем же комплектом.

Скиллы установки и обновления (`harness-init`, `harness-sync`) живут только в одном месте - каталоге
`skills/` архива рядом с установщиком; они никуда не копируются: ни в проект, ни в каталог скиллов
пользователя. Агенту называют путь `SKILL.md` в распакованном архиве: `harness-sync` -
`$KIT/skills/harness-sync/SKILL.md` архива новой версии.

Повторный `apply` того же архива дерево, которое проект не правил, не меняет. Каждый `apply` пишет
файлы managed, блоки конфигов и ключи комплекта в json версией комплекта, даже если проект их правил, добавляет
новые файлы и снимает файлы и блоки снятых модулей; блок project, ключи проекта в json и заготовки -
в том числе `AGENTS.md`, `CONTRIBUTING.md` и `docs/README.md` - не трогает, а текст вне блоков конфига переносит в блок project
([обновление](payload/.harness/docs/harness.md#обновление)). Правку проекта, которую `apply`
переписал, в файлах оболочки показывает `git diff`; поставленный файл `install` переписывает без следа в
git, и его правку проект переносит до обновления: нужную проект переносит в место проекта, которое называет отказ
гейта `harness-files`. `.harness/state/lock.json`
коммитится вместе с установкой.

## Ошибки и что с ними делать

| Симптом | Причина | Действие |
| --- | --- | --- |
| `init` или `change` код 2, вопрос без ответа | терминала нет, а у вопроса нет значения по умолчанию | действие владельца: та же команда в терминале |
| `init` или `change` код 2, ответ не подходит | ответ в `answers.json` или в манифесте не прошел схему вопроса | действие владельца: исправить ответ той же командой в терминале |
| `doctor`: `git push` отказ | нет SSH-ключа в `~/.ssh` или `ssh-agent`, нет HTTPS-токена в credential helper, нет права на ветку | действие владельца: настроить доступ, повторить `doctor` |
| `doctor`: нет токена поставщика кода | переменной нет в окружении оболочки или IDE | действие владельца: задать переменную и перезапустить сессию |
| `apply` код 2, регистр путей | каталог проекта отличается от пути комплекта только регистром | действие владельца: `git mv` каталога под регистр комплекта, повторить `apply` |
| `apply` код 2, перечень параметров | манифест не проходит проверку | действие владельца: ответить заново в `python3 .harness/ah.py change` |
| `apply` код 2, модуль вне архива | архив собран под другие решения | архив под новые решения: `ah.py pack` полного комплекта |
| `verify`: модуль выключен без причины | технология модуля есть в дереве | включить модуль или назвать причину ответом `modules.<модуль>.off` |
| `apply` код 2, серверы TOML | таблица `mcp_servers` проекта в `.codex/config.toml` повторяет сервер блока комплекта | снять названные таблицы из файла проекта, повторить `apply` |
| `verify` код 2, другой комплект | `verify` запущен другой сборкой: другая версия, другой `tree` или другая сборка под решения | запустить `verify` тем архивом, которым шла установка (`version` и `tree` в `lock.json`); после установки архивом под решения - архивом `ah.py pack` с теми же решениями |
| `verify`: правило выключено без причины | запись `rules.disabled` в `.harness/project/manifest.json` без `reason` и `replacement` | дописать поля или удалить запись |
| `verify`: проба прошла | гейт не отказал на заведомом нарушении | гейт сломан: не обходить, разобрать вывод гейта |
| `не найден ...` в `doctor` или `verify` | нет инструмента | поставить скриптом из `installer/stages/STAGE-1.md`, раздел "Зависимости" |

## Критерии готовности

Этап 1:

- [ ] `doctor`: отказов нет;
- [ ] `ah init` владельца завершился кодом 0: каждое решение принято владельцем в терминале;
- [ ] повторный `apply` печатает `изменено: 0`;
- [ ] `verify --no-gates`: ошибок 0;
- [ ] PR этапа 1 открыт, локальный круг ревью прошел; без поставщика кода - ветка запушена.
{{#if module:forge/github}}- [ ] администратор подтвердил защиту веток и доступы из `installer/stages/STAGE-1.md`, раздел "Поставщик кода";
  непроверенные настройки и ответы 403 остаются блокерами готовности установки.
{{/if}}
Этап 2:

- [ ] заготовки заполнены фактами проекта;
- [ ] `check-all.py --docs --base origin/chore/harness-install`: все гейты документации зеленые, `verify --no-gates` из `KIT`: ошибок 0;
- [ ] с поставщиком кода - Check на голове PR этапа 2: каждый гейт из `check-all.py --docs --list` зеленый, кроме
  `adr-reference` и `secret-scan`: в Check они читают и код, и дерево целиком, и красными остаются только на
  нарушениях в коде, которые чинит этап 3; нарушение в документе в их выводе - работа этапа 2. Остальные
  красные гейты Check - вне `--docs`, их работа этап 3;
- [ ] выключенные правила несут причину и замену и названы в отчете;
- [ ] PR этапа 2 открыт в `chore/harness-install`, локальный круг ревью прошел; без поставщика кода - ветка запушена.

Этап 3:

- [ ] подключение к коду сделано: `apply --dry-run` не печатает строки о правке агента;
- [ ] `check-all.py --base origin/chore/harness-context`: все гейты зеленые, `verify` из `KIT`: ошибок 0, пробы отказали, Check на голове PR зеленый;
- [ ] PR этапа 3 открыт в `chore/harness-context`, ревью прошло; без поставщика кода - ветка запушена.

Приемка архива подтверждает состав и локальные проверки комплекта. Готовность установки в проекте
также требует проверки интеграций и административных настроек выбранных модулей; перечень действий
владельца в отчете не считается их выполнением.

```markdown
- Решения владельца: <id - значение>
- Выключенные правила: <id - причина - замена | нет>
- Правила без факта проекта: <правило - какого типа каркаса нет | нет>
- Правки файлов комплекта под проект: <путь - зачем | нет>
- Работа следующих этапов: <гейт - число нарушений - где | нет>
- Действия владельца: <права, защита веток, скрипт окружения облачного агента | нет>
- Секреты CI по модулям: <имя - задание - с какого момента нужен | нет>
- Не проверено: <что и почему>
```
